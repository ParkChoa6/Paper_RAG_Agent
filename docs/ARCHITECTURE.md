## 0. 一页看懂

```
═════════════════════ 离线：跑一次，几分钟 ═════════════════════

  data/raw/*.pdf
        │  ingest.py
        ▼
  data/processed/chunks.json   1345 条，带 paper_id / page / section
        │  index.build() → embed.embed_texts() → bge-m3
        ▼
  data/processed/vectors.npy  (1345, 1024) float32
  data/processed/ids.json     {model, count, dim, ids[]}


═════════════════════ 在线：每次提问，约 13 秒 ═════════════════

  用户问题
     │
     ├─ ① expand_query()            补英文写法（只给检索看）
     ▼
  DenseRetriever                    vectors @ q → 取前 50
     │  50 条 (chunk_id, 余弦)
     ▼
  CrossEncoderReranker              50 对逐对打分（CPU，10.6 s）
     │  取前 5
     ▼
  按 chunk_id 取回正文
     │
     ├─ ② generator.answer()        拼 prompt → qwen2:7b → 解析
     ▼
  {answer, used[], quotes{}}
     │
     ├─ ③ cite.verify()             每条 quotes 回材料原文里核
     ▼
  result {status, retrieved, parsed, problems}
```

**两条链路唯一的交点**是 `data/processed/` 里的两个文件。离线只写不读，
在线只读不写。所以「换嵌入模型」只要重跑后半段，「换切分逻辑」才需要整条重来。

## 1. 离线链路：PDF → 索引

### 1.1 三个产物

| 产物 | 内容 | 谁生成 | 失效条件 |
|---|---|---|---|
| `chunks.json` | `{count, chunks[]}`，每条一个段落 | `scripts/build_index.py` | 换 PDF / 改切分 / 改清洗 |
| `vectors.npy` | `(N, 1024) float32` | `scripts/build_vectors.py` | 换嵌入模型 / 换 chunks |
| `ids.json` | `{model, count, dim, ids[]}` | `scripts/build_vectors.py` | 同上 |

`ids.json` 和 `vectors.npy` **靠行序绑定**：`ids[i]` 描述的就是 `vectors[i]`。
这条纽带没有校验，只有 `count == shape[0]` 这一道粗检 —— 所以生产路径上
取正文永远**按 `chunk_id` 查**，不按行号。

### 1.2 ingest 的五道工序（顺序不能变）

```
  整篇 PDF
     │
     │  ⓪ 通读全文 → find_furniture()
     │     找出「版面家具」：去掉数字后，
     │     在 ≥3 页 且 ≥30% 的页面上重复出现的文本
     │     = 页眉 / 页脚 / 授权水印。★ 必须文档级视野，不能按页判断
     ▼
  逐页
     │
     │  ① 收块：跳过图片块、旋转块（竖排水印）、家具块
     ▼
     │  ② find_column_split()   找栏间空隙 → 双栏 / 单栏
     ▼
     │  ③ order_blocks()        排成【人读的顺序】
     │       单栏：从上到下
     │       双栏：带1左 → 带1右 → 跨栏块 → 带2左 → …
     ▼
     │  ④ 逐块：
     │       clean_text()        NFKC → 接行断词 → 压换行
     │       is_heading_block()  是标题 → 更新 current_section，不产出 chunk
     │       太短（< 40 字）      → 丢弃（图里的文字、公式碎片）
     │       参考文献段          → 丢弃
     │       否则                → 产出一个 Chunk
     ▼
  1345 个 Chunk
```

★ **②③ 必须在 ④ 之前。** `current_section` 是沿阅读顺序推进的状态；
顺序错了，一个 chunk 会被打上它**后面**那一节的标签 —— `section` 元数据就废了。
而 `section` 是「绝不砍」清单上的东西：prompt 用它，引用核对也用它。

★ **参考文献按 `section` 判，不是「遇到 REFERENCES 就停」。** 后者在参考文献
不在文末（比如前面有 Appendix）时会静默截断后面整篇。实测参考文献曾占全库 53% 的
chunk，且词面上跟领域问题高度重叠，不丢会挤掉真正的正文。

### 1.3 为什么建索引要两个脚本

```
  build_index.py     PDF → chunks.json     （文本层）
  build_vectors.py   chunks → vectors      （向量层）
```

两者的**失效条件不同**：换 PDF / 改切分逻辑只影响文本层；换嵌入模型只影响向量层。
合成一个脚本的话，换个嵌入模型也得把 PDF 重新解析一遍 —— 白等几分钟。

## 2. 在线链路：问题 → 答案

### 2.1 一次问答的调用账

| 步骤 | 干什么 | 谁在算 | 实测耗时 |
|---|---|---|---|
| ① 查询扩展 | 扫原问题，追加英文写法 | 纯 Python，< 1 ms | — |
| ② 嵌入 query | 1 条文本 → 1024 维 | bge-m3 (Ollama) | 与 ⑤ 合计 |
| ③ 粗排 | `(N,D) @ (D,)` 一次矩阵乘法 | numpy | 0.09 ms（★237 条时量的） |
| ④ 重排 | 50 对 (问题, 正文) 逐对打分 | bge-reranker-v2-m3 (CPU) | **10.6 s** |
| ⑤ 生成 | prompt → 一段 JSON | qwen2:7b (Ollama) | ②+⑤ ≈ **1.3 s/题** |
| ⑥ 引用核对 | 字符串子串匹配 | 纯 Python | < 1 ms |

⚠️ **②⑤ 没有拆开量过。** `1.3 s` 是 dense 臂端到端的整题耗时，
里面混着嵌入和生成，本表不假装能分开。要拆开得单独加计时。

⚠️ **③ 的 0.09 ms 是在 237 条语料上量的**，现在是 1345 条 ——
就算线性放大到 ~0.5 ms，结论不变（仍是 0.24% → 0.04% 这个量级），
但**那个数字描述的语料已经不是现在这个了**。

**重排占了约 80% 的时间。** 这不是没优化 —— 是优化过了：
`RERANK_BATCH_SIZE` 从上游默认的 32 改成 4，同一批候选、同样的分数，
18.3 s → 10.6 s。理由写在
[`config.py`](../paper_rag/config.py) 的 `RERANK_BATCH_SIZE` 注释里
（上游默认值是照「GPU ⇒ 无 padding」选的，在 CPU 上是反的）。

### 2.2 检索为什么要两个阶段

```
        query
          │
          ▼
  ┌───────────────────────────────────────┐
  │ 粗排 DenseRetriever  pool = 50        │  只比向量，快但粗
  └───────────────┬───────────────────────┘
                  ▼  50 条候选
  ┌───────────────────────────────────────┐
  │ 重排 CrossEncoder                     │  逐对读正文，慢但准
  └───────────────┬───────────────────────┘
                  ▼  取前 k = 5
            送进 prompt
```

**`pool` 必须明显大于 `k`**，否则重排只能在你给它的 5 条里换顺序，第 6 名永远上不来 ——
而「正确答案排第 6」恰恰是重排最该修的情况。

实测（28 题）的天花板：`pool=5` 时 recall@5 = 71%，`pool=20` 时 86%，
`pool=50` 时 89%。多捞 45 条，把天花板抬高了 18 个点。
而 pool 从 50 加到 200 只换来 4 个点（就一题），代价是候选翻 4 倍 ——
**这是权衡，不是越大越好。**

### 2.3 生成：一次调用里有三道契约

```
  build_prompt(question, chunks)
        │
        │  ★ 契约一：材料用 render_material() 渲染
        │     "[1] （标题 · 章节，第 8 页）\n 正文…"
        │     ↑ 表头里的标题是【判别器】，不是装饰：它让模型分得清
        │       「嵌入那篇」和「推理那篇」，否则会张冠李戴而引用全是真的
        ▼
  llm.generate(format=GEN_SCHEMA)
        │
        │  ★ 契约二：JSON Schema 约束解码
        │     采样器被限死在合法 JSON 上，从源头掐掉「壳没闭合」
        ▼
  parse_response()
        │
        │  ★ 契约三：只校验【形状】—— answer 非空、used 是整数、quotes 是字典
        │     内容真不真，不归它管
        ▼
  {answer, used, quotes}
```

三道契约必须一致，少改任何一处，症状各不相同且都难查。
`GEN_SCHEMA` 是 prompt 里那个示例的机器可读版本，`parse_response` 是它的执行者。

### 2.4 引用核对：校验器站在「模型看到的那份材料」这边

```
  材料 ──render_material()──┬──▶ prompt ──▶ 模型 ──▶ quotes
          ▲                 │
          │                 └──▶ cite.verify 的比对基线
          │                        （同一个函数，不是抄一份）
          └────────────────────────┘
```

★ 这不是代码复用，是**正确性要求**：模型会把表头一起抄进 quotes，
如果校验基线只有正文，一条**真引用**会被报成**伪造**。
2026-10-09 第一次端到端跑就撞上了。

`verify()` 查四件事：

| # | 查什么 | 病名 |
|---|---|---|
| ① | `used` 里的编号越界 | 引用了不存在的材料 |
| ② | 说了用、交不出原句 | 声称使用但未提供原文 |
| ③ | 交了原句、没说过要用 | 提供了原文但未声明使用 |
| ④ | 原句在材料里找不到 | **再分两种**：编号错配 / 疑似伪造 |

## 3. 接口设计

### 3.1 `Retriever`：一个只需要两个成员的 Protocol

```python
class Retriever(Protocol):
    name: str
    def search(self, query: str, k: int) -> list[tuple[str, float]]: ...
```

返回的是 `(chunk_id, 分数)`，**不是正文**。分数**不在检索器之间可比**：

| 实现 | 分数是什么 | 范围 |
|---|---|---|
| `DenseRetriever` | 余弦相似度 | [−1, 1] |
| `BM25Retriever` | BM25 分 | [0, +∞) |
| `RerankedRetriever` | cross-encoder logit | 无界，可负 |

所以判断检索好不好，看**排序**和**「对的那条在不在里面」**，不要看绝对值。

### 3.2 四个实现，接口一次都没改

```
                    Retriever (Protocol)
                           ▲
        ┌──────────────┬───┴──────────┬─────────────────┐
    DenseRetriever  BM25Retriever  RerankedRetriever  OracleRetriever
    （S5-1）         （S5-2）        （S5-5）            （评测里手搓的假货）
```

- `RerankedRetriever` **包装**另一个 Retriever：先让底下的捞 `pool` 条，再重排取 `k`。
- `OracleRetriever` 只在 `eval_answer.py` 里存在：它把标准答案直接当检索结果返回。
  **生产代码一行没改就接进去了** —— 这是那个 Protocol 判断的第三次兑现。

### 3.3 为什么 `search()` 收的是 `query: str`，不是 `query_vec: list[float]`

**BM25 根本没有 query 向量。** 接口要是收向量，BM25 就实现不了这个接口，
只能在外面包一层假的，这个抽象当场失去意义。

收文本，则每个实现自己决定怎么理解它：dense 嵌成向量，BM25 分词查倒排表。
另一条路「接口收向量，BM25 那边传 None」叫「只对一半实现成立」——
那是抽象漏了，不是抽象。

### 3.4 为什么重排器不是第三个 `Retriever`

看输入：

```
  Retriever.search(query)              → 只有 query，自己去全库找
  Reranker.rerank(query, candidates)   → query + 一批已经捞回来的候选
```

重排器**没有能力检索**，也拿不到全库。把 rerank 塞进 `Retriever` 接口，
等于逼每个重排器都先实现一遍「怎么从 1345 条里捞 50 条」—— 而那件事它根本不干。

但「检索器 + 重排器」这个**组合**应该仍然长得像检索器 —— 所以有
`RerankedRetriever implements Retriever`。这样评测脚本和 `pipeline.ask()`
一行都不用改。

## 4. 失败怎么分类

> ★ 这一节是整个项目最贵的一条经验：
> **一个把不同性质的失败糊成一个数的指标，会指向错误的修法。**

### 4.1 `ask()` 的四个 `status`

```
                 generator.answer() 抛异常？
                          │
               是 ────────┴──────── 否
                │                      │
         parse_failed           used 非空？
      （模型没按格式交付）       │
                       是 ─────┴───── 否
                        │              │
                     answered    answer == REFUSAL_TEXT？
                 （走 verify）     │
                            是 ────┴──── 否
                             │             │
                          refused       suspect
                       （真拒答）   （给了答案却零引用）
```

★ **最危险的一条边是 `suspect`。** 以前「有答案、无引用、又不是标准拒答话术」
会被当成「本次没有引用，跳过校验」—— 一次**解析失败**就这么伪装成了一次**正常的拒答**，
全程无人报错。

★ 另一个方向：`parse_failed` **不抛异常**（入口崩掉对用户没意义），
但也不许悄悄降级成拒答。`parse_failed` 和 `refused` 是两个 status，不允许合并。

### 4.2 `verify()` 的四类问题，④ 还要再分一次

实测 684 条真实 quote，旧版 `verify` 报了 56 条问题：

```
  56 条报错
   ├── 19 条  假警报   ← ★ 校验器自己看错了（我们的锅）
   │           材料被 PDF 抽取弄坏：丢空格、连字符断行、表头夹在中间
   │           而模型是 token 级生成，它会把坏的"修好" → 真引用被报成伪造
   ├──  8 条  编号错配 ← 内容真的、编号贴错。是模型的错，但【不是伪造】
   └──  2 条  真伪造   ← 校验器正常工作 ✅
```

**病名必须报对**，因为两种病的药完全不一样：

| 病 | 药 |
|---|---|
| 编号错配 | 改 prompt（让它先定编号再写句子） |
| 真伪造 | 这一层本来就该挡住 —— 说明它工作正常 |

旧版把这两种糊成一句「原文中找不到对应内容（疑似伪造）」—— 拿着
「模型会编引用」的结论，你会去修一个不存在的病。

**改松判据的代价是明说的**：`_norm` 现在删掉所有空白和标点，
所以 `"a b"` 和 `"ab"` 不再能区分。仍然认这个代价，因为这条校验的对手
是**一个会努力模仿格式的模型**，它不是排字工人 —— 它编出来的句子和原文的差别
是**成句的**，不是一两个空格。实测改松之后 2 条真伪造一条没被放行，
其中一条只差 1 个字母（`causality` vs `causalcity`）照样抓住。

### 4.3 「找不到」不是一种病，是三种

同样的思路，`recall@k` 的「没找到」也拆成了三种，修法各不相同：

```
  没找到
   ├── 空结果       query 里一个词都没进倒排表（BM25 撞上纯中文）
   ├── 未进候选     粗排没捞进 pool —— 重排再神也救不回来
   └── 排名靠后     进了 pool，但排在 k 名之后
```

★ 这也是「平均排名」这个指标被判死刑的原因：pool 从 50 到 200 时，
它给的两个版本**方向相反**（只统计找到的题说变差，全量说大幅变好），而且两列都有偏。
现在改用 `recall@k`（找到了吗）+ `Top-1`（排第一了吗），两个分开报。

### 4.4 `parse_failed` 的修法：不是容错解析，是把契约交给采样器

实测 8 次运行 × 28 题，`parse_failed` **每次都是 `[Q6, Q13]`** ——
不是「随机 7%」，是「这两题上必然失败」。

```
  Ollama 响应里的 done_reason = 'stop'，不是 'length'
  → 不是被 num_predict 砍短的，是模型自己停了，而 JSON 的壳没闭合
```

缺的是**字符**（少一个 `}`），不是**切点** —— 所以容错解析（预写的 `raw_decode`）
对这个病无效，没有合法 JSON 可解。

修法：把 JSON Schema 交给 Ollama 的 `format` 参数，**在模型开口之前限死它的嘴**。
实测 8/16 失败 → 16/16 通过，而且内容一个字没变。

⚠️ 别传裸 `"json"`：语法太松，模型在允许的空白里打转，触发 Ollama 的重复保护直接 500。
**必须传具体 schema。**

## 5. 评测装置

三把尺子，量的东西不同，**不能混在一起测** —— 否则分数动了你不知道是模型的锅、
策略的锅，还是生成层的锅。

```
  一把尺子                       固定什么            换什么
  ─────────────────────────────────────────────────────────────
  eval_embed.py                  检索方式            嵌入模型
  eval_retrieve.py               题 + 语料           检索策略
  eval_answer.py                 整条流水线          三个 arm

  一个算分器
  score_judge.py                 人填的盲判表        揭盲 + 配对检验
```

### 5.1 `eval_answer.py` 的三个 arm

```
  dense      控制组。只跑生产配置的话，「合规率 79%」没有参照系
  rerank     生产配置
  oracle     ★ 把标准答案直接当检索结果喂进去 → 检索层 100% 正确
```

有了 oracle，一条脱节的流水线才能被**切开**：

```
  检索层的损失 = 1 − 材料含答案率
  生成层的损失 = oracle 的失败率
```

没有它，你看到「rerank 合规率 79%」只能干瞪眼：剩下 21% 是没捞到，还是捞到了没用？
**修法完全不同。**

### 5.2 判卷表是盲的

`eval_answer.py` 产出三件东西：

| 文件 | 给谁 |
|---|---|
| `e2e_results.json` | 机器，全部原始结果 |
| `e2e_judge.md` | **人**，盲判表：甲 / 乙 / 丙 逐题打乱，不知道哪个是「新方法」 |
| `e2e_key.json` | 揭盲用，填表时别看 |

★ 不盲的话，你会在看到答案之前就知道哪个是新方法，然后不自觉地宽容它 ——
这不是道德问题，是人脑的默认行为。

★ 判卷表是 **28 题 × 3 臂 = 84 个格子**，全靠人手填。填完之后**不能靠人眼数**：
「dense 大概对了 18 题吧」—— 那 84 个格子里积累的注意力，
就在最后一步换成了一句估计。人做判断，机器数数。

## 6. 依赖方向

```
  ┌───────────────────────────────────────────────┐
  │  scripts/  入口 / 评测 / 探针（脚手架）         │
  └───────────────────────┬───────────────────────┘
                          │ 只能向下依赖
  ┌───────────────────────▼───────────────────────┐
  │  pipeline.py    编排，不含业务判断              │
  └──┬────────┬────────┬────────┬────────┬─────────┘
     │        │        │        │        │
  ingest   index   retriever  rerank  generator
     │        │        │        │        │
     │        │     retrieve.py │        │
     │        │                │        │
     └────────┴────────┬───────┴────────┘
                       ▼
          cite.py ──(import render_material)──▶ generator.py
                       │
  ┌────────────────────▼──────────────────────────┐
  │  config.py / llm.py / embed.py / logger.py    │
  │  基础设施：谁都能用，自己不依赖业务模块        │
  └───────────────────────────────────────────────┘
```

一处**故意违反分层**的 import：`cite.py` 从 `generator.py` 里取 `render_material`。
直觉上校验层不该依赖被校验的东西，但 `verify` 要回答的问题是
「这句话是不是从**模型看到的那份材料**里抄的」—— 它**必须**知道模型看到的是什么，
而只有 `render_material()` 知道。

不 import 的后果是校验层自己再拼一遍材料，两份拼法迟早漂移，
**而漂移的表现是「真引用被报成伪造」** —— 一个没人会往 import 上查的 bug。

## 7. 关键决策表

| 决策 | 结论 | 依据 |
|---|---|---|
| 用 LangChain 吗 | **不用**，全手写 | 看清 RAG 的真实面目就是 for 循环 + 一次 API 调用。之后再用框架是「选择」，不是「只能」 |
| 上向量库吗 | **不上**。numpy 暴力检索 | 1345 条上占一次问答的 0.24%；FAISS 把它变成 0.09%。触发条件见 `requirements.txt` |
| FAISS 为什么还装着 | 装了，**不接线** | 在错得起的小语料上先把 API 用熟。删之前先读那四条触发条件 |
| 重排跑 GPU 吗 | **CPU** | 4070 的 12GB 还要给 Ollama；挤进去撞显存墙时，现象是「Ollama 超时」，看不到重排的错 |
| RRF 融合 BM25 + dense | **否决** | 实测最优权重 = 0。机制为真（两边错法不同），但整体是负的 |
| 表头里放论文标题吗 | 放，**截断 40 字** | 标题是判别器：只有真标题才让模型敢排除另一篇。太长模型干脆不交 quotes，太短判别词被切断 |
| 生成温度 | `temperature=0` | 入口也要可复现。但注意：**它相当可复现是量出来的**，不是从参数名推的 |
| 拒答文案 | `config.REFUSAL_TEXT` 一个常量 | prompt 和判断逻辑引用同一个值。以前只写在 prompt 里，代码无法区分「真拒答」和「解析失败伪装成拒答」 |

## 8. 改配置前的清单

`config.py` 不是「参数表」，是**决策日志**。每一块常量上面都写着
「为什么是这个值 / 量过什么 / 什么时候该重量」。改之前先看这几条：

1. **改任何检索侧的开关，先问：生产的取值是这个吗？**
   这个仓库栽过三次：query 前缀只活在评测脚本里、查询扩展开关评测里从来不存在、
   `RETRIEVE_POOL` 决策定在 50 但 `config` 还写着 20。
   ★ 三次的共同点：**不改代码路径、不报错、不影响单测，只让评测和生产悄悄量不同的东西。**
   ★ 而且「只有一个来源」还不够 —— **这个来源还必须被回写过**。

2. **改嵌入模型 → 必须重跑 `build_vectors.py`。**
   `index.load(model=...)` 会替你核对；对不上直接报错，而不是拿不可比的向量
   算出一堆看起来正常的错结果。

3. **改切分逻辑 → 必须重跑 `build_index.py` 和 `build_vectors.py`。**
   `chunks.json` 变了，`vectors.npy` 就过期了，而行序错位**不会报错**。

4. **改 `RERANK_MAX_LENGTH` 要重测指标；改 `RERANK_BATCH_SIZE` 不用。**
   前者是**截断**（真丢信息），后者是**调度**（不改数学，实测 max|Δ分| = 4e-7）。
   ★ 两条加速路必须分清 —— 光看数字分不出来，而且前者的数字可能更好看。

5. **加语料 → 三件事：登记 `PAPERS`、重跑两级索引、补评测题。**
   没补题的那几篇，所有指标都测不到它 —— 而指标不会报「我没测」。

6. **换生成模型 → 重量一遍约束解码。**
   语法约束是**和模型配合**的关系，不是普遍安全的。裸 `"json"` 在 qwen2:7b 上
   触发 500 就是证明。
