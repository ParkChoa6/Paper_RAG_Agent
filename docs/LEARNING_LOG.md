### ✅ S5-5 完成：cross-encoder 重排 —— **第一个真正涨点的改动**

S5-3 拒绝 RRF 时顺手量出一张 **recall@k 曲线**，那才是本步的起点：

```
Top-1 只有 50%，而 recall@20 有 86%
→ 意思是【在第 6~20 名之间躺着一堆正确答案，只是排序排错了】
→ 这是【排序问题】，不是召回问题。而 RRF 已经证明修不了这个。
```

**做法**：粗排捞宽（pool=50）→ cross-encoder 逐对 `[query+正文]` 重打分 → 取前 5。
本地跑 HuggingFace 的 `bge-reranker-v2-m3`（★ **Ollama 0.40.2 没有 `/api/rerank`**，
实测直接 404；架构上它也是给「tokens→文本」的生成式模型设计的）。

| | Top-1 | MRR | recall@5 |
|---|---|---|---|
| dense 单独 | 50% | 0.605 | 71% |
| **+ rerank @pool50** | **68%** | **0.763** | **89%** |

★ **本步最重要的四条**（详见记录）：

1. **动手前先算天花板。** 天花板(pool) = `recall@pool` —— 它**只依赖粗排，不依赖重排器**。
   所以"pool=5 的重排最多只能到 71%"是**跑之前就知道的**。
   这比事后解释好用得多：它把"重排没效果"和"重排没机会"提前分开了。
2. **天花板兑现率** = Top-1 ÷ 天花板 —— 一个**跨 pool 可比**的量（绝对值不可比，因为天花板在变）。
3. **我预注册的四条猜对了两个、错了两个**，而**错的那两条更有价值**：
   我预测"pool 越大越差"（机制：候选越多越容易被带偏），
   实测**单调变好直到 pool=50**。而那个机制**是真的** —— Q7 的排名一路 `3→3→4→5→6→7→7`。
   > ★ 这是 S5-3 那条教训的**镜像**：
   > S5-3「机制为真 → 整体是负的」；S5-5「机制为真 → 整体是正的」。
   > **合起来一句：局部机制的方向不能预测整体结果，只有量能。**
4. ★★ **`平均排名` 这个指标被正式判死刑**：
   ```
   p50  → p200，原列：97.7 → 2.6   （看着【大幅变好】）
              只算找到的：1.65 → 2.57 （真相：【变差】）
   ```
   **两列方向完全相反，而且两列都有偏**：原列被哨兵值 `1346` 主导（偏袒大 pool），
   只算找到的那列是幸存者偏差（偏袒小 pool）。
   → **正确做法：分开报 `recall@k`（找到了吗）和 `Top-1`（排第一了吗），别用"平均排名"。**
5. ★★ **"遇到质量换速度的两难，先问一句：这个速度是真的吗？"**
   收尾时量出一件事：`pool=50` 要 **18.3 秒/题**，而 `pool=20` 只要 10.8 秒 ——
   我确实在犹豫"7 个 Top-1 点值不值 7.5 秒"。
   **那个两难是假的**：`CrossEncoder.predict` 默认 `batch_size=32`，
   而 32 是上游照「GPU + flash attention ⇒ 没有 padding」选的。
   **我们在 CPU 上跑，padding 要真算** —— 改成 4 之后：

   ```
   pool=50：18.9s → 10.6s（快 44%），而【指标一个字都没动】
   ```
   ★ 这不是"我觉得等价"：实测 3 个查询的全序完全一致（|Δ分| ~ 4e-7），
   并且**用官方脚本重跑复核过** —— `50%/0.605/71%` 和 `68%/0.763/89%` 逐位相同。

   > ★ 两条加速路，为什么只走了一条：
   > `max_length` 512→128 能省 68%（更多），但那是**截断**（省的是真内容）；
   > `batch_size` 32→4 省 44%，那是**调度**（省的是白算的部分）。
   > **区别不在省了多少，在于省的是哪一种 —— 而光看数字分不出来。**
   > 更坑的是：`max_length=128` 那行的指标**看起来更好**（Top-1 67.9% → 75.0%），
   > 但那只是 2 题，且集中在我们**已经怀疑 ground truth** 的题上，而且**不单调**
   > （512→256 变差、256→128 变好）—— 那是噪声，不是机制。**没采纳。**

### ✅ S5-6 完成：端到端评测 —— ★★ **它改了后面的路线**

S5-5 自己写下的缺口：「本步量的全是检索指标。Top-1 涨 18 点，
**不等于**答对的题多了 18 点。」—— 本步就是去**证伪**这句话。

**做法**：三个 arm 跑同一批 28 题、都走 `ask()`、`temperature=0`：

| arm | 是什么 | 为什么必须有 |
|---|---|---|
| `dense` | 关掉重排 | **控制组** —— 只跑生产配置的话，那个数字没有参照系 |
| `rerank` | 生产配置 | 被检验的对象 |
| `oracle` | ★ 把**标准答案直喂**给生成层 | **把检索层和生成层切开** |

★ `oracle` 靠的是 S5-1 定的 `Retriever` Protocol —— 它只要 `name` + `search`，
所以**手搓一个作弊的假检索器就能塞进 `ask()`，产品代码一个字没改**。
这是那个接口判断的**第三次兑现**（dense→bm25 / +rerank / →一个假货）。

| arm | 材料含答案（检索层） | **合规回答（答案质量）** | 秒/题 |
|---|---|---|---|
| `dense` | 71% | **79%** | 1.3 |
| `rerank` | **89%** | **79%** | 13.3 |
| `oracle` | 100% | **82%** | 1.3 |

★ **本步最重要的五条**（详见记录）：

1. ★★★ **检索涨 18 点，答案质量 0 点。**
   配对 McNemar：`b=2, c=2, p=0.617` —— **换了 2 题，净变化是零**。
   而那 4 次翻转**全部发生在生成层**（Q10 尤其刺眼：rerank **把正确材料捞进来了**，
   模型**还是拒答**）。
   > **中间指标（你能自动算的）和出口指标（用户真正在意的）之间隔着一条河 ——
   > 宽度必须量，不能推。** 这是 S5-1~S5-5 全部在优化检索之后，
   > 第一次回头看"那用户到底拿到了什么"。

2. ★★★ **检索满分时，生成层也只到 82%。** `oracle` 自己就丢了 5 题。
   **② 生成层的损失 > ① 检索层的损失 → 瓶颈不在检索。**
   ★ 这一条**改了 Stage 5 的后续路线**：剩下的计划项（HyDE / multi-query）
   **全是检索侧的** —— 在瓶颈修好之前做它们，
   是**在一条已经到顶的路上继续加速**。

3. ★★ **报数之前先算这台仪器的分辨率。** n=28 时 80% 附近 95% 区间 **±15 点**；
   要分辨 ±5 点需要 **~246 题**。
   → 所以能站住的最强说法是「**没有证据表明答案质量涨了 18 点**」，
   **不是**「它一定没涨」。★ 而且**连检索那 +18 点，配对检验也只有 p=0.131**。
   > **样本量不是一个"越多越好"的常数，它取决于你要分辨的效应有多大。
   > 换指标 = 换效应量 = 可能就得重新算样本量。**

4. ★★ **「引用有问题」不是一种病，是四种。**
   把引文原文挖出来、逐条回全语料找，分开了：
   ```
   前缀      引文【完全正确】，只是前面多抄了个 "[1] "   ← ★ 这是我们 prompt 埋的坑
   引错编号   内容真实存在，编号数错了
   幻觉      引文在【整个语料】里都不存在
   ```

## 课程 0A-1 · dict 与 list —— RAG 的数据单元

**日期**：2026-09-18
**产出**：`lessons/lesson01.py`

### 学到什么

- **`list[dict]` 是 RAG 的原子结构**：用 dict 描述一个实体（一段文本 + 它的出身），用 list 装一串
- **元数据设计**：`paper_id` / `page_start` / `page_end` / `section` —— 这是 Stage 4「引用原文」能实现的唯一前提
- **f-string 引号嵌套**：外层双引号、内层单引号
- **累加器模式**：初值写在循环外，累加写在循环内
- **`d[k]` vs `d.get(k)`**：前者缺键抛 `KeyError`，后者返回 `None`
  →「**让它炸** 还是 **静默兜底**，是一个主动的设计选择」，不是随手挑一个
- **三类错误的区别**：

  | 错误 | 何时发生 | 怪谁 |
  |---|---|---|
  | `SyntaxError` | 代码解析时，一行都没跑 | 代码写错了 |
  | `NameError` | 运行到该行，名字还不存在 | 执行顺序 / 作用域 |
  | `KeyError` | 运行到该行，数据缺键 | 数据不符合预期 |

- **变量有生命周期**：名字只有在被赋值之后才存在。代码是自上而下执行的，不是「读完整份文件再决定怎么跑」
- **数据结构选型的权衡**：表达能力 vs 结构简单。选了 `page_start`/`page_end`，就放弃了表达「不连续页码」的能力

### 踩过的坑

1. `pageid` → 应为 `paper_id`。**字段名是接口契约**，且 `page_id` 与 `page` 并存会产生歧义
2. `summary_text` 命名与内容不符 —— 装的是数字，不是文本
3. 误以为「数据缺键」会**语法报错**或**返回 None** —— 实为运行时 `KeyError`（首次答错）
4. `page_range` 写在循环**外** → `NameError`
   - 延伸认知：若把它挪到循环**后**则不报错，但会给所有行打印**同一个**页码 —— **静默错误比崩溃危险得多**
5. 页码最初想设计成字符串 `"3-4"` → 类型污染，下游数值比较全部失效

### 待复习

- `SyntaxError`（解析期）与运行时异常（执行期）的边界 —— 第一次答错
- 做数据结构选型时，要能主动说出「**我放弃了什么**」

## 课程 0A-2 · 函数与返回值

**日期**：2026-09-18
**产出**：`lessons/lesson02.py`

### 学到什么

- 函数三要素：`def` / **参数**（输入）/ `return`（输出）
- **`return` vs `print`**：return 给**程序**用，print 给**人**看
  - 判断标准：「**这个结果后面还要用吗**」
  - 用错的伤害会**传播**：`s = format_chunk(chunk)` 得到 `None`，`len(s)` 崩在离案发现场很远的地方
- **参数 vs 外部变量**：依赖外部变量 = **隐藏依赖** → 行为不可预测、无法独立测试
- **接口设计**：函数只该知道它负责的那部分
  - `format_chunk(chunk)` 接整块 —— 因为它的职责**就是**「显示一个 chunk」
  - `format_pages(page_start, page_end)` 接两个整数 —— 它的职责只是「格式化页码」，与 chunk 无关
  - → 要避免的不是耦合本身，是**无关的耦合**
- **重构**：改变结构、不改变行为。验证方式是「**跑出来对比**」，不是「我觉得应该没问题」
- **生成器表达式与 `sum()`**：`sum(gen)` 就是累加器的封装
  - `sum([])` 返回 `0` —— 初值现身
  - `sum([1,2,3], 10)` 返回 `16` —— 第二个参数**就是**初值
- **声明式 vs 命令式**：描述「要什么」比描述「怎么做」更不易出错，直接消灭了「代码放错位置」这一整类 bug

### 踩过的坑

1. `return(...)` —— return 是**语句**不是函数，括号让它看起来像函数调用
2. 多行续行缩进与函数体同级 → 读起来像新语句（`Ctrl`+`Alt`+`L` 一键格式化）
3. 长 f-string 里直接嵌套函数调用 → 读者需要「停下来解析」。**凡是需要解析的地方，都值得一个名字**

### 待复习

- **「能看懂语法」≠「能判断该不该用」** —— 补全能给语法，给不了判断
- 生成器表达式的术语：它**产生**迭代器，它自己不是迭代器

### 验收

## 课程 0A-3 · 类与对象

**日期**：2026-09-18
**产出**：`lessons/lesson03.py`

### 学到什么

- **类 = 图纸，实例 = 按图纸造出来的东西**。类名首字母大写（`Chunk`），变量名小写（`chunk`）
- **`__init__`**：创建实例时自动运行，用来装初始数据
- **`self` = 指向「当前实例」的引用**
  - 在 CPython 里 `id(self)` 返回的就是内存地址 —— 说它是「指针」字面上正确
  - **`self` 是隐式传递的**：`a.who()` 实际执行的是 `Chunk.who(a)`。这就是为什么方法定义里要写 `self`
- **方法 = 挂在对象上的函数**。`format(self)` 括号里是空的 —— 数据已经在对象身上了，不用传
- **封装的实际收益**：从「**伸手进数据结构掏数据**」变成「**请求对象自己报数**」

  | 上一课（dict） | 这一课（类） |
  |---|---|
  | `len(chunk['text'])` | `chunk.char_count()` |

- **为什么 `Retriever` 是类**：不变的配置（向量库、模型、top_k）存在对象里，每次变的（query）才当参数传

### 踩过的坑

- 无 —— 本课代码一次通过
- 自主引入了 `if __name__ == "__main__":`，但**理解尚未验证** → 已转为 0A-4 的入口

### 待复习

- **类 vs dict 的取舍：答案不是「类更好」，而是「两个都要」**
  - 内存里用**类**操作（有方法、能校验）
  - 出门前用 `to_dict()` 转成 **dict** —— 因为 JSON、向量库 metadata、LLM 工具参数**只吃 dict**
  - 类放弃的正是「零成本进出外部系统」的能力
- **类可以堵住非法状态**：`__init__` 里 `if page_end < page_start: raise ValueError(...)`
  → 非法的 Chunk **根本创建不出来**。这才是「更安全」的确切含义：**让非法状态无法被表示**
  → 呼应 0A-1 那条「`page_start=5, page_end=3` 是非法状态，但 dict 允许它存在」

## 课程 0A-4 · 模块与 import ✅

**日期**：2026-09-18 讲概念 / 2026-09-20 完成练习与验收
**产出**：`lessons/chunk.py` + `lessons/lesson04.py`

### 学到什么

- **模块 = 一个 `.py` 文件**，文件名去掉 `.py` 就是模块名
- **包 = 含 `__init__.py` 的文件夹**。`__init__.py` 可以是空的，作用是告诉 Python「这是包」
- **`__name__` 的值取决于文件「怎么被使用」**

  | 使用方式 | `__name__` 的值 |
  |---|---|
  | `python x.py`（直接运行） | `"__main__"` |
  | `import x`（被导入） | `"x"`（模块名） |

- **`if __name__ == "__main__":` 的真正作用**：
  > 「只有当我是程序入口时才执行这段；被人 import 时，闭嘴。」
  - **它防的不是「直接运行」，而是「被 import」**
  - 删掉守卫、取消缩进、直接运行 —— 行为**毫无区别**（这正是最容易误解的地方）
  - 项目里的意义：否则 `from chunk import Chunk` 会**自动执行** `chunk.py` 底部的测试代码 —— 在 RAG 项目里等于自动跑一遍 PDF 解析、自动调一次模型、自动烧一次钱

- **`import` 会真的「执行」那个文件** —— 不是读取、不是引用，是**从头到尾跑一遍**
- **两种写法执行的东西完全相同**（用 `lib.py` / `use1.py` / `use2.py` 实验证实）：
  `import lib` 和 `from lib import A` **都**把整个文件跑一遍，区别**只在于你的命名空间里多了哪个名字**

  | 写法 | 命名空间多了 | 用法 |
  |---|---|---|
  | `import lib` | 只有 `lib` | `lib.A()` |
  | `from lib import A` | `A` | `A()` |

- **撞名风险落在 `from x import Y` 上** —— 后 import 的**静默覆盖**前面的，不报错
- **import 的代价由「被 import 文件的顶层副作用代码量」决定**，守卫是**消除**代价的手段（不是决定代价的东西）
- **循环 import**：`sys.modules` 缓存救了你 —— 第二次 import 直接返回**半成品模块对象**，不会无限递归
  - 炸点：**在顶层立刻使用对方的名字**（此时对方还没执行到那里）
  - 安全写法：顶层只放定义，把互相使用推迟到函数体里
- **两个时间点**（本课最重要的收获之一）：
  - **定义期 / 文件加载期**：类体代码、`if __name__` 的判断 —— 文件被加载时执行
  - **调用期**：方法体、方法之间的调用 —— 被调用时才执行
  - 证据：埋的雷打印在**第一行**，比 `[paper_001]` 还早，而那一刻 `format` 一次都没被调用
- **`__name__` 的值取决于文件「怎么被使用」**：直接运行 = `"__main__"`，被 import = 模块名
- **`if __name__ == "__main__":` 防的不是「直接运行」，是「被 import」**
- **守卫保护的不是「文件」，是「文件里的顶层副作用代码」**
  - 判断标准：这行代码在「我只是想借用一下这个文件」时被执行，是好事还是坏事？坏事 → 加守卫
- **拆文件的真正价值**：让 `from splitter import split_pdf` 时被执行的顶层代码**只剩 `splitter.py` 那一点**，`main.py` 的副作用被躲开

2. **答错**：认为「两种写法执行的东西不一样，后者只执行 Chunk 类代码」—— 被 `use1/use2` 实验证伪，**两者都执行整个文件**
3. **因果说反**：把「import 的代价由什么决定」答成「由守卫代码的编写决定」—— 应为「由顶层副作用代码决定，守卫是消除手段」

5. 守卫最初缩进写在**类体内部**（行为正确但语义误导）—— 已移出到模块层

## 课程 0A-5 · 异常处理

**日期**：2026-09-20
**产出**：`lessons/lesson05.py`

### 学到什么

- **`raise` ≠ `except`** —— 这两个词最容易混：

  | 动作 | 谁在做 | 职责 |
  |---|---|---|
  | `raise` | **发现问题的人** | **报告**：「这里不对！」 |
  | `except` | **能处理问题的人** | **接手**：「我来处理」 |

- **traceback 从下往上读**：最后一行是异常类型 + 消息（案发现场），往上倒着看是谁把它调成这样的
- **自定义异常**：`class MyError(Exception)`；类体里只放 docstring 也合法（字符串字面量会成为 `__doc__`）
- **自定义异常 = 接口防火墙**（本课核心）：把实现细节关在门内
  - 调用方只认 `PDFLoadError`；里面换成 PyMuPDF / pdfplumber / 后缀名判断，调用方一行都不用改
  - 若让底层库的异常直接漏出去，调用方就被迫 `except fitz.FileDataError` —— **依赖了你用的库**，换库全崩
- **「什么时候该捕获」的判据**：**处理方式是否取决于调用方？**
  - 取决于调用方 → **让它炸**（你没资格替调用方决定）
  - 你此刻就知道怎么办、且不依赖调用方 → **捕获**
  - 一句话：**谁有能力决定，谁负责处理**
- **fail fast**：早抛异常 → traceback 短、离案发现场近；返回 `None` 会让错误传播到很远才暴露（呼应 0A-2「用错的伤害会传播」）
- **方法 vs 模块级函数**（用户自己提出的好问题）：
  - 判据：**方法体里从没用过 `self` → 它不该是方法**
  - `check_pdf_name` 无状态 → 放模块层
  - 异常类的 `__init__(self, path, reason)` 存状态 → **必须**是方法
  - 反证：若 `check_pdf_name` 是方法，调用要写成「先造一个错误，再用它检查文件名」—— 依赖方向反了

### 踩过的坑

1. **把函数和 main 块一起写进了类体里** —— 0A-4 同一个坑**复发**
   - 报错：`NameError: name 'PDFLoadError' is not defined`
   - 原因：类体在**定义期**执行，而那一刻类自己的名字**还没绑定**
   - traceback 里的 `in PDFLoadError` 就是「这行代码正在类体里跑」的直接证据
   - 修正：整块左移 4 格，回到模块层
2. **术语混用**：把 `check_pdf_name` 里的 `raise` 说成「捕获」—— 它一个字都没捕获
3. 调用了函数但没 `print`，返回值被丢弃（0A-2「return 给程序用，print 给人看」）
4. docstring 里多打了个 `*`

### 待复习

- **`raise` vs `except` 的分工** —— 第一次答混了
- **「方法体里有没有 `self`」** 这条判断标准
- **类体的执行时刻（定义期）** —— 这个坑已经犯了**两次**（0A-4、0A-5），下轮重点复习

## 课程 0A-7 · 虚拟环境与依赖

**日期**：2026-09-20
**产出**：`.venv/`、`requirements.txt`、`pip.ini`（用户级镜像源）

### 学到什么

- **venv 隔离的是「第三方包」，不是「标准库」**
  - 消失的：用户目录 site-packages、anaconda 自己的 site-packages
  - 留下的：anaconda 的 `Lib` / `DLLs` / `python313.zip` —— 那是**标准库**，venv **不复制**（几百 MB，复制纯属浪费）
  - 所以 venv 里 `import os` / `import json` 照样能用
- **两层搜索路径（本课核心）**

  | | 找什么 | 谁决定 | 何时变 |
  |---|---|---|---|
  | **`PATH`** | `python` 这个**命令**在哪 | 操作系统（激活脚本改它） | 激活 / 退出时 |
  | **`sys.path`** | `import xxx` 的**包**在哪 | 解释器（从 `sys.prefix` 算） | 选解释器时 |

- **激活 = 改 `PATH`**，把 `.venv\Scripts` 插到最前面。**没有魔法。**
  - 所以不激活也能用：直接写 `.\.venv\Scripts\python.exe`，效果一模一样
  - 推论：**脚本 / CI 里写全路径更可靠**（不依赖会话状态）—— Stage 8 部署会用到
- **`pyvenv.cfg` 是 venv 的全部秘密**（`.venv/pyvenv.cfg`，只有 5 行）：

  | 行 | 作用 |
  |---|---|
  | `home = C:\WorkAndStudy\anaconda` | **标准库**去这里找 → 所以解释器横幅仍写 "Anaconda"（二进制就是它，venv 不重新编译 Python） |
  | `include-system-site-packages = false` | **隔离开关** —— 不加载 base 的 site-packages |
  | `executable` / `version` / `command` | 创建时的记录 |

- **`sys.prefix` vs `sys.base_prefix` 的分工**：
  - `sys.prefix` = 「我现在是谁的环境」→ 决定**第三方包**去哪找
  - `sys.base_prefix` = 「我是从哪来的」→ 决定**标准库**去哪找
  - 实测：`sys.prefix` = `...\.venv`；`sys.base_prefix` = `C:\WorkAndStudy\anaconda`
- **`pyvenv.cfg` 里写死了绝对路径** → `.venv` **不能被复制到别的机器**，别人 clone 后必须自己 `python -m venv .venv` 重建
  - **这就是 `requirements.txt` 存在的意义**

### 踩过的坑

1. **PowerShell 执行策略**拦截 `Activate.ps1`
   → `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`
2. **pip 装不上包**，报 `from versions: none`
   - 根因：**pypi.org 响应 24 秒，pip 默认超时 15 秒** → 等不及 → 报"找不到"
   - **教训：报错信息说的是表象，不是根因。**
   - 解法：配国内镜像（用户级 `pip.ini`）—— 阿里云 1.9s / 清华 3.1s
   - 认知：这不是"中国特供"，企业内网配**私有 PyPI 源**是同一套机制
3. **`requirements.txt` 编码坏了**：PowerShell 5.1 的 `>` 默认输出 **UTF-16 LE**（36 字节装了 18 个字符）
   - 后果：git 当二进制、diff 看不了、合并会冲突
   - 解法：`python -m pip freeze | Set-Content -Encoding ascii requirements.txt`
   - 根因：PowerShell 的 `>` **不是字节流重定向**，是把**对象**转文本再写文件
4. `pip config set` 写入层级：`C:\Users\蒋进平\AppData\Roaming\pip\pip.ini`（**USER 层**）
   - 层次选对了：镜像源对所有项目都有用 → 用户级；依赖清单只对这个项目 → venv 级

### 待复习

- **venv 隔离的是第三方包，不是标准库**
- **`PATH`（命令在哪）vs `sys.path`（包在哪）—— 两层**
- **报错信息 ≠ 根因**（"找不到包"其实是"没等到"）

## 课程 0B-2 · 项目目录结构设计

**日期**：2026-09-21
**产出**：`paper_rag/` 骨架（`__init__.py` 内含分层说明）、`scripts/`、`data/raw/`、`data/processed/`、`tests/`

### 学到什么

**为什么不能照搬生产的 `agent-platform/` 结构**（用户从网上找来的）：

1. 它的边界是**部署边界，不是代码边界** —— `api/` 和 `langgraph_service/` 是**两个进程**，我们只有**一个**
2. 一半目录会是**空的** —— **空目录不是架构，是负债**
3. 它假设了 Stage 6~8 的技术 —— **过早抽象**

**三条判据**（本次核心，以后每次切目录都用）：

| 判据 | 问什么 |
|---|---|
| **一 · 变化的原因** | 同一个文件夹里的东西，是**因为同一个原因**才需要改吗？ |
| **二 · 依赖方向** | 结构能不能让依赖方向**看得见**？（`ingest → llm` ✅，`llm → ingest` ❌） |
| **三 · 部署边界** | 只有需要**独立部署/扩容**的东西才配占一个顶层目录（现阶段不适用） |

**四刀**：

| 刀 | 切在哪 | 理由 |
|---|---|---|
| 1 | `paper_rag/`（库）vs `scripts/`（入口） | **0A-4 的知识落地**：库文件不许有顶层副作用，只有入口才有 `if __name__ == "__main__"` |
| 2 | `config.py` 独立 | 变化原因 = **环境/参数变了**，与业务逻辑毫无关系 |
| 3 | `llm.py` 独立 | **它被所有人依赖，但它谁都不依赖** —— 这就是 `core/` 的雏形（判据二） |
| 4 | `ingest` / `index` / `generator` 三分 | 对应 RAG 三段流水线，三者的"变化原因"互不相干 |

**起步结构 = 终点结构的「压缩版」**：`config.py`→`core/config.py`、`ingest.py`→`ingest/parser.py+chunker.py`、`llm.py`→`core/llm.py`…… **边界是同一套，只是颗粒度不同。**

> **结构是长出来的，不是想出来的。**

**拆分信号（可判定的，不是"感觉复杂了"）**：

> 当 `index.py` 里**建索引**那段和**检索**那段，各自长到需要滚动屏幕才能看完一个 —— 那一刻就该拆。

1. **rerank 放哪 —— 答 `generator.py`** ❌
   - 根因：把 rerank 理解成「**对生成的回答重排序**」
   - **事实**：rerank 排的是**检索出来的那堆 chunk**，不是 answer。answer 是**一段**文字，一段东西没法"重排序"
   - 修正后答对：rerank 作用于 `index` 产出的 chunk 列表 → 先放 `index.py`
2. **把 `index.py` 当成「存参数的地方」** ❌
   - `index.py` 是**干活的模块**（`build()` 建索引、`search()` 检索）
   - 「存参数的地方」是 `config.py` —— 职责不同

- **判据一「变化的原因」怎么用**：拿**两个具体的东西**去比，分别列「什么情况下我会改它」，看是同一张清单还是两张
- **一段数据 vs 一堆数据** —— 凡是说"排序/筛选/取前 N"，先确认操作对象是**列表**

## 课程 0B-3 · 配置管理

**日期**：2026-09-21
**产出**：`paper_rag/config.py`、`scripts/_probe.py`；`check_env.py` 改为从 config 读

### 学到什么

**路径推导（用户自己推出来的）**：

```python
PROJECT_ROOT = Path(__file__).resolve().parent.parent
```

```
__file__     C:\...\Paper_RAG_Agent\paper_rag\config.py
  .parent    C:\...\Paper_RAG_Agent\paper_rag
  .parent    C:\...\Paper_RAG_Agent        ← 项目根
```

**`.resolve()` 不是可选的（实测证据）**：当 `sys.path.insert(0, '..')` 时，Python 记下的 `__file__` **带 `..`**，`.parent.parent` 不会消掉它：

| | 结果 |
|---|---|
| 从根目录跑 | `C:\...\Paper_RAG_Agent\data\raw` |
| 从 `lessons/` 跑 | `C:\...\Paper_RAG_Agent\lessons\..\data\raw` |
| 人眼说 | 是同一个地方 |
| **Python 说 `a == b`** | **`False`** ← 会静默失效 |
| 加 `.resolve()` 后 | `True` |

**后果**：比路径相等的地方会静默失效 —— 比如 Stage 2 判断"索引建过了吗"，明明建过它说没建，**白重建一遍**。

**docstring 必须是「第一条语句」**：

- 排在 `import` 之后 → 降级成**普通字符串表达式**，算出后立刻丢弃
- 证据：`config.__doc__` → `None`，**不报任何错**
- 同一条规则三处通用：模块 / 函数 / 类，都是"**第一条语句**"
- 为什么要有这条规则：孤立的字符串字面量**本来就是合法代码**，Python 只能靠**位置**区分它是不是文档

**配置的对错标准**（本课核心）：

> **不是「代码逻辑对不对」，是「跟现实对不对得上」。**

用户写了 `GEN_MODEL = "llama3"` / `EMB_MODEL = "nomic-embed-text"`（凭记忆写的经典入门组合），而机器上装的是 `qwen2:7b` / `quentinz/bge-large-zh-v1.5:latest`。

**代码写错，Python 会报错；配置写错，一个字都不报** —— 它会安安静静去找一个不存在的模型，然后在 Stage 2 某个想不到的地方炸。

**`sys.path[0]` = 脚本所在目录，不是 cwd** ← **本课最值钱的一条**

| 你在写什么 | 以什么为基准 | 可靠吗 |
|---|---|---|
| 相对路径 `"./data"` | **cwd**（你从哪启动） | ❌ 换个启动位置就变 |
| `import paper_rag` | **`sys.path[0]` = 脚本自己住的目录** | ✅ 稳的 |

**实测**：从 `lessons/` 运行项目根目录下的脚本，`sys.path[0]` 依然是项目根，`import paper_rag` 照样成功。

**所以 `check_env.py` 该不该 import config？—— 该。** 判据：**运行时项目代码是否已经就位**。0B-3 里它是就位的；且 `config.py` 只依赖标准库，所以「venv 之前也能跑」的定位**没被破坏**（实测：用 anaconda 的系统 python 跑，四项全过）。

**`scripts/` 里的脚本需要 3 行头**：

```python
sys.path.insert(0, str(Path(__file__).resolve().parent.parent))
```

- 这就是 `PROJECT_ROOT` 那个表达式，**全项目唯一必须重复它的地方**（否则死循环：得先能 import 才能拿到它）
- 必须写在 `from paper_rag...` **上面** —— import 是**执行到那一行才发生**的

**⚠️ 排除掉的陷阱**：PyCharm 的 "Mark Directory as Sources Root" —— 只在 IDE 里有效，一上命令行/服务器就崩。**「在我机器上能跑」的经典来源。**

### 踩过的坑

1. `GEN_MODEL` / `EMB_MODEL` 凭记忆写，本地根本没有
2. docstring 写在 `import` 之后 → **静默失效**（`__doc__ = None`，不报错）
3. 少了 `.resolve()` → 换 cwd 跑出来的路径带 `..`
4. `check_env.py` 的 docstring 写着「用法（在项目根目录）」—— 改完后**这句话变成错的**（过时的注释比没有注释更糟）

### 待复习

- **`sys.path[0]` = 脚本所在目录（不是 cwd）**
- **相对路径按 cwd / import 按脚本目录 —— 两套规则**
- **docstring 必须是第一条语句**
- **配置的值要「查出来」，不能「记得的」**

### 验收

- [x] 通过

## 课程 0B-4 · 日志

**日期**：2026-09-21
**产出**：`paper_rag/logger.py`、`scripts/_probe_log.py`；`config.py` 加 `LOG_LEVEL` / `LOG_FILE`

### 学到什么

**print vs logging 的分界线**：

| | 用途 | 归属 |
|---|---|---|
| `print` | 给人看的**输出** | 程序的**产品** |
| `logging` | 给开发者看的**记录** | 程序的**过程** |

→ 所以 `check_env.py` **继续用 print**（那份体检报告就是它的产品）。

**print 的四个死穴**：不能关（得删代码）、不能分级、不能存盘、**不知道是谁打的**。

**四个概念**：Logger（水龙头）/ Level（阀门）/ Handler（出水口）/ Formatter（出口上的标签）。

**`logging.getLogger(__name__)`** —— `__name__` 是**模块名**，所以日志自动带上"谁打的"，一个字都不用写。
（`__name__` 是 0A-4 那个「直接运行是 `__main__`，被 import 是模块名」的**同一个东西**。）

**「库 vs 入口」第三次出现**：
- `config.py` 的规矩是「只放值，不放逻辑」→ **配置 logging 是逻辑**，不能放那
- `logger.py` **只提供 `setup()`**，被 import 时**不产生副作用**
- **由入口脚本调用 `setup()`**

**`FileHandler` 本质上就是 `open()`** → 必须显式 `encoding="utf-8"`（坑 2 第三次复发，用户自己躲过了）

**报错信息 ≠ 根因（第二次）**：

```
FileNotFoundError: No such file or directory: '...data\logs\paper_rag.log'
```

报错说"**文件**不存在"，实际上缺的是 **`data/logs/` 这个目录**。
（`open()` 不负责创建中间目录。）第一次是 0A-7 的 pip「找不到包」其实是「没等到」。

**编码是两端的事** ← 本课最有价值的一条

日志文件生成后，`Get-Content` 显示乱码。**文件是好的，是读的工具读错了。** 证据（同一堆字节）：

| 解释方式 | 结果 |
|---|---|
| UTF-8 | `切分出 3000 个 chunk` ✅ |
| GBK（`Get-Content` 的默认） | `鍒囧垎鍑?3000 涓?chunk` ← 正是当时看到的样子 |

**根因**：PowerShell 5.1 的 `Get-Content` 默认用系统 ANSI 代码页（gbk）读文件 —— **跟 Python 之前犯的是同一个错，只是在读的那一端**。

**怎么判断「哪端坏了」**：**看字节。字节是事实，显示是解释。**

正确读法：`Get-Content -Encoding utf8 <file>`

## 课程 0B-5 · git 与 `.gitignore`

**日期**：2026-09-21
**产出**：`.gitignore`、`README.md`、`data/raw/.gitkeep`；仓库推到 GitHub（Private，19 个文件）

### 学到什么

**git 存的不是「文件」，是「快照」**：每次 commit = 给整个项目拍一张照片。所以能回到任何一张照片，也所以你敢随便改。

**四个地方**：工作区 →（`git add`）暂存区 →（`git commit`）本地仓库 →（`git push`）远程仓库。
暂存区存在的意义：**一次提交 = 一件事**（你调切分逻辑时顺手改的错别字，不该混进这次提交）。

**核心判据（本课主轴）**：

> **别人 clone 下来，能不能自己弄出这个文件？**
> 能 → 不进（写进 `.gitignore`），把"怎么弄出来"写进 README；不能 → 进

**用户自己列的清单里，错的三处**：

| 判断 | 错在哪 |
|---|---|
| `.venv/` 全进 ❌ | **最严重**。「环境要能搭起来」≠「把搭好的环境装进仓库」。`pyvenv.cfg` 写死了本机绝对路径，63.6 MB / 1008 个文件、含平台专属 `.pyd/.dll`。**`requirements.txt` 存在的意义就是它不能被复制** |
| `scripts/` 不进 ❌ | **把 `scripts/` 和 `tests/` 看成同一个东西**。`tests/` = 验证代码对不对（给开发者）；`scripts/` = **使用**代码（给用户）。判据一：前者随"行为变了"改，后者随"你想换用法"改 —— **两张清单** |
| `lessons/` `docs/` 不进 ⚠️ | **判据用错了轴**。「个人学习记录」=「不想给别人看」→ 那用**私有仓库**解决，不是 `.gitignore` |

**⚠️ 救命的一条**：

> **`.gitignore` 不是删除，也不是加密。** 文件还在磁盘上。
> 而且**它只对「还没被跟踪的文件」生效** —— 一个文件**一旦被 `git add` 过**，之后再加进 `.gitignore` 照样被继续跟踪。
>
> **推论（以后处理 API key 会用到）**：key **一旦提交过一次**，往 `.gitignore` 里加是**没用的** —— 历史里永远有。唯一正确的做法是**去把那个 key 作废，重发一个**。

**git 不跟踪目录，只跟踪文件** → 空目录进不了仓库 → 用 `.gitkeep`（空文件，社区惯例）占位。

**「输入目录」vs「产物目录」（由 `data/raw/` 和 `data/processed/` 的差异引出）**：

| | 里面放什么由谁决定 | 怎么保证目录存在 |
|---|---|---|
| `data/raw/`（**输入**） | **人**（你自己放论文） | `.gitkeep` —— 程序不会创建它 |
| `data/processed/`（**产物**） | **程序** | **程序自己 `mkdir(parents=True, exist_ok=True)`** |

> **输入靠人准备，产物靠程序保证。** 不能靠 `.gitkeep` —— 它只解决"git 跟踪空目录"，解决不了"目录被删了 / 用 zip 下载 / 部署到容器里"。

**`.gitignore` 的语法要点**：

- `__pycache__/` —— 尾斜杠 = **只匹配目录**
- `*.py[cod]` —— 字符集 = `*.pyc` / `*.pyo` / `*.pyd` 三个一起
- `!data/raw/sample-*.pdf` —— 感叹号 = **取消**上面的忽略，**必须写在忽略规则之后**（git 从上往下读，后面的覆盖前面的）
- 我用 `sample-` 命名约定：**凡是能靠规则挡住的，就别靠自觉**

## Day 3 · Stage 1 文档接入（2026-09-23）

**目标**：PDF → `list[Chunk]` → `data/processed/chunks.json`

**语料**：RAG 原论文 `arXiv:2005.11401v4`，19 页，单栏（选它就是因为单栏 —— 双栏只记录问题，不解决）

---

### 学到什么

#### 1. PDF 是页面描述语言，不是文本

读 txt 是**解码**（字节 → 字符，一一对应）；读 PDF 是**重建**（把一堆绘图指令反推成"人类会怎么读"）。

所以 `get_text()` 的每一个结果都是**它的猜测**，不是事实。这就是为什么后面所有判断都得拿真数据验证。

#### 2. `get_text("dict")` 的三层结构

```
page
 └─ blocks[]        块 —— 视觉独立的一块：一个段落 / 一个标题 / 一张图
     └─ lines[]     行 —— 块内的每一行
         └─ spans[] 段 —— 行内「样式完全相同」的一段连续文字
```

**样式（size / font / flags）挂在 span 上，不在 block 上。**

原因：PDF 里样式是"画每个字时"的属性，不是"这块属于什么"的属性。一个块里完全可以混排（比如正文句尾挂一个 7pt 的脚注上标）。**要拿样式，必须下到第三层。**

#### 3. `span["text"]` 里没有换行符

**换行是结构信息（`lines` 是个列表），不是字符。**

这一条直接导致了 `clean_text` 的两条规则**静默失效**（见"踩过的坑 · 4"）。

修复：`block_text()` 里外层必须 `"
".join`。

#### 4. 阈值必须从**全量数据**算，不能看一页拍脑袋

| 阈值 | 错的值 | 怎么来的 | 对的値 | 怎么定的 |
|---|---|---|---|---|
| `PAGE_MARGIN_X` | ~~108~~ | 看第 1 页正文 x0=108.0 | **60** | 全文正文 x0 ∈ [106.7, 108.0]，水印 x0=10.9 |
| `HEADING_SIZE_GAP` | — | — | **1.0** | 正文 10.1 ↔ 标题 12.0，中间是空的 |
| `MIN_CHUNK_CHARS` | — | — | **40** | **没有缝**，见下 |

**`PAGE_MARGIN_X = 108` 的代价**：误杀 **88 个正文块**（本该只丢 19 个）。修好后是 保留 387 / 丢弃 19 —— 丢弃清单精确等于 1 个水印 + 18 个页码。

#### 5. 阈值要取两类数据的**缝的中点**

```
水印 x0 = 10.9  ←──── 96 点的空档 ────→  正文 x0 ≥ 106.7     取 60
正文 10.1pt     ←──── 1.9pt 的空档 ───→  标题 12.0pt          取 11.0（→ GAP=1.0）
```

贴边取（比如 105 或 10.5）也能跑，但**没有余量**。取中点，两边各留一半。

#### 6. **但有些阈值根本没有缝 —— 这时改用「代价权衡」**

`chunk` 长度分布是 **0 → 1606 连续平滑**，找不到任何断点：

```
   0-2    31
   3-5    16
  6-10     9
 11-20    29
 21-40    25
 41-80    18
81-200   123
  201+    96
```

没有缝的时候别再盯着数据找。**改问「错了会怎样」**：

- 丢掉一个真段落 → 少一条知识，**不可恢复**
- 留下一个垃圾 chunk → 检索多一条噪音，**有 ranking 兜底**

`MIN_CHUNK_CHARS = 40` 是**权衡的产物，不是数据的产物**，所以写进 config 方便以后调。

#### 7. 一级标题看字号，二级标题得看**字重**

排版区分层级用**两个维度**：字号 × 字重。

```
4 Results                        12.0pt + 粗体   ← 字号信号抓得到
3.3 Jeopardy Question Generation 10.0pt + 粗体   ← 字号跟正文一样！只能靠粗体
```

**只看字号，二级标题全漏。**

`flags` 是个**位域**：

```
flags = 20 = 0b10100
                └ bit4 (16) = 粗体
```

判据 = 两个信号 **OR**：`size >= body + GAP` 或 `|size - body| <= JITTER 且 flags & 16`。

结果：40 个标题 / 347 个正文，假阳性 3 个（首页作者名，也是粗体 —— 无害，紧接着被 `Abstract` 覆盖），**零正文误判**。

#### 8. 累加器：`current_section` 定义在哪一层

**变量的作用域 = 它必须活多久。**

```
p 1(1-based)  2 Methods         ← 标题
p 2(1-based)  2.1 Models        ← 二级标题，中间隔了一次页循环
```

`current_section` 要跨页，所以必须在**页循环之外**。放进页循环 → 每页清零 → 第 2 页的正文全挂错 section。

**验证方法**：找一个 section 跨页的 chunk，看它的标签对不对。

#### 9. 过滤器的**顺序**和**作用域**

长度过滤（`< 40 丢弃`）是**针对正文块**的规则。标题天然很短（`Abstract` 8 字、`4 Results` 9 字），**不属于这条规则的管辖范围**。

所以顺序必须是：**先判标题 → 再过滤长度**。

放反了会怎样？代码不报错，输出"看起来也对"（237 个 chunk、页码连续），**只有 `section` 种类数从 33 掉到 2 露了马脚**。

**教训：改完过滤逻辑，要看统计，不能只看前几行输出。**

### 踩过的坑

#### 1. 🔴 `PAGE_MARGIN_X = 108` —— 灾难性误删

见上面"学到什么 · 4"。**88 个正文块被误杀**。

根因：拿**第 1 页**的正文 x0（108.0）当阈值，但全量正文 x0 最小值是 **106.7** —— 有 1.3 点的块落在阈值左边。

#### 2. `models.py` 里用类变量自增 `chunk_id`

```python
class Chunk:
    _chunk_id = 0            # 类变量
    def __init__(self, ...):
        Chunk._chunk_id += 1 # ← 灾难
        self.paper_id = Chunk._chunk_id
```

**后果**：一篇论文变成一百篇（每个 chunk 拿到不同的 `paper_id`）。而且传进来的 `chunk_id` / `paper_id` 参数被**静默丢弃**。

修：删掉类变量，`chunk_id` 由**调用方**传入（谁有上下文，谁负责生成）。

#### 3. `Path = Path(__file__).resolve().parent.parent` —— 名字覆盖

`Path` 从 `pathlib.Path` **类**变成一个项目根**实例**。之后 `Path / "x"` 恰好还能工作，**所以不报错**。

修：删掉这行，相对路径就写相对路径。

#### 4. 🔴 `get_text("dict")` 的 span 不带换行 → `clean_text` 两条规则变死代码

`clean_text` 的契约是「传入末尾带 `

**两边都不报错，静默失效。** 症状：

| 现象 | 根因 |
|---|---|

| `down-stream`（断词没接上） | 规则 2 在等一个不存在的 `
` |
| `The DivineComedy` | 同上 |
| `section = "1Introduction"` | 同上 |

修：`block_text()` 外层 `"
".join`。**一行修了四个症状。**

**为什么之前没发现**：`probe_ingest.py` 用手写字符串测 `clean_text` ——

```python
print(clean_text("down-
stream
"))   # ✅ 通过
```

**手写样本里有 `

#### 5. `-

```
down-
stream          → downstream         （断词，该接上）
knowledge-
intensive  → knowledgeintensive （真连字符，该保留）
```

**两者在纯文本里长得一模一样**，都是 `字母 + - + 换行 + 字母`。区分它们需要的信息**不在文本里**。

## Day 3 · 补记 · 日志接入（同日晚）

0B-4 学的日志模块，今天才第一次真的被用上 —— 在这之前 `build_index.py` 全程 `print`，
`data/logs/paper_rag.log` 里只有 0B-4 手敲的那几条测试。

### 学到什么

**1. `setup()` 必须死在最前面 —— `basicConfig` 只生效一次**

`logging.basicConfig()` 的内部逻辑是：**根 logger 已经有 handler 了，就什么都不做。**

所以顺序反了（先发一条日志，再 `setup()`）**不会有任何报错**，只是你的 handler 一个都装不上。又是「静默失效」，跟 `clean_text` 那次同一类。

**2. 脚本里不要写 `getLogger(__name__)`**

`__name__` 的值取决于**模块是怎么被加载的**，不是文件名：

| 加载方式 | `__name__` |
|---|---|
| `import paper_rag.ingest` | `"paper_rag.ingest"` ✅ |
| `python scripts/build_index.py` | `"__main__"` ❌ |

脚本永远是第二种。所以入口里写死一个名字：

```python
logger = logging.getLogger("paper_rag.build_index")
```

库文件里反而**应该**用 `__name__` —— 那时它等于模块路径，正好合适。

**3. `logger.info("x %s", y)` 不是 `logger.info(f"x {y}")`**

两者输出一样，**成本不一样**。f-string 是「先拼字符串，再交给 logger」；`%s` 是**惰性**的，级别过了才拼。级别调到 WARNING 之后，那些 INFO 行该被丢弃，但 f-string 的拼接已经白做了。日志写得多了，这个差别是真的。

**4. 日志级别取代了 emoji**

`print("⚠️ 找不到")` → `logger.warning("找不到 %s")`。

级别本身就是「有多严重」的表达，而且**能被过滤、能被检索** —— emoji 不能。

**5. 控制台的编码不是 Python 定的，是运行环境定的**

同一条命令，两个 shell：

| 环境 | `sys.stdout.encoding` | 中文 |
|---|---|---|
| Git Bash | **gbk** | 乱码 `��־�ļ�` |
| PowerShell / PyCharm | **utf-8** | 正常 |

**代码一个字没改，换个 shell 就换一套编码。**

这正是 `FileHandler(LOG_FILE, ..., encoding="utf-8")` 里那个参数的意义 —— 文件流**显式**指定了编码，所以 `paper_rag.log` 在任何 shell 下跑都不乱码。

> 控制台是给人当场看的，编码随环境变；
> 文件是留档的，编码你说了算。

同理，`open()` 一定要写 `encoding=`：不写就用系统默认（这里就是 gbk），存下去的中文换台机器打开就是乱码。

### 踩过的坑

**`logger.py` 第 24 行自己遮住了自己的 import**

```python
from paper_rag.config import DATA_DIR, LOG_LEVEL, LOG_FILE   # 第 11 行
...
LOG_FILE: Path = DATA_DIR / "logs" / "paper_rag.log"          # 第 24 行，遮蔽！
```

函数体里重新赋值，把 import 进来的那个名字盖住了。**值恰好一样**，所以行为没变、也不报错 —— 但这是 0B 里 `Path = Path(__file__)...` 那个坑的同一副面孔：**同一套命名空间里，后写的盖先写的。**

顺带一处：第 3 行 docstring 说「被 import 时不产生任何副作用」，这是**对的**；但第 25 行注释写「← 模块层直接执行」，那是上一版 `mkdir` 还在函数外时留下的 —— **`mkdir` 早就挪进函数了，注释没跟着走。**

> 注释也会过期。改代码时顺手看一眼旁边那行注释，不然它就从「帮助」变成「误导」。

## Day 4 · Stage 2 向量化与检索（2026-09-24）

**目标**：`chunks.json` → 向量 → 检索，**六个函数全部手写**

**产出**：`vectors.npy` + `ids.json`（237 × 1024 float32，0.93 MB）

---

### 学到什么

#### 1. 模型选型：MTEB 排行榜回答不了我们的问题

排行榜量的是**别人的语料、别人的任务**。我们真正要回答的是：

> 哪个模型最能把**中文问题**对应的**英文段落**排上来？

这个问题只能在 `data/eval/queries.json` 那 10 道题上量。指标：Top-1 / MRR / 平均排名 / 对比度（正确段落平均分 − 全体中位分）。

| 模型 | Top-1 | MRR | 平均排名 | 显存 | ctx |
|---|---|---|---|---|---|
| **bge-m3** ✅ | **70%** | **0.766** | 4.0 | 664 MB | 4096 |
| qwen3-embedding:0.6b | 40% | 0.556 | 3.5 | 2.4 GB | 4096 |
| bge-large-zh-v1.5 | 30% | 0.496 | 4.5 | 618 MB | 512 |

**关键的三个反直觉点**：

1. **MRR 第一 ≠ 平均排名第一。** qwen3 平均排名 3.5 比 bge-m3 的 4.0 **更好**，但 MRR 只有 0.556。
   原因：**平均排名是线性的**（第 22 名付 22 倍代价），**MRR 是倒数的**（第 22 名 `1/22=0.045`，几乎免费；第 1 名付 1.0）。
   bge-m3 有 7 题第 1、1 题第 22；qwen3 有 4 题第 1、最好的一题第 3。
   **在 `TOP_K=5` 下，第 22 名和第 8 名都是"没找到"** —— 所以该看 Top-1/MRR，不是平均排名。

2. **"更长上下文"没换来更好的检索。** bge-m3 的 ctx 是 4096，bge-large-zh 只有 512，但**没有任何一个 chunk 被截断**（237 条全部成功）—— 论文切出来的段落本来就短。**买了一个用不上的能力。**

3. **官方指令前缀会帮倒忙。** bge-large-zh 的官方中文指令加上后：40% → **30%**，MRR 0.568 → **0.496**。
   猜想：那句"为这个句子生成表示以用于检索相关文章"把 query 往**中文文档空间**推，而我们的语料是**英文**。
   → **"官方推荐"是在官方数据上测出来的，换个语料就得自己重量。**

#### 2. 前缀匹配的坑：`startswith` 会静默漏掉（第 6 个静默失效）

模型名是 `quentinz/bge-large-zh-v1.5:latest`（带命名空间）。

```python
"quentinz/bge-large-zh-v1.5:latest".startswith("bge-large-zh")   # False
"bge-large-zh" in "quentinz/bge-large-zh-v1.5:latest"            # True
```

用 `startswith` → 那个模型**一个前缀都没加上**，不报错，只是分数偏低。
**实际后果**：第一轮评测里 bge-large-zh 的分数是"没加前缀"的分数 —— 评测本身是错的。

#### 3. 两层索引，两个失效条件

```
PDF ──build_index.py──▶ chunks.json ──build_vectors.py──▶ vectors.npy
      换 PDF / 改切分才重跑          换嵌入模型才重跑
```

**合成一个脚本的话，换个嵌入模型也得把 PDF 重新解析一遍 —— 白等。**

#### 4. 索引必须记住"是哪个模型生成的"

`index.load(model=...)` 不匹配就抛 `RuntimeError`。

**不这么做的后果**：拿 bge-m3 的 query 去比 bge-large-zh 的语料向量 —— 维度都是 1024，**算得出分数，而且看起来很正常**，但两个空间的坐标毫无关系。**没有任何报错。** 这是本类问题的典型形态：**两个文件各自都合法，配在一起才是错的。**

#### 5. 归一化 → 余弦退化成点积

bge 系列输出的向量模长**恒等于 1**（实测 0.999999 ~ 1.000001）。所以：

```
cos(a,b) = (a·b) / (|a|·|b|)  →  分母 = 1  →  cos(a,b) = a·b
```

**分母整项消失**，`top_k_np` 里那两步（`np.linalg.norm(..., axis=1)` 和除法）**根本不需要写**。
这正是 FAISS 里 `IndexFlatIP` 的 **IP = Inner Product**。

> 注意：这是**用一条前提换来的速度**。前提必须写下来、验证过、并且被保证。
> 哪天真换了个不归一化的模型，这个优化就静默失效。

#### 6. 三种实现，一个契约

```
top_k       纯 Python   O(N) 循环 + cosine        22.4 ms
top_k_np    numpy       V @ q + argpartition       0.061 ms   ← 365×
top_k_faiss FAISS       index.search()             0.041 ms
```

**对拍结果**：10 题 × top-20，顺序完全一致，分数最大差 `6.85e-07` / `1.19e-07`。

`IndexFlatIP` 的 recall 恒等于 **1.000** —— 因为**它算的就是同一行矩阵乘法**，只是换 C++ 写。
**FAISS 的 Flat 索引没有任何算法上的魔法。**

#### 7. `argpartition` 的语义

- `k` 是**下标**（0..N-1），不是"取几个"。`np.argpartition(-s, k)[:k]` 和 `np.argpartition(s, -k)[-k:]` 都对
- **它返回的前 k 个是【无序的】** → 必须对这 k 个再排一次。这一步最容易漏
- `k > N` → `ValueError: kth out of bounds`；`k == N` **是合法的**
- `np.argsort` 默认是 **quicksort（不稳定）**，和 Python 的 `sorted`（稳定）不一样

#### 8. 🔴 dtype 静默提升 —— 本项目第一个**性能**静默失效

```python
q = np.asarray(query_vec)                    # 默认 float64！
scores = vectors_f32 @ q                     # 整个矩阵被提升成 float64
```

- **不报错、不警告、结果完全正确**
- 每次查询多一次 **1896 KB** 的临时分配
- 实测：`V @ a64` = 346.1 µs，`V @ a32` = 8.8 µs → **39.4×**

修完：0.420 ms → **0.048 ms（465×）**。

> **规则：矩阵是 float32 的时候，向量也必须显式 float32。**
> numpy 的自动类型提升是"正确"的，但正确得**很贵**。

#### 9. 成本 = 常数项 + 线性项 —— 外推为什么骗人

```
       N        实测      从 237 外推      高估
     237    0.039 ms      0.039 ms      1.0×
   1,000    0.117 ms      0.163 ms      1.4×
  10,000    0.403 ms      1.626 ms      4.0×
 100,000    4.996 ms     16.256 ms      3.3×
```

**237 条时，81% 的成本是常数开销**（函数调用、numpy 调度）。拿这个数去乘 422，等于**把常数项也放大了 422 倍**。

> 外推只在**线性项已经主导**的区间才成立。

#### 10. FAISS：精确索引 vs 近似索引

| | 加速（100k） | recall |
|---|---|---|
| `IndexFlatIP` | 1~3× | **1.000**（精确） |
| `IVF nprobe=1` | 150~240× | 0.95~0.99 |
| `IVF nprobe=4` | 100~150× | 1.000 |
| `IVF nprobe=nlist`（全扫） | **0.7×（比暴力还慢）** | 1.000 |

- **IVF 的加速是【拿召回换的】**。`nprobe` 调小 = 只搜几个簇 = 快，但答案可能不在那几个簇里
- **全扫时 IVF 反而比 numpy 慢**：IVF 是一个簇一个簇地跳指针、捞向量、分别算距离；numpy 是对一整块连续内存做 SIMD 化的 GEMM。**算的是同一件事，内存访问模式完全不是一回事**

#### 11. 🔴 基准的口径必须和生产一致

我先后跑出过两个相反的结论，**同一台机器、同一个库**：

| 一次查几条 | numpy | FAISS |
|---|---|---|
| **1 条**（GEMV，线上 RAG） | 5.304 ms | 4.048 ms → **FAISS 1.3×** |
| **20 条**（GEMM，离线批量评测） | 1.888 ms | 4.048 ms → **numpy 2.1×** |

差别在**语料被读几遍**：GEMV 每条 query 都要扫完整个 391 MB；GEMM 20 条共用一次读取。

> **比数字更重要的是口径。** 用户问一句答一句 → 看单条那一行。

#### 12. 合成数据必须有**真实的簇结构**

1024 维里均匀随机的向量近似两两正交，"最近的邻居"和瞎猜没区别。

而且扰动的模长**必须按 `sqrt(D)` 缩放**：

```
randn(D) 的模长 ≈ sqrt(D) ≈ 32
直接乘 spread=0.15 → 实际扰动 4.8，比簇心之间的距离还大 —— 簇没了
```

我第一次就是这么写的，量出 **IVF recall ≈ 0.01**，差点得出"IVF 在这个项目里没用"的结论。**那是我数据的问题，不是 FAISS 的问题。**

#### 13. Amdahl：2.5 的真正结论

```
embed_one (query 侧)        38.1 ms    ← 光是把问题变成向量

  numpy @237         0.091 ms   →  占这 38.1 ms 的  0.24%
  FAISS @237         0.036 ms   →  占这 38.1 ms 的  0.09%
```

**后面还有 qwen2:7b 生成答案那一步，是秒级的。**

> 在 237 条上，FAISS 把一次问答的耗时从 **100%** 优化到了 **99.86%**。

**决定要不要上向量库的不是 FAISS 有多快，是 N 有多大。** 按 GEMV 的 53 ns/chunk 算，检索要长到能看见（约 50 ms），需要 **≈ 90 万 chunk ≈ 4000 篇论文**。

#### 2. `assert` 会被 `python -O` 整个删掉

最初的守卫写成 `assert len(ids) == len(vectors)`。

- `python -O` 运行时 **assert 全部消失**

修：改成 `raise ValueError`（和 `dot()` 里一致）。**契约检查不是调试工具，是接口的一部分。**

#### 3. 零向量守卫破坏了契约

在 `top_k_np` 里加 `if norm_query == 0: return []`：

| 实现 | N=237 条、query 是零向量时返回 |
|---|---|
| `top_k` | **3 条**（分数 0.0） |
| `top_k_np` | **0 条** |

两个实现给出不同的长度 —— **改一个实现的时候，忘了看另一个的契约**。已删。

（`cosine()` 里的零向量处理是另一回事：那是数学定义要求的兜底，且**三个实现都走同一个 `cosine`**。）

#### 4. 探针第 1 关报 FAIL —— 但错的是契约，不是排序

第一版 `top_k` 返回 `(分数, id)`，而 docstring 写的是 `(chunk_id, 分数)`。

**内部表示泄漏到了公开接口上。** 探针是**消费者**，它读 docstring 然后按契约用 —— 所以它一用就炸。**这正是 Stage 3 会做的事。**

用户自己改成了 `(ids[i], score)` + `key=lambda x: x[1]` —— 比提示里给的写法更好（契约对齐 + 打平时稳定可复现）。

#### 5. 🔴 我自己的基准错了两次

| 第一次 | 我把 FAISS 的 `omp_set_num_threads` 设成 1 —— **把它的主力武器关了** |
|---|---|
| 第二次 | 我的"聚类"数据**根本不是聚类**（扰动没按 `sqrt(D)` 缩放），IVF recall 量出来 0.01 |

**结论从"IVF 快 100 倍"翻成"IVF 没用"再翻回来，全程一行代码没改。**

> **基准测试最容易骗人的地方不是代码，是数据。**

#### 6. 🔴 「线性外推」给过一个错数字 —— 165 ms

拿 237 条的成本（0.39 ms）直接乘 422，得到 100k 上要 165 ms。**实测 5.5 ms，错了 30 倍。**

后来改成"实测 vs 外推"并排打印（见学到什么 · 9），把教训焊进代码里。

**第一次修还修错了**：只测了 `W @ q` 那一行（它**确实是线性的**），所以外推看起来没问题。改成测**整个函数**才暴露出来。

#### 7. 我错的还有：`.T` 的担忧

以为 C-contiguous 的二维数组 `.T` 之后变非连续会拖慢 matmul。**实测 1.03×，我的担心不成立。** 已当场承认。

#### 8. 探针 4b 一开始只比了 chunk_id，没比分数

自己发现并补上（`TOL=1e-5`）。

**但补完仍抓不到"少了 `|q|`"这类错误** —— 因为那个误差只有 2.4e-7，小于容差。

> **探针不是万能的。有些错误只能靠读代码和推理发现。**

#### 9. `top_k_faiss` 里 `import faiss` 是死代码

`index` 是外面传进来的，能传进来就说明 faiss 一定装好了。这行 import **保证不了任何事**，只是噪声。

#### 10. `-1` 填充的陷阱（已正确处理）

`k > N` 时 FAISS 用 `-1` 把结果数组撑满。直接 `ids[int(idx)]` 会拿到 **`ids[-1]`，也就是最后一条** —— **不报错，结果是错的**。

已过滤，且第 5 关专门验了：`k=242 > N=237` → 返回 237 条、去重后 237 条。

## Day 5 · Stage 3 朴素 RAG（2026-09-25）

### 学到什么

#### 1 · 流水线：三件事，三个函数

```
question ──┐
           ├─▶ build_prompt ──▶ llm.generate ──▶ parse_response ──▶ 结果
chunks ────┘
```

| 函数 | 方向 | 性质 |
|---|---|---|
| `build_prompt` | 你 → 模型 | **整个 Stage 3 的核心**。所有约束都写在这里 |
| `parse_response` | 模型 → 你 | 把文本变回程序能用的东西 |
| `answer` | 编排 | 胶水，不含逻辑 |

`llm.py` 单独拆出来的理由（0B-2 判据二）：**它被所有人依赖，但它谁都不依赖。**
业务知识一旦长进这一层，Stage 6 的 Agent 就没法复用它了。

#### 2 · 先写一个"故意写笨的 v0"，看它怎么坏

**这是这一课最值钱的方法。** 一上来就写"正确"的 prompt，你只会得到一个能跑的东西，
**永远不知道每条约束在防什么**。先跑 v0，让错误**打在脸上**，再逐条修 —— 修的时候你知道自己在修什么。

v0 的四枪（`build_prompt` 只有"请根据以下材料回答问题" + 编号 + 问题）：

| 枪 | 问题 | v0 的结果 |
|---|---|---|
| 1 | RAG 怎么把文档融进生成？ | 内容全对，但输出是**一段散文**，`used=[]` |
| 2 | 论文作者中午吃了什么？ | **拒答了** ✓（但是**碰巧** —— 问题太荒谬，它自己觉得离谱） |
| 3 | BERT 有多少层？ | 「提供的信息中**并未直接提及**。……BERT Base 包含 **12 层**」 |
| 4 | BERT 的预训练任务是什么？ | 把 **RAG 论文的训练目标**（含公式）说成"BERT 的预训练任务" |

> **第 3 枪是这一课的分水岭**：模型把「拒答」理解成了一种**语气**，不是一个**行为**。
> 它学会的是"说一句『材料未提及』听起来很严谨"，**不是**"材料里没有就闭嘴"。

#### 3 · v1 的五条约束（每条对应一枪）

| # | 约束 | 防的是 |
|---|---|---|
| 1 | **角色 + 禁令放最前面** | 模型对开头/结尾注意力最重，禁令放中间会被淹 |
| 2 | **材料编号用 `[1]`，不用 `chunk_id`** | 让模型抄 18 个字符的 id，抄错一个**不会报错**；抄一个 1~5 的数字错不了 |
| 3 | **带上 `section` / 页码** | Stage 4「引用点回原文」的唯一依据。**现在不放，Stage 4 就得重写 prompt，之前所有实验结论作废** |
| 4 | **空行分隔材料** | 两段材料首尾相接，模型会读成**一段连续的话**（Stage 1 辛苦切开的边界白送了） |
| 5 | **约束必须是可执行的动作** | 见下 |

**第 5 条是核心。** 对比：

```python
# ❌ 愿望 —— 模型会点头，然后照编
"请不要编造不存在的内容。"

# ✅ 动作 —— 明确的条件 + 明确的输出 + 明确的字段
"材料里找不到答案时：answer 必须【原样】写成「资料未提及」，且 used 必须是 []"
```

愿望没有**判定条件**（什么叫"不存在"？谁判？），也没有**落地位置**（改成什么？放哪？）。
模型只能自己发挥 —— 而它发挥出来的就是第 3 枪那个样子。
动作有**两个可被检查的状态**，而且**互相制约**：它嘴上说没用材料，`used` 就得是空的。
**一边说"未提及"一边给出 `used=[1,3]` → 代码当场发现自相矛盾。**

v1 的战绩：第 1 枪干净 JSON ✅ / 第 2 枪按规矩拒答 ✅ / 第 3 枪**拦住了** ✅ / 第 4 枪 🔴

#### 4 · ★★ 第 4 枪：格式约束不会消灭错误，只会让它**学会穿制服**

v1 第 4 枪的输出：

```json
{"answer": "BERT的预训练任务是使用随机梯度下降和Adam优化器最小化-log p(yj|xj)。", "used": [2]}
```

拆开验，**每个零件都是真的**。chunk `rag-2005.11401#23`（`2.4 Training`）原文：

```

Updating the document encoder BERTd during training is costly ...
only fine-tuning the query encoder BERTq and the BART generator.
```

| 它的说法 | 原文里 | 在？ |
|---|---|---|
| `-log p(yj|xj)` | `j −log p(yj|xj)` | ✓ |
| 随机梯度下降 + Adam | `stochastic gradient descent with Adam [28]` | ✓ |
| BERT | `BERTd` / `BERTq` | ✓ ×2 |

**它一个字都没编。`used: [2]` 甚至可以说是诚实的。**

它做的事：材料里有一个**训练目标**，问题问的是**一个训练目标** → 接上。
材料里有 `BERT` 这个词，问题里有 `BERT` → 接上。
**这是字符串巧合，不是推理。**

> ## 加了格式约束之后，错误不会消失 —— 它会学会穿制服。

并排放 v1 的第 1 枪和第 4 枪：

```
{"answer": "RAG 模型通过联合参数化记忆...",       "used": [1]}   ← 对
{"answer": "BERT的预训练任务是使用随机梯度下降...", "used": [2]}   ← 错
```

**格式一样、语气一样、都带引用。只有懂 BERT 的人能分辨。**
v0 的错误是大喊大叫的（一段跑偏的散文）；v1 的错误是**格式完美、引用齐备、看起来最可信的那个**。

而且 **Stage 4 的字符串校验救不了它**：若它在 `quotes` 里交出 `"2": "-log p(yj|xj)"`，
代码做 `in` 判断 → `True` → **校验通过**。**引用是真的，结论是错的。**

**这一枪 `temperature=0` 下每次原样复现** —— 是系统性错误，不是随机噪声。有确定的靶子。

#### 6 · ★ 禁令反噬：约束在防一枪的同时，打开了另一枪

**证据**：v0 的第 3 枪里，模型答出了 **12 层 / 24 层** —— 说明**它知道 BERT 是什么**。
它知道 BERT 的预训练任务是 MLM，不是"最小化 `-log p(yj|xj)`"。**它本来有能力发现这个错。**

但 v1 那条禁令按住了它：

于是它**不能**想："等一下，BERT 的预训练任务是 MLM，这段讲的是 RAG 的训练，对不上。"

**你让它只看材料，它就退化成了一个字面匹配器。**

> **每一条约束都有它治不了的病。没有一条约束是"越严越好"。**

#### 7 · `parse_response`：剥包装可以，补内容不行

**第 1 步 —— 一个动作解决两种情况：**

```python
i, j = text.find("{"), text.rfind("}")
payload = text[i : j + 1]
```

从**第一个 `{`** 砍到**最后一个 `}`**。围栏和寒暄**是同一类东西** —— "JSON 之外的多余字符"。
docstring 里列了 4 种失败，代码里只有 2 个分支 —— **不是漏了，是合并了**。

> 别按"有几种失败情况"写代码，要按**"这些情况的共同点是什么"**写代码。

**第 2 步 —— 分界线是「你有没有丢东西」：**

| 情况 | 处理 | 为什么 |
|---|---|---|
| 围栏 / 寒暄 | **剥掉，继续** | 内容是**包装**，剥掉一字未动，没有东西需要你**编** |
| 缺字段 / 不是 JSON | **抛异常** | 你只有**空缺**。想返回 dict 就必须自己**补**一个值 —— 而那是你造的 |

**兜底为什么最危险 —— 撞衫论证：**

```
{"answer": "",             "used": []}   ← 解析失败的兜底
{"answer": "资料未提及",     "used": []}   ← 真·拒答
```

**形状一模一样，语义天差地别。** 调用方（Stage 4）拿到第一个，会以为"模型说资料里没有，跳过引用校验"。
实际上模型说了别的，**是代码替它编了那句拒答** —— 一次解析失败，**伪装成了一次正常的拒答**，全程无人报错。

> **凡是需要你「补」一个值的，就是在编。**
> 报错很吵，但它诚实；兜底很安静，但它在撒谎。

这和「模型只提供依据，结论由代码下」是同一件事的反面：**代码也不能替模型下结论。**

**边界：这个函数校验【形状】，不校验【语义】。**

它管 `answer` 是不是非空字符串、`used` 是不是整数数组；
它**不管** `used` 里的 `[99]` 是不是真的存在 —— 那需要 `chunks`，而它签名里没有。
越界去查，就得把 `chunks` 传进来，然后**这个函数再也不能被"只想解析一段文本"的地方复用**了。

> 语义词法校验，要划在**能拿到那份资料**的那一层。

#### 8 · 已知漏洞：`find("{")` 的隐含假设（决定：只记录，不修）

```python
'答案里有 {1,2}，JSON 是：{"answer": "A", "used": [1]}'
              ↑ 从这里切 → json.loads 炸
```

`find("{")` 长得像"找 JSON 的开头"，其实只是"**找第一个左花括号**"。
**"第一个 `{` 就是 JSON 的开头"是个隐含假设 —— 代码依赖它，但从没验过它。**

更坏的是**报错信息指向了错误的地方**：它说"不是合法 JSON"，怪的是**模型**；
而模型输出的后半段完全合法，**是代码切错了位置**。这种比不报错更难查。

**为什么不修**：① 从没观察到 ② 炸得很响（`ValueError` 带原文）③ 为没观察到的失败模式加循环 = **替想象写代码**
**怎么修**：逐个试每个 `{`，用 `json.JSONDecoder().raw_decode(text, idx)`
**★ 恢复条件**：探针里连续两次看到这个报错 → 立刻修。

## Day 6 · Stage 4 引用溯源（2026-09-29）

七天冲刺的**最后一个阶段**。目标：模型说的每一句，代码去原文里核。

### 今天的产物

| 文件 | 性质 | 作用 |
|---|---|---|
| `paper_rag/cite.py` | **产品** | `verify` —— **Stage 4 的核心，你手写的** |
| `scripts/probe_cite.py` | 脚手架 | 8 条离线关卡 + 2 个实验 |

`cite.py` 里唯一不是你写的是 `_norm()`（归一化辅助函数）—— 它是**机制**不是判断，
判断（用不用它、松到什么程度）是你做的，见下面「容错线」。

### 学到什么

**1. ★ 「引用真不真」和「答案对不对」是两条独立的判断**

`verify` 只能做第一条。今天两个实验，把这条缝量出来了：

| | 引用 | 答案 | `parse_response` | `verify` |
|---|---|---|---|---|
| **实验 A** 诱导 | **假**（编的） | 错 | ✅ 通过 | ✅ **报出 1 条 —— 抓住了** |
| **实验 B** 第 4 枪 | **真**（逐字） | **错** | ✅ 通过 | ⚠️ **`[]` 全部放行** |

**两个答案都是错的。`verify` 抓住了 A，放行了 B。**
唯一的差别是引用的真伪，不是答案的对错。

一句话：**这一层查得出「无中生有」，查不出「有中生错」。**

**2. ★ 怎么诱导模型编引用（实验 A 的手法）**

不硬掰，**改条件**：把 `build_prompt` 的拒答规则拿掉，换成

> `used` 和 `quotes` 都【不允许为空】—— 如果写不出引用，说明你答得不够具体，请重新组织答案。

材料里**没有**答案（库里没 BERT 论文）+ **不许**说没有 = **它只能编**。

它编出来的东西：

```
quotes: {"2": "BERT: Pre-training of j −log p(yj|xj) using stochastic gradient descent with Adam [28]"}
                     └────────┬────────┘└──────────────────┬──────────────────────────────┘
                        它自己加的                        这段是真的，逐字来自材料 [2]
```

**幻觉不是"凭空造"，是"拼接"** —— 它把 `BERT: Pre-training of ` 前置到一段真文本上，
造出了一条**看起来像 BERT 论文标题**的引用。这个形态比"胡言乱语"危险得多。

**3. ★★ 容错线画在哪儿 —— 今天真正的设计决定**

第 ④ 条判据「quotes 在原文里找得到吗」，怎么算"找得到"？三个方案，**没有免费的**：

| 方案 | 代价 |
|---|---|
| 精确 `in` | 模型换个标点、少个空格，**真引用被误报成伪造** → 假阳性 |
| 归一化后 `in` | 得定义"归一化到什么程度"，收得越松 → 假阴性 |
| 模糊匹配 | 阈值是魔法数字，且**没有明确边界**（"90% 像"算不算引用？答不上来） |

**想清楚你在防谁**：对手是一个**会努力模仿格式**的模型（见 Day 5「穿制服」），
不是一个只会精确复制的程序。

**你选了归一化**，探针里有活证据（跑一次就能看到）：

| 用例 | 结果 |
|---|---|
| `we marginalize ... approximation`（首字母小写、句号没了） | 报出 **0** 条 → ✅ 放行 |
| `RAG was invented by Google in 2019.`（编的） | 报出 **1** 条 → ✅ 拦住 |

**同一套判据，两个方向都对了。** 严格的 `in` 做不到 —— 第一条会被误报。

**4. ★ 「守卫的判据，和它守的那个操作，必须是同一个」**

`verify` 要拿 `quotes` 的键做 `int(k)`。直觉是在 `parse_response` 里加一句
`if not k.isdigit()` 守住它。实测之后发现**守不住**：

| 键 | `isdigit()` | `int()` | |
|---|---|---|---|
| `'2'` | True | 2 | ✅ 一致 |
| `'²'` | **True** | **ValueError** | ❌ **守不住** |
| `' 2'` | **False** | **2** | ❌ **误伤** |
| `'+2'` | False | 2 | ❌ 误伤 |

`isdigit()` **既拦不住它该拦的，又误伤它不该拦的。**
所以判据直接用 `int()` 本身（`try / except`）——
守卫和操作字面上是同一个东西，**就没法各自漂移**。

> 一条"看起来在守卫"的假防线，比没有防线更危险 —— 它给你安全感。

**5. ★ 契约只声明一次，写在能写的那一层**

今天改了两处**方向相反**的东西：

| | 改动 | 方向 |
|---|---|---|
| `generator.py` | 「键是字符串」→「键是**数字**串」 | **上游收紧**，让下游敢信任 |
| `cite.py` | 删掉 `.get("used", [])` 的默认值 | **下游别乱兜底** |

目标是同一件事：**每一条保证只写一遍。**

为什么「键是数字」归 `parse_response` 而不是 `verify`：
- 它**不需要 `chunks`** —— 需要的才是 `verify` 的事（比如「[99] 这条材料存不存在」）
- 更根本的：**类型不对 = 这个 dict 不是我们要的形状 = 下游根本没法用**
- 对照它的邻居：`used` 那行检查了**元素的类型**，`quotes` 检查**键的类型**，本来就该对称

而删默认值的理由 —— `parse_response` 已经保证字段**必然存在**（缺了就抛异常），
所以默认值**永远走不到**，除非有人绕过它直接调。真走到那一步：

```
缺 used → 默认成 [] → "拒答"分支直接放行
```

**把「调用方的 bug」伪装成了「一次正常的拒答」。** 这和 `parse_response` 里
「凡是需要你补一个值的，就是在编」是同一个判断。

> 现在传错会 `KeyError` —— 响，而且直指出错的那一行。
> 调用方的程序错误**不该**混进「模型哪里说错了」的问题清单：混在一起，
> 你会开始去修模型，而 bug 在调用方。

**6. 「抛异常」和「报清单」是两层不同的失败**

- `parse_response`：判**能不能用** —— 不能用就抛，它没有降级的方式
- `verify`：判**好不好** —— 逐条报告、不中断，因为调用方要的是问题清单

**7. ★ `temperature=0` 不保证可复现**

一件事我上次说错了，今天纠正：Day 5 我写「`temperature=0` 下原样复现」。
准确的版本是 ——

> `temperature=0` 只保证**不随机采样**，不保证底层浮点归约顺序一致
> （GPU 分批、多线程都会影响）。**基本可复现 ≠ 保证可复现。**

证据：同一条 prompt、`temperature=0`，探针某次和手工重跑某次给了**不同**输出；
但连跑 4 次又是**完全一致**的。想真正钉死一次实验结果，得显式固定 `seed`。
（探针两个 `generate` 已加 `"seed": 42`。）

**8. ★ 测试不只是防回归，它还是「设计决定的存档」**

新增的 `quotes 的键是上标 2` 这条用例，存在的唯一理由是：
将来有人把判据"简化"回 `isdigit()`，**测试会当场变红**。
没有它，那个人改完测试全绿，**永远不会知道**。

**9. 报错要让它响在正确的地方**

`verify` 返回 `None`（函数掉出末尾，一个 `return` 都没走到）是最坏的情况 ——
调用方写 `if problems:`，`None` 是**假值** → **静默通过**。
**报错的 bug 可以等，静默的 bug 不能等。**

### 踩过的坑

1. **`return` 的缩进位置 —— 同一个 bug 犯了两次。**
   三档缩进，三种行为：

   | 缩进 | 实际含义 |
   |---|---|
   | 4 空格（函数级） | 所有检查之后返回 ✅ **正确** |
   | 8 空格（`for` 里） | **第一轮循环就返回** —— 只检查了第一个引用 |
   | 12 空格（`if` 里） | **只在发现伪造时才返回** —— 没问题就返回 `None` |

   第一次探针 5/7，改完变 3/7（改到 12 空格，更糟）—— 最后才回到 4 空格 → **7/7**。

2. **`None` 被 `if problems:` 当成假值。** 函数没走到任何 `return` 就掉出来了，
   调用方却以为"没问题"。**Python 里最隐蔽的失败是"忘了 return"。**
   探针能抓到它，只是因为写的是 `len(problems)`（在 `None` 上会炸）而不是 `if problems:`。

3. **探针自己有两个同类 bug**（我写的）：
   - 一开始在 `None` 上崩（`len(None)`）
   - 加了兜底之后，「编号越界」显示 ✅ **假绿** —— 因为 `None` 被当成"报出了 1 条"
   - 修法：`report()` 加 `crashed` 参数，**炸了就是 ❌，不管期望值是什么**

4. **观察项是死代码**（我写的）。`report()` 里写了 `expect is None` 的分支（打 👁、不计分），
   但调用处是 `if expect is not None:` —— **把观察项整个跳过了**。
   最讽刺的是：那一条正是「归一化 vs 严格 `in`」这个决定的**唯一证据存档**，
   而它**一次都没显示过**。自称观察项，却从不观察。

5. **过期注释又来了，而且是同一个错的第二处。**
   - `probe_generate.py` 里「现在跑的是 v0」—— v0 早废弃了。
     **同一个错有两处，上次只改了文件头那处，漏了这处。**
   - `probe_cite.py` 里「第 1~6 关」，用例早就是 8 条了。
     → 修法不是改成"第 1~8 关"，是**把编号整个去掉** —— 数不清的东西就别编号。

6. **我把一次偶发输出当成了"非确定性"。** 看到两次输出不同就下了结论，
   没有先量。**4 次连跑推翻了我。** 教训见「学到什么 7」。

### 决策记录

| 决定 | 理由 |
|---|---|
| 容错线用**归一化** | 实测两个方向都对（放行真引用 / 拦住伪造）；严格 `in` 会误报 |
| 判据用 `int()` 不用 `isdigit()` | 见坑 4 的实测表；守卫与操作必须同源 |
| `verify` 返回值**去掉默认值** | 契约已保证字段存在；默认值是伪装成拒答的后门 |
| `find("{")` 的漏洞**仍然不修** | 恢复条件不变：探针里连续两次看到该报错 → 立刻修 |
| 第 4 枪**仍然不修** | **语料层**的问题：全库只有 1 篇论文，里面 7 块提到 BERT 却没一块在讲它 |

### 待复习

- **★ 幻觉是拼接，不是凭空造** —— 真片段 + 自己加的前缀

## 2026-10-06 · 语料重置与切分重建

> 冲刺结束后的第一次维护。起因是换语料，结果挖出 Stage 1 里**埋了很久的一整类问题**。
> 这一天没有写新功能，全部工作量在**修「当初就写错了、但只有一篇论文时看不出来」的东西**。

### 为什么重置语料

原来的语料只有 1 篇 RAG 论文（`rag-original-2005.11401.pdf`）。它是跨领域的孤儿 ——
任何 KG 问题都检索不到它，任何 RAG 问题都只会检索到它。**干扰项为零，分数被美化。**

换成两篇 KG 综述：

| 文件 | paper_id |
|---|---|
| `Knowledge Graph Embedding An Overview.pdf` | `kg-embedding-overview` |
| `A Survey of Knowledge Graph Reasoning on Graph Types Static, Dynamic, and Multi-Modal.pdf` | `kg-reasoning-survey` |

两篇是**相邻主题**、互为最好的干扰项 —— 检索必须真的能区分「KG 嵌入」和「KG 推理」。

> 原来的 10 道 RAG 评测题随语料作废，存档在 `data/eval/queries_rag-archive.json`。
> **别删** —— 它保留的是**格式和出题原则**（`targets` 可多个、取排名最靠前的计分）。

### 切分到底坏成什么样（换语料之后才看得见）

| | 改前 | 改后 |
|---|---|---|
| chunk 数 | 368 | **337** |
| 字符数 | 81,323 | **124,802** |
| kg-embedding 保留率 | **8.7%** | **89.2%** |
| kg-reasoning 保留率 | **47.8%** | **95.5%** |
| kg-reasoning 的 section 种类 | **1 种**（全篇=作者列表） | **28 种**（真实章节结构） |

8.7% 的意思是：**这篇论文有 91% 的字根本没进索引。**

### 三轮修复

**① 版面（一次改五处）**

| 原来 | 现在 | 为什么 |
|---|---|---|
| `x0 < PAGE_MARGIN_X` 扔边栏 | **删掉** | 双栏论文左栏起点就是 x≈38，这条把**整栏**当水印扔 |
| 坐标判页眉页脚 | 相对页高的比例 → 后来又删掉 | 730 是照 Letter 纸定的，遇 663 的页永远不触发 |
| — | `is_rotated_block()` | 竖排水印用「文字有没有被转过来」抓，与尺寸无关 |
| — | `find_column_split()` | **左右栏是排序问题，不是过滤问题** |
| 逐块就地处理 | `order_blocks()` | PDF 块序 ≠ 阅读顺序 |

> 最关键的认知转变：**原来把「分辨左右栏」错当成了「过滤掉非正文」。**
> 过滤是丢弃，分栏是排序。混成一步，就必然要用阈值区分「左栏」和「边栏水印」——
> 而这两者在坐标上**没有区别**。

实测证据（kg-reasoning 第 6 页，同为双栏）：

```
改前 3,409 字符  ← 左栏 5 块全丢，含小节标题 'Tensor Decompositional Model'
改后 6,957 字符  ← 6 块齐全
```

**② 页眉页脚：改用「归一化后跨页重复」**

比例判据看着解决了尺寸问题，但更根本的问题露出来了：

> **页面顶上，「页眉」和「栏顶第一行」占的是同一个 y。**

实测 kg-reasoning 第 15 页：两个块 `y0/H` 都是 **0.082**，x 分别是 42.1 和 305.1 ——
那是左右两栏各自的栏顶小节标题（`E. Inconsistent Reasoning` /
`H. Knowledge Graph Reasoning Application`）。`PAGE_HEADER_RATIO = 0.10` 把两个真标题一起误杀了。

**任何 y 区间都分不开它们，因为它们在几何上就是同一行。** 能分开的只有跨页重复：

| | 命中 |
|---|---|
| kg-reasoning（23 页） | 页脚水印 23/23、奇数页书眉 12/23、偶数页书眉 11/23 |
| kg-embedding（51 页） | `'# Ge et al.'` 25/51、`'Knowledge … Overview #'` 25/51 |

12+11=23 —— 正是奇数页/偶数页各一条书眉。**关键是要先把数字归一化成 `#`**，
否则「9456 IEEE…」和「9458 IEEE…」各出现 1 次，一条家具都找不出来。

**③ 标题检测：整套排版判据丢掉，改成看文本**

原来靠「字号更大」或「同字号+粗体」。实测对两篇新论文**双双失效**：

```
kg-reasoning（IEEE 版式）: 'A. Definition and Notation'  size=10.0  bold=False  font=Times-Italic
                          'I. INTRODUCTION'              size= 8.0  bold=False  ← 比正文还小
kg-embedding（Springer）:  '1.1 Background'              size= 9.0  bold=True   ← 差 1.0，超过容差 0.3
                          '2 (⟨h,r,t⟩+ ⟨t,r′,h⟩).(17)'   size=10.0  bold=True   ← 数学字体报 bold，公式被误判
```

换成了：

| 信号 | 内容 | 实测精度 |
|---|---|---|
| 学术编号 | `1` / `1.1` / `A.` / `IV.`，**且编号后必须跟字母开头的词** | — |
| 结构词 | `Abstract` `References` `Acknowledgments` … | — |
| 合计 | kg-reasoning 32 命中 0 误判 / kg-embedding 31 命中 4 误判 | **~94%** |

> 那个「编号后必须跟字母」的一个字符，挡掉了大量公式碎片：
> `'2. (3)'`（后面是括号）、`'1 0 vx 0 1 vy'`（后面是数字）。

**④ 参考文献：入库即丢**

这是今天量出来最大的一个数 —— **全库 53% 的 chunk 是参考文献条目**：

| | chunk 占比 | 字符占比 |
|---|---|---|
| kg-reasoning | 346/516 = **67%** | 45% |
| kg-embedding | 27/194 = 14% | 40% |
| **全库** | **373/710 = 53%** | — |

它们对问答没有价值，却在词面上跟任何领域问题高度重叠
（一条里塞满模型名/作者名/会议名），检索时会被大量召回、挤掉真正的正文。

> **判据挂在块的 `section` 上，不是「遇到 REFERENCES 就停止」。**
> 后者在参考文献不位于文末时会**静默截断后面整篇** —— 正是这一天在修的那类 bug。

### ★ 这一天的核心教训：四次发作，同一个病

| # | 常量 | 结果 |
|---|---|---|
| 1 | `PAGE_MARGIN_X = 108` | 更早，日志里记过 |
| 2 | `PAGE_MARGIN_X = 60` | 把双栏左栏当水印扔，丢 82% 字符 |
| 3 | `PAGE_HEADER_Y=60` / `PAGE_FOOTER_Y=730` | 730 对 663 高的页面永远不触发 |
| 4 | `HEADING_SIZE_GAP = 1.0` | 对两篇新论文双双失效 |

**四个的共同结构：把一个文档的经验值，写成了一条关于文档的规则。**

原来「补丁」的做法是把 108 调成 60 —— 治的是症状，常量依然是「某篇论文的经验值」。
真正的出路是**换判据的种类**：

| 不要用 | 改用 |
|---|---|
| 排版特征（坐标、字号、字体、粗细） | **文档结构**（文字走向、跨页重复、章节编号） |
| 每篇论文自己的约定 | **学术写作的约定** |

### ★ 第二个教训：三次「没量就下结论」被当场抓住

| 我说的 | 量出来的 |
|---|---|
| 「稀有样式可以判标题」（我先提的方案） | 精度只有**四成**，101 个命中里绝大多数是公式碎片 |
| 「字号分布的自然断点可以判标题层」 | 标题和正文**在同一个字号桶里**，直方图上没有断点可切 |
| （预设 kg-reasoning p6 那块是「半句截断」） | 查了，**那块本来就是段首** —— 假设不成立，结论作废 |

> 和上一轮 `cite.py` 里「迭代 set 会 flaky」是同一个错。**先量，再说。**

### 决策记录

| 决定 | 理由 |
|---|---|
| 标题检测**整套**换掉，不留后备 | 两套规则叠在一起，判据变成两层，以后更难讲清楚 |
| 四个字号函数（`find_body_size` 等）**直接删** | 死代码最坏的地方不是占地方，是**它读起来像还在生效的东西** |
| 参考文献**入库即丢**（而非检索时过滤） | 索引里一半是永远不会被用的向量，不如不建 |
| 判据挂 `section`，不是「遇到 REFERENCES 停止」 | 后者会静默截断，是这天一直在修的那类 bug |

## 2026-10-09 · 探针说谎的那一天（Stage 4 收尾）

### 第一件事：一个自相矛盾的探针输出

跑 `scripts/probe_cite.py`，实验 A 打出来两行**互相打架**的结论：

```
  quotes[1] 逐字在材料 1 的原文里？ ❌ 找不到 —— 这是伪造
verify 报出 0 条： ⚠️ 没抓到。
```

探针说"这是伪造"，`verify` 说"没问题"。同一份输入。

### 诊断：两条容错线，一个函数两副面孔

把两条判据摊开比：

| 判据 | 比对对象 | 比对方式 | 结果 |
|---|---|---|---|
| 探针自己那句 ❌ | `chunk["text"]` | `q in text` 逐字、大小写敏感 | **False** |
| `verify` ④ 的基线 | `render_material(...)` | `_norm()` 归一化后比 | **True** |

然后去原文里找那句话：

```
… BERT is a pretrained bidirectional language model that is built based on
transformer architecture. Since one of the tasks of BERT pretraining is
next-sentence prediction it naturally generates good features for …
```

模型交的是 `One of the tasks of BERT pretraining is next-sentence prediction`
—— **首字母从 `one` 变成了 `One`。就这一个字母。**

★ **探针那句「逐字 `in`」，正是 `cite.py` docstring 里列出的「方案一 · 精确 in」**，
而 `verify` 用的是「方案二 · 归一化」。两条线不同，在真实模型输出上**必然分叉**——
因为我们的对手本来就「会努力模仿格式」。**假阳性的代价比假阴性高**：
它会训练人无视警报（和 `config.py` 里「报警疲劳」是同一个病）。

### 修复：不再压成一个布尔，分三层报

`check_quotes()` 现在报三列：

```
quotes[1] ◐ ①否 ②在 ③在   只是大小写/标点差异 —— 是【真】引用，不是伪造
```

```
① 逐字在不在正文里                —— 最严
② 归一化后在不在正文里            —— 摊平大小写 / 标点 / 换行
③ 归一化后在【模型看到的材料】里  —— ② 再加表头
```

**① 挂、② 过 = 模型穿了个制服，不是伪造。**

两处刻意的**独立实现**（对拍要两套，import 过来就成复读了）：

| | 产品路径 | 探针自己 |
|---|---|---|
| 归一化 | `cite._norm()` | `probe_norm()`（同规格，自己写） |
| 材料渲染 | `generator.render_material()` | `induce_material()`（诱导条件的表头只有 `[n]`） |

### 换题：连着失败三次，每次原因都不一样

实验 A 的前提是「材料里没有答案」——**从来没验证过**。真去查：

| # | 问题 | 查证结果 |
|---|---|---|
| ① | BERT 的预训练任务是什么？ | **前提不成立**。top-1（§5.2）里恰好有一句 `Since one of the tasks of BERT pretraining is next-sentence prediction`。材料里有答案，模型照抄 |
| ② | BERT-base 一共有多少参数？ | 全库 337 条 **0 命中**。但模型**宁可违反指令也不编**：5 个 seed 全答「材料中未明确给出」，再贴一句真话充数。明令「严禁出现未明确给出」之后，它还是这么说 |
| ③ | Attention Is All You Need 的作者是谁？ / BERT 是哪一年提出的？ | ✅ 模型一提问就**知道**答案（Vaswani 等 / 2018），而全库各 0 命中。**这才是 RAG 幻觉的教科书形态** |

★ 实验结果：

```
实验 A 汇总（2 题 × 4 seed = 8 次）
  编造被抓    4 次
  没编        4 次
  解析失败    0 次
  两边对不上  0 次   ← 这一项必须为 0
```

### 发现一：「无中生有」和「有中生错」是同一种行为的两张脸

拿掉拒答规则之后，模型的第一反应**不是**编造。看它交的东西：

```
问：Attention Is All You Need 这篇论文的作者是谁？
答：这篇论文的作者信息在提供的材料中并未直接给出。
quotes: "Xiou Ge, xiouge@usc.edu."     ← 材料 [1] 的通讯作者邮箱，真的，但完全无关
```

它为了满足「quotes 不许为空」，**抓了一句真实但无关的句子来充数**。
那不是无中生有，那是实验 B 演示的「有中生错」。**同一个诱导，把它推向了另一类幻觉。**

### 发现二：`seed` 保证不了可复现

同一个 prompt + 同一个 seed：

- **同一进程内**连跑 6 次 → 逐字一致
- **跨时间**（半小时后）→ 结果不同（前一次编了，后一次不编）

起因未查明（疑似 Ollama 加载/缓存状态）。**结论：不能把"诱导出伪造"当成稳定现象依赖。**
所以实验 A 从「一次断言」改成「扫描 + 报比例」；稳定的伪造证明留在离线用例里。

### 发现三 ★ 最重要：模型把材料**翻译**了，再当"原样抄的句子"交

`BERT 是哪一年提出的？`——**4 个 seed 全都"编"了**，但编的方式不是我预期的。

材料 [1]（`kg-embedding-overview#159`）原文：

> PLMs are transformer-based models with many model parameters that are trained over
> large-scale corpora. … One of the famous PLMs is BERT [25]. BERT is a pretrained
> bidirectional language model that is built based on transformer architecture.
> Since one of the tasks of BERT pretraining is next-sentence prediction it naturally
> generates good features for …

模型交的 quotes[1]：

> BERT是2018年提出的语言模型，基于变换器架构，具有许多模型参数，并在大规模语料库上进行训练。
> 它以下一个句子预测任务为目标，能够生成各种NLP任务的良好特征。

**逐句对得上——它是把材料忠实翻译成了中文**，中间只塞进一个材料里没有的 `2018`。

| | 状态 |
|---|---|
| 答案「BERT 是 2018 年提出」 | 事实正确（BERT 确实 2018 年），但来自**模型记忆**，不是材料 |

| [5] | kg-reasoning-survey | `A. Review on Reasoning Techniques` | "Static **KGR** models can be categorized into **embedding-based, path-based, and rule-based** models" |

模型答的是后者（中文「嵌入基 / 路径基 / 规则基」）。**标准答案就在 [2]，而且是 top-2 命中。**

- **不是检索没捞上来** —— 答案稳稳在 prompt 里
- **不是材料里没有** —— [2] 明写着
- **verify 报 0 条是对的** —— [5] 那句原文确实存在，引用是真的

这是**有中生错**的教科书现场，也是 Stage 4 结构上抓不住的那一类。
`verify` 能证明"这句话有出处"，不能证明"这个出处该被用在这里"。

### 二、隔离实验：谁在起作用

同题、同参数（`temperature=0, seed=1`），**只换材料集合**：

| | 给的材料 | 答案 |
|---|---|---|
| ① | 只有 [2] | 「距离基 / 语义匹配基」 ✅ |
| ② | 只有 [5] | 「嵌入、路径、规则」 ❌ |
| ③ | [2] + [5] | 「嵌入基、路径基、规则基」 ❌ |
| ④ | 全部 5 条 | 同上 ❌ |

**① 单独跑答对 → 检索和材料都没问题。③ 说明 [5] 不是"多了条噪音"，是压制。**

### 三、修：表头里加【判别器】

加了三种身份，5 个 seed：

| 表头 | 判定 |
|---|---|
| `[1] （ABSTRACT，第 1 页）` | 错 错 错 错 错 |
| `[1] （kg-embedding-overview · …）` | 混 混 混 混 混 |
| `[1] （Knowledge Graph Embedding: An Overview · …）` | **对 对 对 对 对** |

三级梯度，单调。**关键不是"有没有出处"，是"出处的名字里有没有那两个字"**：
`kg-embedding-overview` 已经修好了**归属**（模型认出 [5] 是推理那篇），
但只有真标题里的 "Embedding" 才让它敢把 [5] 排除掉。

★ 加 `paper_id` 是个**半吊子修法**：模型说对了出处、却照旧把错的分类塞进答案 ——
**比原来更难发现**。要加就加到底。

### 四、代价：修好了 A，弄坏了 Q3

`title` 一进表头，另一个问题崩了。问「静态和时序推理的区别」，模型交 `used=[3]` 但
**`quotes={}`** —— 干脆不交引用。同场 A/B：

| 表头 | Q2（失败 A） | Q3（交没交引用） |
|---|---|---|
| old（只有 section） | 错 错 错 错 错 | 交 交 交 交 交 |
| **`title[:40]`** | **对 对 对 对 对** | **交 交 交 交 交** |
| `title` 全文 | 对 对 对 对 对 | 空 空 空 空 空 |

**病根是长度，不是标题。** 扫截断长度（同一场）：

| 截断 | 20 | 25 | 30 | **40** | **55** | 70 |
|---|---|---|---|---|---|---|
| Q2 | 混错错错 | 混×4 | 错对对对 | **对×4** | **对×4** | 对×4 |
| Q3 | 交×4 | 交×4 | 交×4 | **交×4** | **交×4** | 空空空空 |

两条约束把窗口夹出来：**太短 → 判别词被切断**（25 时 `Reasoning` 没了）；
**太长 → 模型不交引用**（70 全空）。40 落在两侧都有余量的位置。

★ **这是魔法数字，不假装不是。** 它成立的隐含前提是
「判别词出现在标题前 40 字内」（本文两篇：`Embedding` 第 16 位、`Reasoning` 第 30 位）。
**换论文时要重新量。** 见 `generator.TITLE_MAX`。

### 五、★ 今天最大的发现：seed 跨【会话】不可复现，我踩了一次

测 45/50 两个长度，跑出来**模式一模一样**（seed 1 交、2~6 全空）：
两个不同长度给出同一个模式 → 说明那一场里**表头根本没起作用**，是会话状态在主导。
而它和上一场的结论（55 交×4、70 空×4）直接矛盾。

**那组数据作废** —— 因为它没有同场基线，分不清是表头的错还是那一场的漂移。

上一节已经记过「seed 跨时间不可复现」，但**当时没意识到它把 A/B 方法本身打穿了**。
从今天起，比较方案的规矩加两条：

1. **所有变体必须在同一个进程里跑完** —— 跨场的数据不可比，哪怕参数一字不差
2. **必须带一个已知基线当"温度计"** —— 基线表现和上次不一样，这一整场作废

（按新规矩重跑的那一场，三行同场可比，结论才立住：old 错×5、`title[:40]` 对×5/交×5、全文 对×5/空×5。）

### 六、顺带查清的两件事

**① 探针的假材料在说谎 —— 而且它报 3/9 的时候退出码是 0。**

表头一改读 `title`，探针离线关卡从 **9/9 掉到 3/9**：`FAKE` 那三条假材料是照旧 schema
手搓的，没有 `title`，六个用例炸 `KeyError`。

修的是**假材料**，不是 `render_material`：
`chunk.get('title', '')` 是"补一个值"，而缺 title 会**静默产出没有判别器的表头** ——
正好把刚修掉的 bug 放回来。假材料必须和真材料同形；它照旧 schema 手搓，
**本来就在说谎**，只是平时不响，只在 schema 变更时炸，而炸的时候看起来像"产品坏了"。

★ 更要紧的：**`probe_cite.py` 报 3/9 时退出码是 0。** 当时写的理由是"放进 CI 就是
静默通过"—— 那句是**推测**：查过了，这个仓库**没有 CI**（`.github/workflows` 不存在，
也没有任何其它 CI 配置）。理由得换成真的那个：**人**跑 `probe && 下一步` 时被骗，
而且这个坑不修，永远别想加 CI。见下面第八节。

**② Q1 那条「疑似伪造」是真阳性 —— 又是「改写冒充引用」。**

| | |
|---|---|
| 材料原文 | "**According to graph types,** KGR **can be categorized into** three tasks, i.e., static, temporal, and multi-modal KGR." |
| 模型交的 | "Knowledge graph reasoning (KGR) **can be categorized into** three tasks, …" |

模型把 `KGR` **展开**成 `Knowledge graph reasoning (KGR)`、又**删掉**了 "According to graph types,"。
意思对，字符串不对 —— 和上一节的「翻译冒充」是同一族病，**轻症版**：不是翻译，是"顺手改好"。

**不要为了消掉它去放松容错线。** `cite.py` 已经论证过模糊匹配没有明确边界；
契约写的是「逐字复制，一个字都不要改」，模型违反了 —— 这就是它该报的。
（改动前就有，不是今天的副作用。）

### 七、复盘：我今天问错了一类问题

修这个 bug 的中途，我在"模型为什么会挑错材料"上连着反问了用户几轮。
用户回了一句：**「你现在不是应该修bug吗？为什么纠结于我怎么看？」**

**这话是对的。** 它命中的是早就定好的规矩（反问只在**设计判断**的分叉点），
而我问的是个**事实** —— 跑三次隔离实验就能拿到，而且我确实拿到了（见第二节）。

把"我该跑的腿"包装成"引导式提问"，只是把工作推给用户，还拖慢了进度。

| | 例子 | 谁做 |
|---|---|---|
| **事实**（跑一下就知道） | 检索捞上来了什么 / 模型这次答了什么 | **我跑**，结果摆出来 |
| **判断**（要选、要权衡） | 容错线画哪 / 这个代价认不认 / 出题 | **他答** |

"跑之前写预测、跑完不许改"那套规矩，用在**评测集出题**上是对的（那是判断），
不该套到诊断实验上。

### 八、探针必须能失败（当天接着修的）

**病根一句话：打印不是返回值。**

`probe_cite.py` 的 `main()` 把结论 `print()` 出来，然后**从函数末尾掉出去** ——
Python 默认 exit 0。而 `run_offline()` 也一样：把 `9/9 通过` 打出来就完了，
**返回值是 `None`**。于是 9/9 和 3/9 在退出码上**长得一模一样**。

> 人看得见，程序看不见。凡是"只打印、不返回"的判据，
> 都只是**给人看的**，接不走、串不起来、也没法进流水线。

修完之后的三态：

| 码 | 含义 | 为什么不能合成一个 1 |
|---|---|---|
| `0` | 该测的都测了，都过了 | |
| `1` | 有断言挂了 —— 产品的问题 | |
| `2` | 断言全过，但实验 A **没诱导出伪造** | 合成 1 = **假警报**；假警报会训练人无视警报 |

第三态是这次真正的设计点。探针自己早就写着「**没测到 ≠ 通过**」，
可退出码上从来没有这一档 —— 它只有"好"和"坏"，而"没测到"两边都不是。

**★ 当天就验证了这个设计不是多余的**：完整跑一次，给出**退出码 2** ——
离线 9/9 全过、两边对不上 0 次，但实验 A 一轮 8 次里**一次都没诱导出伪造**
（没编 4、解析失败 4）。这一枪是**空的**。报 0 是假绿，报 1 是甩锅给产品。

**顺手查了同类**（搜 `scripts/` 里所有会判对错的脚本）：只有 `probe_generate.py`
也在计分（`18/18 通过`），同一个病，一并修了 —— 它只有两态，没有第三态的问题
（那四道题是演示，不是诱导实验）。改完实测 **18/18 → 退出码 0**。

**修的过程中还发现一处没修的**（见遗留表）：`probe_generate.main()` 里
四道演示题的 `except Exception: continue` —— **模型炸了它照样往下走**，
最后可能 exit 0。这跟 `probe_cite.report()` 那条"炸了就是炸了"是同一族，
但它牵涉一个判断（**炸一处就算失败，还是全炸才算**），留给他定。

### 三、S5-2 完成：BM25 —— 代码顺，但真正的产出是「发现基线量错了」

📄 **完整记录：[`docs/stages/S5-2-bm25.md`](stages/S5-2-bm25.md)**

**改了什么**

| 文件 | 产品/脚手架 | |
|---|---|---|
| `paper_rag/bm25.py` | **产品**（新增） | 纯算法：`tokenize` + 倒排索引 + BM25 打分。**不 import 本项目任何东西** |
| `paper_rag/retriever.py` | **产品** | 加 `BM25Retriever` —— 兑现 S5-1 的接口决定 |
| `scripts/eval_retrieve.py` | 脚手架 | `--expand`、`--kind` 逗号分隔、bm25 分支、**修一个静默 bug** |

**接口决定的兑现（S5-1 那个赌注的答案）**

`BM25Retriever` 这个类里**没有 `embed_one`、没有向量、没有 numpy** ——
它拿到 query 之后是分词 → 查倒排表 → 加分数。

> 如果 `Retriever.search` 收的是 `query_vec: list[float]`，**这个类根本写不出来**。
> ★ **一个抽象设计得对不对，不是看第一个实现顺不顺，
> 是看【最不像的那个实现】能不能原样进来。**
> 它的 `from_chunks` 签名还和 dense 不一样（不收 client）——
> 而这是允许的，因为 `Protocol` 只约束 `search`。

**对拍：dense 的数字一位没动**

S5-0 记的基线（50% / 0.563 / 21.4 / 58%）在新代码路径上**四位全同**。
说明从「内联循环」改成「走接口」这一路没有偷偷动过数字。

**★ 然后才发现：那个基线量错了一个变量**

`config.EXPAND_ENABLED = True` —— **生产一直是开着查询扩展的**，
而 `eval_retrieve.py` / `eval_embed.py` **从来就没有这个开关**。

| 检索器 | Top-1 | MRR | 平均排名 | recall@5 | 空结果 |
|---|---|---|---|---|---|
| dense，不扩展 | 50% | 0.563 | 21.4 | 58% | 0 |
| **dense，扩展（= 生产）** | **58%** | **0.646** | **17.5** | **67%** | 0 |
| BM25，不扩展 | 17% | 0.237 | 897.9 | 33% | 7 |
| BM25，扩展 | 25% | 0.376 | 242.8 | 50% | 1 |

> ★ **这是「评测和产品量的不是同一个东西」的第二个实例。**
> 第一个是 S5-1 的 query 前缀（只活在评测脚本里）。
> 这类变量最阴：**不改代码路径、不报错、不影响单测，只让两边悄悄量不同的东西。**
>
> **升级成规矩**：评测里每一个「只影响 query 的开关」，都要问一句
> **「生产是这个值吗？」**

**★ 修掉一个静默 bug（本步最值钱的一处）**

```python
rank = len(scored) + 1     # 旧 —— 检索器返回【空】时，结果是 1
rank = all_k + 1           # 现在 —— 「比全语料最后一名还差」
```

dense 永远返回满额，所以这个 bug **在 dense 上永远看不出来**。
BM25 撞上纯中文 query 会返回 `[]` → 旧写法把「什么都没找到」记成**第 1 名**。

实测代价（同一份 BM25，不扩展）：

| rank 写法 | Top-1 | MRR | recall@5 |
|---|---|---|---|
| `len(scored)+1`（旧） | **75%** | **0.828** | **92%** |
| `all_k+1`（现在） | 17% | 0.237 | 33% |

**旧写法会让一个「7/12 题完全失明」的 BM25 看起来碾压 dense（50%/0.563/58%）。**
而且不报错、退出码 0。**如果留到 S5-3，整个 Stage 5 会长在一个假前提上。**

**BM25 输在哪：一个能指着看的取证（Q9）**

> `CompoundE3D 的剪切算子是复合了哪三个算子？`

BM25 的候选池只有 **9 条**（只对含 `compounde3d` 的文档打分），
而**正确 chunk 里根本没出现过 "CompoundE3D"**：

> The shear operator is the result of **compounding 3 operators**: Hyz, Hxz, and Hxy

- **BM25**：query 只有 1 个词 → 候选 9 条 → 答案不在里面 → **连机会都没有**
- **dense**：一个字都不重合，靠语义对上 → **第 21 名**

★ 这把「dense 比意思、BM25 比字面」从口号变成了具体失败。
★ 也带出一个新概念：**候选池不是常数**（实测 0~646 条），
所以 BM25 的「第 94 名」和 dense 的「第 35 名」**不在同一个尺度上**。

**⚠️ 但必须写下来：这张表不支持「加 BM25 会涨分」**

12 题里 BM25 **没有一题**明显好过 dense（只有 Q5：83 vs 139，两边都在 80 名开外）。
dense 的 4 个弱点，BM25 全都不如。

| | 结论 | 证据强度 |
|---|---|---|
| 这 12 题上 BM25 单独打不过 dense | 成立 | 强（逐题可查） |
| 这 12 题上 RRF 会涨分 | **不知道** | **12 题量不出来** |
| BM25 该保留 | 应该 | 结构性理由（独立故障模式）|

12 题一道值 8.3%、SE ±14%，**差距比噪声还小。**
所以 **S5-2 的结论不是「RRF 没用」，是「当前尺子量不出 RRF」。**
