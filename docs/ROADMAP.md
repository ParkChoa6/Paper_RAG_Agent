### Stage 0A · Python 最小必要集

**为什么要这一段**：RAG 项目里 `Retriever`、`Splitter` 全是类，跨文件 `import` 是日常。基础不补，后面每一步都在抄代码而不是写代码。

**只补这个项目绕不开的**，每课配一个跟 RAG 直接相关的练习：

| 课 | 内容 | 在项目里对应什么 |

| 0A-1 | dict 与 list | 一个 chunk 就是 `{"text": ..., "page": 3, ...}` |

| 0A-3 | 类与对象 | `Retriever`、`PDFLoader` 都是类 |

**明确跳过**：装饰器、异步、元类、推导式进阶、多线程 —— 用到时再补。

### Stage 1 · 文档接入

**内容**

- PDF 解析（PyMuPDF）
- 学术论文特有的坑：双栏排版、公式、表格、页眉页脚、参考文献
- 切分策略：固定长度 / 递归 / 按章节结构
- **元数据设计**：`paper_id` / `page` / `section` / `chunk_id`

**为什么元数据是重点**：它是后面"引用原文"能否实现的**唯一前提**。这里偷懒，Stage 4 要推倒重来。

**验收**：喂进一篇真实论文，输出带完整元数据的 chunks，且**页码准确**。

---

### Stage 2 · 向量化与检索

**内容**

- Embedding 是什么、为什么需要它
- 余弦相似度
- **先用 numpy 手写一遍暴力检索**
- 再换成向量库（FAISS）

**为什么先手写**：你才会知道向量库到底替你做了什么。否则它就是个黑盒。

**验收**：手写检索的结果与向量库一致，并能解释"为什么索引能加速"。

---

### Stage 3 · 朴素 RAG

**内容**

- 检索 → 拼 prompt → 调 LLM → 输出
- Prompt 设计：上下文注入、**拒答**、格式约束

**硬性要求：不许用 LangChain。** 全手写一遍，你会看清 RAG 的真实面目就是一个 for 循环加一次 API 调用。之后再用框架，你是"选择"用，不是"只能"用。

**验收**：对一篇论文提问能得到基于原文的回答；问论文里没有的内容时**会拒答**，而不是编造。

---

### Stage 4 · 引用溯源

**内容**

- 让模型输出结构化引用（而非自由文本）
- chunk → 原文的映射与回显
- **引用真伪校验**：生成的引用是否真的存在于检索结果中

**会做的实验**：故意构造一个让模型编造引用的场景，亲眼看一次幻觉。对幻觉的切肤之痛，比任何警告都管用。

**验收**：每条引用都能点回原文；能自动检出模型伪造的引用。

---

- **先建评测集**（这一步必须在所有优化之前）

**核心工程认知**：没有评测集，你所有的"优化"都只是感觉。

**验收**：有一套评测集，任何改动后都能**定量**说明是变好还是变坏。

**★ S5-6 的结论（2026-10-13）—— 它改了后面的路线**

```
                材料含答案(检索)     合规回答(答案质量)    秒/题
    dense          71%                79%              1.3
    rerank         89%  ▲+18          79%  ← 一点没动   13.3
    oracle        100%  (满分)        82%              1.3
```

**检索涨了 18 点，答案质量一点没动**（配对 McNemar：b=2, c=2, p=0.617）。
而**检索满分**时生成层也只到 82% —— **瓶颈在生成层，不在检索。**

⚠️ 两个限定，别把它读过头：
① n=28，80% 附近 95% 区间 **±15 点**，能站住的说法只是
「**没有证据表明答案质量跟着涨了 18 点**」；
② 「合规回答」= 有据可查，**不是**「答对」—— 真正那一列是判卷表，**还空着**。

在瓶颈修好之前做它们，是**在一条已经到顶的路上继续加速**。

**材料是坏的，模型反而把它"修好"了**（它是 token 级生成，不是字符级复制）。

⚠️ **八条本阶段学到的规矩**

1. **评测里每一个「只影响 query 的开关」，都要问「生产是这个值吗？」**
   撞到过两次：S5-1 的 query 前缀、S5-2 的查询扩展。这类变量不改代码路径、
   不报错、不影响单测，只让评测和生产悄悄量不同的东西。
   ★ **S5-5 是第三次的靶子**（`RETRIEVE_POOL` 只活在评测脚本里）—— 这次提前用
   `pipeline.build_retriever()` 挡掉了。
   ★ 但 S5-5 收尾时发现**只挡路径还不够**：决策定在 `pool=50`，
   而 `config.RETRIEVE_POOL` 还写着 20 —— **记录说生产是 @pool50，实际跑 @pool20**。
   → **「只有一个来源」之外，还要「这个来源被回写过」。**
2. **当一个指标把「完全不同性质的失败」糊成一个数时，它会指向错误的修法。**
   （「平均排名 897.9」= 9 题找到 + 7 题压根没找到；「没找到」其实有
   空 / 未进池 / 排名靠后**三种**，修法各不相同。）
   ★ S5-5 把这条**推到了极端**：`平均排名` 这个量被**正式判死刑** ——
   pool 从 50 到 200 时，原列说「大幅变好」（97.7 → 2.6），
   只统计找得到的题说「变差」（1.65 → 2.57）。**两列方向相反，而且两列都有偏。**
   **改用 `recall@k`（找到了吗）+ `Top-1`（排第一了吗），两个分开报。**
3. **★ 「我找到了机制」≠「改了这个会变好」。**
   局部为真的机制，整体可以是负的 —— RRF（标准做法 → 实测净负）、
   词表裁剪（机制清楚 → 整体掉 15 点）。
   ★ S5-5 补上了**镜像的另一半**：机制为真（候选越多越容易被带偏，Q7 的排名
   `3→3→4→5→6→7→7` 是活证据），**整体却是正的**（单调涨到 pool=50）。
   **合起来：局部机制的方向不能预测整体结果，只有量能。**
4. **★ 动手前先算「完美情况下能做到多少」。**
   `天花板(pool) = recall@pool` —— 它**只依赖粗排，不依赖你正要写的东西**。
   S5-5 靠这一步在写代码前就知道「pool=5 的重排最多到 71%」。
   如果天花板本身很低，**你要修的不是你正准备修的那个东西**。
5. **★ 遇到「质量换速度」的两难，先问一句：这个速度是真的吗？**
   S5-5 收尾时 `pool=50` 要 18.3 秒/题、`pool=20` 只要 10.8 秒，
   一度真在犹豫「7 个 Top-1 点值不值 7.5 秒」。
   **那个两难是假的** —— `CrossEncoder.predict` 的默认 `batch_size=32`
   是照「GPU ⇒ 无 padding」选的，在 CPU 上改成 4 之后
   **18.9s → 10.6s，而且实测指标一个字没动**。
   → 先怀疑默认值，再怀疑自己的需求。
   ★ 配套的一条：**两条加速路要分清省的是「白算的部分」还是「真内容」。**
   `max_length`（截断，丢信息）vs `batch_size`（调度，不改数学）——
   **光看数字分不出来，而且前者的数字可能更好看。** 见 S5-5 记录 4.6。

6. **★ 中间指标（你能自动算的）和出口指标（用户真正在意的）之间隔着一条河，
   宽度必须量，不能推。**
   S5-1 ~ S5-5 量的全是**检索排名** —— 那是中间指标。
   S5-6 第一次量出口：**检索涨 18 点，答案质量 0 点**（79% → 79%，配对 p=0.617）。
   更要命的是**检索满分时生成层也只到 82%** —— **瓶颈根本不在你一直在优化的那一侧。**
   → **每优化一步，都要问一句：我量的这个数，离用户拿到的东西有多远？**
   ★ 配套的一条：**报数之前先算这台仪器的分辨率。**
   n=28 时 80% 附近是 ±15 点 —— 不先算这个，
   你会把噪声当信号（S5-6 的 §4.5）。

7. **★★★ 一对运行不能标定仪器 —— 「什么是正常」需要反复量，不需要更好的解释。**
   S5-7 里我拿**一对配对**（A vs A2）算出"本底噪声 = 7/28"，
   还配了一个讲得通的机制（浮点归因翻了 argmax），写进了记录和代码注释。
   **补到 8 次运行后：真实本底噪声是 1 题，7/28 来自其中唯一一次异常运行。**
   ```
   8 次无约束运行两两对比：21 个配对在 0~2/28，
   剩下的 7 个配对全是同一个 A —— A 和【每一个】其它运行都差 7 题
   ```
   → **一个机制讲得通的解释 + 一对数据 = 看起来像结论。它不是。**
   ★ 配套：**差 1 题永远不算数**（这台仪器上 1 题就是噪声）。
   ★ 配套：`temperature=0` 本身就是这么被**误判**的 ——
   实测（11 题 × 3 遍）它**相当可复现**：11 题全部只出 1 种输出，
   而默认温度下 11 题全部出 2~3 种。**参数的实际行为要用探针量，别从端到端指标反推。**

8. **★★★ 报错文案是一种【压缩】，压缩之前先数清楚有几种病。**
   S5-8 里 `cite.verify` 对三种完全不同的失败只输出一句话
   「原文中找不到对应内容（疑似伪造）」。实测 684 条 quote：
   **19 条是它自己看错了，8 条是"编号错配"（不是伪造），只有 2 条是真伪造。**
   ```
   旧版报 56 条问题 → 34% 是假警报；剩下的还被糊成一句"疑似伪造"
   ```
   → **一个 34% 假阳性的安全组件，实际防护力低于一个少报一半但没有假警报的组件** ——
     因为假警报会**训练人无视警报**，真问题（那 2 条）跟着一起被无视。
   ★ 配套：**改松判据的那一步，必须配"构造的伪造还抓不抓得住"的测试。**
     只测"误报降了几条"是不够的 —— 一个什么都放行的校验器误报率是 0，看起来完美。
     S5-8 用的是离线 9 关 + 诱导伪造 5/5 全抓（探针【独立实现】对拍，不 import）。
   ★ 配套：**"原文"不是无损的 ground truth。** PDF 抽取会把材料弄坏
     （丢空格 `Amongthem,65.31%`、连字符断行 `knowl`+`edge`），
     而模型是 **token 级生成、不是字符级复制** —— 它会把坏的"修好"。
     **「让模型逐字抄原句」这个要求在 token 级别不可能被满足。**
   ★ 配套：**信息该在它第一次被看见的那一层就被区分开。**
     S5-6 发现了这三种病，但在**评测脚本**里事后分类 ——
     于是**只有跑评测的时候才有诊断**，生产路径上用户拿到的还是那句"疑似伪造"。
