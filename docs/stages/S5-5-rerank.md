# S5-5 · cross-encoder 重排 —— 把「排错了」和「没捞到」分开

**日期** 2026-10-12　**阶段** Stage 5
**状态** ✅ 完成。**结论：重排有用，而且这次的收益是实的 —— Top-1 50% → 68%，recall@5 71% → 89%。**
**生产 pool 取 50**（理由见 4.5，不是"越大越好"，也不是拍脑袋）。

## 1. 改了什么

### 1.1 `paper_rag/rerank.py`（新，产品）

三个东西，一层套一层：

```python
class Reranker(Protocol):                    # 契约
    name: str
    def rerank(self, query, candidates) -> list[tuple[str, float]]: ...

class CrossEncoderReranker:                  # 实现：真去调模型
    def __init__(self, id_to_text, *, model, device, max_length): ...
    @classmethod
    def from_chunks(cls, chunks, **kw): ...

class RerankedRetriever:                     # 组合：包住【任何】Retriever
    def __init__(self, base, reranker, *, pool, k): ...
    def search(self, query, k=None): ...     # 满足 Retriever
```

### 1.2 `paper_rag/rerank.py` 里的进程级模型缓存（`_MODEL_CACHE` / `_load_model`）

```python
_MODEL_CACHE: dict[tuple[str, str, int], object] = {}   # (模型, 设备, max_length) → CrossEncoder
```

★ 这不是优化，是**语义修正**（见 2.4）。

### 1.3 `paper_rag/pipeline.py`：`build_retriever()` + `ask(retriever=...)`

```python
def build_retriever(client, emb_model, vectors, ids, chunks, *,
                    k=TOP_K, pool=RETRIEVE_POOL, enabled=RERANK_ENABLED) -> Retriever:
    base = DenseRetriever(client, emb_model, vectors, ids)
    if not enabled:
        return base
    return RerankedRetriever(base, CrossEncoderReranker.from_chunks(chunks), pool=pool, k=k)
```

`ask()` 里原来那行：

```python
hits = DenseRetriever(client, emb_model, vectors, ids).search(query, k=k)
```

变成：

```python
if retriever is None:
    retriever = build_retriever(client, emb_model, vectors, ids, chunks, k=k)
hits = retriever.search(query, k=k)
```

★ **默认不传时行为完全不变**（自己建一个 dense），所以老调用方一行都不用改。

### 1.4 `ask()` 的返回值多了一项 `"retriever"`

```python
"retriever": retriever.name,   # "dense:...:raw > ce:bge-reranker-v2-m3:cpu @pool50"
```

理由和当年加论文标题**一模一样**：输出里看不出材料是怎么来的，失败就能藏很久。

### 1.5 `scripts/eval_retrieve.py`：新增 `未进候选` 一列

`evaluate()` 里原来「找不到」只有一种记法。现在拆成三种：

```python
if not scored:        empty += 1        # 空 —— 一条都没返回
elif scored:          not_in_list += 1  # 未进候选 —— 返回了，但目标不在里面
```

## 2. 为什么这么写

### 2.1 为什么重排器**不该**塞进 `Retriever` 接口

看输入：

```
Retriever.search(query)             → 只有 query，自己去【全库】找
Reranker.rerank(query, candidates)  → query + 【一批已经捞回来的候选】
```

**重排器没有检索能力。** 它拿不到全库，也不想拿。硬塞进 `Retriever` 的话，
每个重排器都得先实现一遍"怎么从 1345 条里捞 20 条" —— 而那件事它根本不干。

★ 但**「检索器 + 重排器」这个组合，应该仍然长得像检索器**：

```python
RerankedRetriever  implements  Retriever   # 只两个约定：name / search
```

**所以最上面那三行（dense / bm25 / rerank 的分支）一行都没改就多了一个成员，而 `evaluate()` 完全不知道有这回事。**
这就是"对的抽象"长什么样：加东西不用改老代码。

### 2.2 为什么重排器手里要攥着 `id → 正文`

`Retriever.search()` 的返回是 `[(chunk_id, 分数)]` —— **只有 id，没有正文**。
而 cross-encoder 算的恰恰是 `score(query, 正文)` 这一对。

正文放哪？三个选项：

| 方案 | 代价 |
|---|---|
| ① 让 `search()` 连正文一起返回 | 要改 `Retriever` 契约，BM25 / dense 全得跟着动 |
| ② 让 `RerankedRetriever` 拿着 | 它为**别人的**需要持有全库文本，绕 |
| ③ **让 `Reranker` 拿着** ★ | 见下 |

★ 选 ③ 的理由：**重排器是唯一【必须】看到正文的东西。**
把正文给唯一需要它的人，是**内聚**，不是耦合。

⚠️ 代价要说清楚：`from_chunks(chunks)` 会在内存里多存一份 `chunk_id → text` 的映射。
但**字符串对象是共享的**（Python 里同一个 `str` 不会复制），所以不是"内存翻倍"，
只是多一张 1345 项的字典。而且它**不持有向量**，不跟 `DenseRetriever` 抢内存。

### 2.3 ★ 为什么 `pool` 和 `k` 是两个参数，而且 `pool` 必须 > `k`

这是本文件**最容易犯、而且不会报错**的错。

```
想象 pool == k == 5：

    粗排捞 5 条 → 重排【只在这 5 条里调顺序】→ 取前 5

    那么第 6 名永远上不来 —— 而"正确答案排第 6"恰恰是重排最该修的情况。
    重排的全部价值就在于"把后面好的提上来"，pool == k 把这个价值【归零】。
```

⚠️ **它不报错。** 数字会动、甚至会好看一点点（在 5 条里重排确实能改善一点），
但它把 rerank 的效果**严重低估**了，而你不会知道。

★ 实测坐实了这一点 —— 同样 28 题：

| | Top-1 | recall@5 |
|---|---|---|
| pool=5（= k，重排白做） | 57% | 71% |
| pool=50 | **68%** | **89%** |

**差 11 个点，全在"第 6 名以后能不能上来"这一件事上。**

所以 `__init__` 里有一条：

```python
if pool < k:  raise ValueError(...)          # 不可能的事，直接炸
if pool == k: logger.warning("重排只能在 %d 条里换顺序，第 %d 名永远上不来", pool, k)
```

★ **这条 warning 在本次评测里真的打出来了**（`--pool 5` 那一格）——
它不是装饰，是给"未来的自己"留的刹车。

### 2.4 ★ 为什么模型缓存在**模块级**，而不是实例上

模型的**权重是只读的**。两个 reranker 指向同一个模型时，它们本来就**应该**共用同一份权重。

```
加载两遍 ≠ 更隔离，只是白白多占 2.3GB 内存、多等一次加载。
权重是 (模型名, 设备) 的【纯函数】，和"谁在用它"无关。
```

★ 但它真正防的是**生产入口的形状**：

```python
for q in questions:          # ← 循环
    ask(client, q, ...)      # ← ask 内部会新建检索器
```

如果权重缓存在**实例**上，那就是**每问一句重新加载 2.3GB**。
现象是「问答突然变得极慢」，而且**不报错、不警告** ——
正是本仓库反复踩的那种**安静的错误**。

⚠️ **但缓存不能替代依赖注入。** 生产入口仍然应该在循环外建好再传进去
（见 `scripts/ask.py`）—— 除了权重，还有对象构造和 `id_to_text` 那份引用。
**缓存只是让"忘了注入"从【灾难】降级成【有点浪费】。**

### 2.5 为什么 `build_retriever()` 放在产品里，不放在 `scripts/ask.py`

因为「生产怎么组合检索」这件事会有**不止一个**调用方：
`scripts/ask.py` 现在要，以后的 web 入口要，批量评测也要。

★ **各写一份的后果，这个仓库已经吃过两次：**

| | 症状 |
|---|---|
| S5-1 | query 前缀**只活在评测脚本里**，生产路径压根没这个概念 |
| S5-2 | 查询扩展开关在 `eval_embed.py` 里**从来不存在**，它历史上量的一直是"没扩展"的数字 |

**两份实现改一处漏一处，而且不会有任何东西报错。**

所以组合逻辑只有这一份。调用方各自决定的是**什么时候建**，不是**怎么建**。

### 2.6 为什么本地跑 HuggingFace 模型，而不是 Ollama

2026-10-12 实测（直接探端点）：

```
/api/tags        → 200
/api/embeddings  → 200
/api/embed       → 200
/api/generate    → 400     （存在，但空 body 不合法）
/api/chat        → 400     （同上）
/api/rerank      → 404     ★ 没有这个端点
```

★ 架构上的原因：**Ollama 是给「tokens → 文本」的生成式 LLM 设计的**，
而 reranker 要的是「`[query, doc]` 对 → **一个标量**」。生态里的绕法是
`llama.cpp --reranking` / vLLM / 自己起一个 `/rerank` 服务。
我们选最后一条的等价物：`sentence-transformers` 直接在进程里跑。

> **一次方法论的自我纠错**：第一遍探测时我发的是 `-d '{}'` 而**没带
> `Content-Type: application/json`**，于是 `/api/embed` 也返回了 404 ——
> 而整个项目的嵌入都靠它。**是我拿一个【已知存在】的端点做对照才发现的。**
> 教训：探测一个"有没有"时，**必须同时探一个"一定有"的**。

### 2.7 为什么 `device` 默认 `cpu`，不是 `cuda`

不是因为 cpu 快（它慢得多）。是因为那台 4070 的 12GB 显存**还要给 Ollama 用** ——
`qwen2:7b` 生成时占约 4.5GB，再挤一个 568M 的 reranker 进去，早晚撞上显存墙。

★ **而撞上时的现象是 Ollama 那边超时或 OOM，看不到 rerank 的错。**

这是一个**错误归属会指错方向**的配置：你会去查 Ollama，而问题在 rerank。

## 3. 不应该怎么写

### 3.1 ❌ `pool = k`

见 2.3。**最强的证据是它不报错** —— 你会得到一个"重排有点用但不多"的结论，
然后可能就此放弃一个实际上能涨 11 个点的方法。

**症状**：重排后 Top-1 只动一两个点，你会以为是"重排模型不行"。

### 3.2 ❌ 在循环里建重排器

```python
for q in questions:
    ask(client, q, ...)      # ask 内部 new 一个 CrossEncoderReranker
```

**症状**：第一个问题正常，之后每个问题都慢几秒到几十秒，**没有任何报错**。
如果权重缓存在实例上，就是每题重载 2.3GB。

**正确**：`build_retriever()` 在循环外调一次，`ask(retriever=...)` 传进去。

### 3.3 ❌ 拿 rerank 的「平均排名」去和 dense 比

本项目 `eval_retrieve.py` 的 `排名` 列，在 `未进候选 > 0` 时是**会骗人的**：

```
p200:  (19×1 + 53 + 0×1346) / 28 = 2.6          ← 原列：看着【极好】
p50:   (19×1 + 24 + 2×1346) / 28 = 97.7         ← 原列：看着【极差】

      但只统计"找到了的那些题"：

p200:   72 / 28 = 2.57                          ← 真相：更差
p50:    43 / 26 = 1.65                          ← 真相：更好
```

★★ **两列方向完全相反，而且两列都有偏：**

| 列 | 偏袒谁 | 为什么 |
|---|---|---|
| `排名`（原） | **大 pool** | 每道 `未进候选` 的题按 `all_k+1 = 1346` 计，惩罚主导了均值 |
| `排名`（只算找到的） | **小 pool** | 幸存者偏差 —— pool 越小，只有最容易的题能被找到 |

★ **结论：不要用"平均排名"这个指标。** 它把「没找到」和「排得靠后」糊成一个数，
而这两种病的修法完全不同。**正确做法是分开报 `recall@k`（找到了吗）和 `Top-1`（排第一了吗）。**

### 3.4 ❌ 把 cross-encoder 的 logit 当成余弦用

```
纯 dense        → 余弦相似度，∈ [−1, 1]
dense + rerank  → cross-encoder 的 logit，【可负、无上界】
```

**两者不能比大小。** 本项目目前没有按分数卡阈值的逻辑（拒答是靠模型输出的
`REFUSAL_TEXT` 判断的，不是靠余弦），所以现在不会出事 —— 但**这个前提要写下来**，
否则以后有人加一个"相似度 < 0.4 就拒答"，会在接上重排的那天静默失效。

`ask()` 的 docstring 里已经把这条写死了。

### 3.5 ❌ 以为"重排分数更高 = 这次检索更好"

**重排是纯排序操作。** 分数是相对的，只对同一次输出内部有意义。

## 4. 怎么验证它真的对了 / 量到了什么

### 4.1 先算【天花板】，再造东西

★ 这一步是本阶段最值得学的一条**方法**：在写任何代码之前，先回答
**「就算重排完美，最好能做到多少？」**

```
天花板(pool=P) = 有多少题的正确答案【本来就在 dense 的前 P 名里】
              = recall@P（就是那个已经量过的数）
```

| pool | 天花板 |
|---|---|
| 5 | 71% |
| 20 | 86% |
| 50 | 93% |
| 200 | **100%** |

**所以"pool=5 的重排最多只能到 71%"这件事是【跑之前就知道的】** ——
它把"重排效果不好"和"重排根本没机会"这两件事**提前分开了**。

★ 副产品：**「兑现率」= Top-1 ÷ 天花板**。它衡量的是"重排器把它拿到的牌打得怎么样"，
是一个**跨 pool 可比**的量（绝对值不可比，因为天花板在变）。

### 4.2 主结果（28 题 / 7 篇 / 1345 条 / `+expand`）

| 检索器 | Top-1 | MRR | recall@5 | 空 | 未进候选 | 天花板 | 兑现率 |
|---|---|---|---|---|---|---|---|
| dense（旧基线） | 50% | 0.605 | 71% | 0 | 0 | 100% | — |
| rerank **@5** | 57% | 0.637 | 71% | 0 | 8 | 71% | 0.80 |
| rerank **@10** | 57% | 0.650 | 79% | 0 | 6 | 79% | 0.73 |
| rerank **@20** | 61% | 0.695 | 86% | 0 | 4 | 86% | 0.71 |
| rerank **@30** | 64% | 0.729 | 89% | 0 | 3 | 89% | 0.72 |
| rerank **@50** | **68%** | 0.763 | 89% | 0 | 2 | 93% | 0.73 |
| rerank **@100** | **68%** | 0.777 | **93%** | 0 | 1 | 96% | 0.70 |
| rerank **@200** | **68%** | 0.779 | **93%** | 0 | **0** | **100%** | 0.68 |

★ `recall@5 == 天花板` 在 pool=5/10/20/30 四档**精确相等**。
翻译：**凡是进了候选池的题，重排器几乎都把它放进了前 5。**
它兑现得最好的地方不是"排第 1"，是"别掉出前 5"。

**① 阶梯：每扩一次池，恰好解锁一题，而且一解锁就直接顶到第 1。**

```
5→10    解锁 dense 排第 6  的 Q17  → 重排后第 1
10→20   解锁 dense 排第 12 的 Q18  → 重排后第 1
20→30   解锁 dense 排第 21 的 Q9   → 重排后第 1
30→50   解锁 dense 排第 35 的 Q12  → 重排后第 1
```

★ **瓶颈是【召回】，不是重排质量。** cross-encoder 一看见正确段落就认出来，几乎没有例外。
所以 `未进候选` 那一列**就是** Top-1 的主控变量：**1 道新候选 ≈ 1 点 Top-1**。

**② 逆流：池子越大，被压下去的题也在变多。**

**Q7 是测谎仪 —— `3 → 3 → 4 → 5 → 6 → 7 → 7`，几乎每扩一次池掉一名，从不回头。**

它终于在第 50 名那一档**掉出前 5**：p50 的 `recall@5 = 89%` 而天花板是 93% ——
**差的正是 Q7 这一题。多捞 20 条候选，代价是一道题的 recall@5。**

**③ 冻结：有四题（Q3=5、Q21=2、Q26=3、Q27=2）一旦进池就再也不动，池子多大都一样。**

这是重排器**自己的判断**，和池子无关 ——
它和 bi-encoder 在这几题上**意见一致，而且一致地错**。这类题加池子永远救不了。

**④ 最后两题：捞得进来，但顶不到第 1。**

| 题 | dense 排名 | 进池后 rerank 给它第几名 |
|---|---|---|
| Q13 | 61 | **2** |
| Q5 | 139 | **25** |

★ Q5 排到第 25（在 200 条里）—— **cross-encoder 明确地认为它不是答案**。
它和 ③ 那四题是同一类：不是"没机会"，是"**两个模型一致地不同意评测集的答案**"。

> ⚠️ 这四到六题值得单独看一眼：是不是**出题时**对"正确段落"的认定太窄了？
> 比如答案其实分散在两个 chunk 里，而 `targets` 只登记了一个。
> **这是评测集的问题，不是检索器的问题。** 见 7.3。

### 4.4 ★ 我的预注册：对两个，错两个

跑之前我写死了四条预测。**记在这里，因为错的那两条比对的更有价值。**

| # | 预测 | 实测 | |
|---|---|---|---|
| 1 | rerank@20 Top-1 ≈ 61~64% | **61%** | ✅ |
| 2 | dense 的 14 道 rank-1 里活下来 12~14 道 | **13**（Q2 被降级） | ✅ |
| 3 | pool 继续加**收益递减**，p50 ≈ p20 或略低 | **p50 = 68% > p20 = 61%，单调上升** | ❌ |
| 4 | 兑现率**随 pool 增大而下降** | 0.80 / 0.73 / 0.71 / 0.72 / 0.73 / 0.70 / 0.68 —— **先降后平，最后才降** | ❌ 半错 |

★★ **#2 和 #3 合起来才是真结论：**

我点名的那个机制（**把对的压下去**）**是真的**，Q7 就是活证据；
**但它的量级被另一个更强的机制盖过了** —— 解锁新候选带来的收益远大于压下去的损失，
一直赢到 pool=50。

★ 这正好是 S5-3 那条教训的**镜像**：

> **S5-5**：机制为真（压下去），**整体却是正的**。

我 #3 猜错的原因，就是拿了"机制为真"去外推"整体会变差" ——

### 4.5 pool 取多少：为什么是 50

不是"越大越好"。看三个数：

```
Top-1     : 64%(p30) → 68%(p50) → 68%(p100) → 68%(p200)     从 p50 起【平的】
recall@5  : 89%(p50) → 93%(p100) → 93%(p200)                 从 p100 起【平的】
未进候选  : 3 → 2 → 1 → 0                                     一直在降，但 Top-1 不动
```

★ **p50 → p200 这三档，唯一的收获是 recall@5 从 89% 涨到 93%（Q13 进池后排第 2），
代价是候选数翻 4 倍、Q7 又掉一名。**

★ **这是一个权衡，不是"越大越好"**：

- **选 p50**：Top-1 已经在平台上了，Q13（唯一还差的那题）排在 p50 之外。
- **选 p100**：多拿 1 题 recall@5，候选数翻倍。

**本步取 50**，理由：**在这个语料规模下，Top-1 是主指标，
而 p50→p100 的 4 个 recall 点只来自一题，不值得让每次问答的重排成本翻倍。**

★ **补上成本之后（这是 §4.6 量完才能填的空）**：

```
pool      Top-1   recall@5   重排耗时/题
  20       61%       86%        4.8s
  50       68%       89%       10.6s     ← 取它：+7 Top-1，代价 +5.8s
 100       68%       93%       21.1s     ← +4 recall（一题），代价 +10.5s
```

**p20 → p50 是这三次里唯一划算的一跳**（7 个 Top-1 点换 5.8 秒），
p50 → p100 不划算（1 个 recall 点换 10.5 秒）。

⚠️ 这里有个**差点发生的误判**：在只量到 `batch_size=32` 的时候，
p50 要 **18.3 秒/题**，而 p20 只要 10.8 秒 —— 我当时确实在犹豫
"7 个点值不值 7.5 秒"。**那个两难是被 `RERANK_BATCH_SIZE` 解掉的**（§4.6）：
改完批大小，p50 降到 10.6 秒，比原来 p20 还便宜。
★ 教训：**遇到"质量换速度"的两难，先问一句"这个速度是真的吗"** ——
它可能只是个没调好的默认值。

这是一个**可以反对的决定** —— 如果以后接入的生成模型对"材料里有对的"特别敏感，
或者语料变成几千篇（候选池的边际成本变得可忽略），应该重新量、重新选。
⚠️ 重选的时候**连着 `RERANK_BATCH_SIZE` 一起重量**：
§4.6 的表显示批大小的最优值本身就和 pool 有关（n=100 时最优是 8 不是 4）。

### 4.6 耗时 —— 以及"为什么它不是线性的"

⚠️ **4.5 说"取 50"是拿 Top-1 平了当理由的，没算时间的账。这一节补上时间的账。**
数字没读完之前，**不要把 pool 当成已经定案**。

#### 先看一个被污染的测量

```
重排 20 条候选 → 16~19 秒    ← 测的时候这台机器正被另一轮评测占满 16 个核
```

这个数**不能信**。它唯一的用处是证伪一句话：`rerank.py` 的 docstring 里
原来写着「20 对候选在 CPU 上大约 1~2 秒」—— **那是一句没有实测支撑的断言**。

#### 干净测量的三个条件（本身就是教训）

重排是**纯 CPU** 的，所以任何"别的进程在吃 CPU"都会污染它：

1. **停掉别的重活**（评测脚本、另一个重排进程）。
   我第一轮就是没做这一步，才有上面那个 16~19 秒。
2. **`python -u`（无缓冲）。** 否则进度全堵在缓冲区里，看起来像卡住了 ——
   ★ 我第一次就是这么误判的，**还因此杀掉了一个其实在正常跑的进程**。
   后来用 `python -u` + `flush=True` 才拿到干净数据。
3. **报 best of N，不报第一次。** 第一次含线程池启动和模型预热。

#### 实测（2026-10-12，单进程独占 CPU，torch 2.14.1+cpu，14 线程）

```
预热（2 条）      9.45s                       ← ★ 这个数是本节的第 2 个重点
pool=  5          0.68s        135 ms/条
pool= 10          2.18s        218 ms/条
pool= 20         10.79s        540 ms/条      ← ★ 非单调
pool= 30         15.91s        530 ms/条
pool= 50         18.31s        366 ms/条
pool=100         24.99s        250 ms/条
```

★★ **重点是这两个，不是"20 条 10.8 秒"：**

1. **每条的成本在 135ms ~ 540ms 之间晃，不单调。**
   如果它是"每条固定成本 × 条数"，pool 就是一道除法题。
   它不是 —— 所以 **不许拿"每条多少毫秒"去外推别的 pool**。
2. **预热要 9.45 秒**（模型从磁盘 mmap + 第一次前向）。
   ⚠️ 这一条**直接决定了生产必须把检索器建在循环外**（见 §2.5 / §3.2）——
   否则**每一次问答都要再付一次 9.45 秒**，而且这笔钱花得毫无产出。
   这也解释了为什么模块级缓存要按 `(模型名, 设备, max_length)` 做键：
   **换 max_length 就是换一个模型实例，缓存不能跨**。

#### 为什么不是线性的：两个假设，一个已经被数据否掉

**假设 A：线程超订阅**（14 个物理线程跑 14 个 torch 线程，如果有别的活，
同步开销会随批大小超线性涨）。

→ **否掉了。** 实测：

```
  线程      n=20      n=50     n=100
    14    10.88s    18.46s    25.04s
     8    15.27s    25.52s    35.41s     ← 线程【减半，反而慢 40%】
```

**线程越少越慢**，说明根本没走到超订阅那一步 —— 这活儿是**真算力受限**的。
（4/2/1 没跑完：方向已经明确，继续量没有信息量，**主动停掉去量别的**。）

**假设 B：批内 padding。** `CrossEncoder.predict` 把**一批**补齐到
**批内最长的那条**。于是成本不是"每条多长"，而是
**"批内最长的那条 × 这一批有多少条"**。

→ 这个假设和语料的长度分布**对得上**：

```
1345 条 chunk 的 token 数：中位 54   p90 227   p99 454   max 686
                                     ↑ 只有 5 条（0.4%）超过 512
```

★ 两个直接推论：

- `max_length=512` **几乎从不生效**（只截到 0.4% 的 chunk），
  所以它**不是**耗时的大头 —— 想靠"调小 max_length"省时间，先看下一段。
- 但 **pool 越大，越可能捞进一条 686 token 的长 chunk**，
  于是**整批 50 条都按 512 算**。中位只有 54，却按 512 算 —— **白算约 9 倍**。
  这解释了"池子越大越超线性"：**不是候选多了，是"最长的那个"更容易进池。**

⚠️ 以上是假设 + 分布证据，**不是直接测量**。直接测量见本节末。

#### 直接测量之一：把 max_length 砍小 —— 时间是真的，指标是假的

```
max_length   Top-1    MRR   recall@5    28 题耗时     每题     变了哪几题
       512   67.9%  0.757     89.3%      511.8s    18.3s
       256   67.9%  0.756     85.7%      287.8s    10.3s    Q3: 5→6   Q26: 3→2
       128   75.0%  0.821     92.9%      164.6s     5.9s    Q3: 5→1   Q7: 6→3
                                                            Q21: 2→1  Q26: 3→2
```

⚠️ 上面这三次是**在 `batch_size` 还没调之前跑的**（= 上游默认 32），
所以那一列的绝对值偏大。调成 4 之后 `max_length=512` 只要约 10.6s/题。
**但这里要的是三档之间的【相对关系】，它不受 batch_size 影响** ——
下面会单独量批大小。

★ **511.8 ÷ 28 = 18.3 秒/题**，正好等于前面单题实测的 18.31 秒 ——
所以"单题耗时"那一列**不是特例，就是平均值**（这一条本身是个小验证）。

★ **时间那一列是干净的、单调的**：511.8 → 287.8 → 164.6。
**padding 假设成立** —— 截得越短，白算的假 token 越少。

★★★ **但指标那一列不能信，尤其不能信 `max_length=128` 那行。**
它看起来最漂亮（Top-1 从 67.9% 涨到 **75.0%**，recall@5 涨到 **92.9%**），
**而我决定不采纳它**。三条理由，一条比一条硬：

1. **绝对值太小。** 28 题的 `Top-1 67.9% → 75.0%` 是 **19/28 → 21/28，
   就是两题**。`recall@5` 是 **一题**。用两题去决定一个生产常数，太薄。
2. **★ 变的正好是我已经怀疑尺子的那几题。** `§7.2` 里列过一张
   「两个模型一致地不同意」的名单 —— Q3、Q21、Q26 全在上面。
   **在一个你怀疑 ground truth 可能有问题的题上"涨分"，
   涨的是你和那把可疑的尺子的一致性，不是系统变好了。**
3. **★ 它不单调，而不单调这件事本身就证伪了机制。**
   512→256 时 Q3 是 `5→6`（**变差**），256→128 却是 `6→1`（**变好**）。
   如果"截断掉长尾噪音"是真机制，它应该**单调**地帮忙；
   而我们看到同一个机制先伤人再救人 —— **那它就是噪声，不是机制。**

★ **再叠一层：我一次试了 3 档、取了最好那档。**
28 题上做 3 次比较再挑冠军，**冠军必然偏高**。这不是"发现了 128 更好"，
这是"在三次带噪测量里挑了最大值"。**和 S5-3 那次"最优 RRF 权重 = 0"
是同一类陷阱的镜像** —— 那次是调参调到没收益，这次是挑到假收益。

→ **结论：`max_length` 保持 512。** 不为了 2 题去截断信息。

★ 这一条是本节最该学的：

> **一个指标变好，不等于系统变好。**
> 尤其当它变好的地方，正好是你已经怀疑**尺子本身**不准的地方。

（★ 顺带认个错：上面这段我**先写成了**「长 chunk 里装的是真内容，截断就是丢信息，
所以不是免费的开关」。那是看到 256 那行就下的结论 —— 第 128 行一出来就被推翻了。
**教训不是"别下结论"，是"别在看到全表之前就把机制解释写进文档"。**）

#### 直接测量之二：★ 上游的默认值是为 GPU 调的，对 CPU 正好是反的

既然病根是 padding，第一反应是"**把候选按长度排序再喂进去**"，
让各批各自补齐。**动手前先去读了 `sentence_transformers` 的源码 —— 幸好读了：**

```python
# CrossEncoder.predict 内部（实测版本见 requirements.txt）
length_sorted_idx = np.argsort([-self._input_length(pair) for pair in inputs])
length_sorted_idx = self._interleave_sorted_indices(length_sorted_idx)
...
for start_index in trange(0, len(inputs_sorted), batch_size):    # ★ 默认 batch_size=32
```

★ **上游已经排序了，而且是【交错】排**。`_interleave_sorted_indices` 的
docstring 把意图写得很直白：

> "When text-only inputs are flattened via **flash attention, there is no padding**.
> Total tokens per batch equals the sum of actual lengths. … Interleaving
> (largest, smallest, 2nd largest, 2nd smallest, …) balances the total token count
> across batches for more uniform memory usage."

★★★ **它的前提是「GPU + flash attention ⇒ 没有 padding」。**
在那个世界里，一批的真实计算量 = 各条长度之和，所以要把长短**混开**以免
某一批全是长的（显存峰值 / 负载不均）。

**而我们在 CPU 上跑，padding 是实打实存在的。** 于是
「让每批都混进一个长输入」这个在 GPU 上正确的策略，在 CPU 上等于
**让每一批都按最长的那个补齐**。**上游那个优化，对我们正好是反的。**

★ 一个具体例子（50 条候选、`batch_size=32`）：

```
交错后的顺序 = [最长, 最短, 第2长, 第2短, …]
  第 1 批（32 条）= [l₁, l₅₀, l₂, l₄₉, …]   → 补齐到 l₁     ← 有个最长的在里面
  第 2 批（18 条）= [l₁₇, l₃₄, …]           → 补齐到 l₁₇
```

**每一批都被拉长了，而且是交错故意这么安排的。**

→ 所以真正能动的杠杆**不是排序**（上游占了，而且我们不能轻易改它），
**只剩 `batch_size`**：调小它，交错窗口就变窄，
极端情况 `batch_size=1` 时**每条各自补齐 = 完全没有 padding**（总计算量取到最小）。
代价是丢掉批内的向量化收益。**哪个赢，只能量。**（见下）

⚠️ 顺带记一条教训 —— 这一条和 §2.6「先探 Ollama 有没有 /api/rerank」是同一个病：

> **★ 别凭"这应该很慢"就去重造一个上游已经做过的东西。
>   先去读它到底做了什么。** 这次读了 10 行源码，省掉一个没用的改动。
>   （但读出来的结论是"它的前提和我们不一样" —— 这比"它做了/没做"更有用。）

#### 直接测量之三：★★ 真正免费的加速是 `batch_size`（本步唯一的白捡）

（`max_length=512`，同一个问题、同一批候选，14 线程，best of 2）

```
batch_size      n=20      n=50     n=100
         1     4.92s    11.73s    23.04s
         4     4.80s    10.60s    21.14s     ← n≤50 最优
         8     6.07s    11.74s    20.92s     ← n=100 反而它最优
        16     9.17s    14.68s    23.92s
        32    10.92s    18.92s    29.39s     ← 上游默认值
```

★ **`pool=50` 那一列：18.92s → 10.60s，快 44%，而指标一个字都没动。**

★★ **"指标一个字都没动"不是靠 3 个查询推的，是用官方脚本复核过的。**
改完 `config.RERANK_BATCH_SIZE = 4` 之后重跑
`eval_retrieve.py --kind dense,rerank --expand --pool 50`：

```
检索器                       Top-1     MRR   recall@5   空   未进候选
dense:...:raw +expand          50%   0.605        71%    0        0
dense:...:raw > ce:...@pool50  68%   0.763        89%    0        2
```

**和 §4.2 里那份基线逐位相同**（`0.605` / `0.763` 一个数字都没飘）。
所以这一条是可以写成"**已验证**"的，不是"应该没问题"。

★★ **为什么它是免费的，而 `max_length` 不是 —— 一句话：**

> `max_length` 是**截断**（丢信息，所以有代价）；
> `batch_size` 是**调度**（不参与数学，所以没有代价）。

★ **这不是推理出来的，是量出来的。** 3 个查询 × 50 条候选，
同一个模型、同一批 pair，只换 `batch_size`：

```
max|Δ分|  = 4.2e-07 / 3.6e-07 / 7.2e-07      ← float32 舍入量级
全序一致  = True / True / True                ← 一条名次都没换
```

★ **而且它和 padding 机制【定量】吻合** —— 这才是我相信机制的地方：

```
bs=50（一整批）  → 全部补齐到 512：50 × 512 = 25600 个 token 位
bs=4            → 各批各自补齐，接近"只算真长度"：≈ Σlᵢ ≈ 9000
预测倍数 ≈ 25600 / 9000 ≈ 2.8×
实测倍数 = 26.39s / 10.49s ≈ 2.5×          ← 对得上（bs=4 仍有一点 padding）
```

**一个机制如果只能"定性地说得通"，它可能是编的；能定量对上，才算量过。**

★ ⚠️ **但别把这个 4 当成常数抄走**，两件事绑着它：

1. **它和 pool 有关。** 看 `n=100` 那行：最优是 **8** 不是 4，
   而且收益从 2.3×（n=20）一路收窄到 1.4×（n=100）。
   **换 pool 就要重量** —— 又一次"pool 是系统的一部分"。
2. **它和 CPU 核数有关。** 这是 14 线程上量的。换机器结论可能不同。

→ **所以它进了 `config.RERANK_BATCH_SIZE`，而不是硬编码在 `rerank()` 里。**

#### 4.6 收尾：两条加速路，为什么只走了一条

```
路线                     时间收益     质量代价              决定
max_length 512 → 128      -68%      指标"变好"2 题，但来源可疑   ❌ 不采纳
batch_size  32 → 4        -44%      实测零（全序一致）          ✅ 采纳
```

★ **只学了 44%，没学 68%** —— 因为那 68% 里有一部分是**从答案里省出来的**，
而它表现得像收益，只是因为**尺子本身可疑**（见"直接测量之一"）。

★★ 本步最大的一条认知，两条路对照着看最清楚：

> **两个都能让时间变少。区别不在"省了多少"，
> 在于"省的是白算的部分，还是真内容"。**
> 而**光看数字分不出来** —— `max_length=128` 那一行的数字比 `batch_size=4`
> 那一行**更好看**。要分开它们，只能去读机制、去验证"分数是否真的不变"。

### 4.7 可复现性

`pool=50` 在两轮**独立进程**里各跑了一次，**逐题排名完全一致**（`main[50] == ext[50]` → `True`）。

★ 这一条要单独记，因为本项目有一个**已知的不可复现问题**
（`probe_cite.py` 的诱导成功率 1/8 → 5/8，见 S5-0 第 7.5 节）。
**重排这条链是可复现的**（`temperature` 无关，模型确定性推理），
所以它上面做的对比是可信的 —— 而 `probe_cite` 那边不是。

### 4.8 ★ 我自己量的时候，差点又造出第二把尺子

量 §4.6 的时候我写了个一次性脚本，顺手在里面实现了 `metrics()`。
结果 `max_length=512` 那档它报 **MRR 0.757**，而记录里 §4.2 的表是 **0.763**。

★ 差在哪，值得写下来：

```
仓库里的那把尺子（scripts/eval_retrieve.py:219）
    mrr = sum(1/r for r in ranks) / n_q        # 找不到的题 r = all_k + 1 = 51
                                               # 排第 7 的题照样贡献 1/7

我临时脚本里的那把
    if pos is not None and pos <= TOP_K:       # ← 只在 pos<=5 时加分
        mrr += 1.0 / pos                       # 排第 7 的贡献 0，找不到的贡献 0
```

**同一个名字（MRR），两个定义，而且两个都有道理。** 我的那把其实更像
"前 5 命中率 × 排名质量"，仓库那把才是标准 MRR。

★ 这件事的病根**不是**"我算错了"，是**"我又手搓了一把尺子"**：

- 这跟 S5-1（query 前缀）、S5-2（查询扩展开关）是**同一个病的新变种** ——
  那两次是"生产"和"评测"各一份实现，这次是"评测"和"临时脚本"各一份。
- 它**不会报错**，两把尺子都算出合理的数，只差 0.006。
  如果我这次没有恰好拿它去对 §4.2 的表，**这个 0.757 就会被我写进记录**，
  而它和 0.763 讲的是两件事。

→ **规矩：量的时候先问「仓库里有没有现成的这把尺子」，有就调它。
  没有，才允许临时写 —— 而且写完要拿一个已知答案去校。**

（Top-1 和 recall@5 两把尺子的定义没有歧义，所以那两个数对上了：
67.9% vs 68%、89.3% vs 89%。**对上了的是它们，不是 MRR。**）

## 5. 你要补的概念

### 5.1 bi-encoder vs cross-encoder

| | bi-encoder（dense 检索） | cross-encoder（重排） |
|---|---|---|
| 输入 | query → 向量；正文 → 向量 | `[query + 正文]` **拼成一个序列** |
| 两者见面吗 | ❌ **从头到尾没见过面** | ✅ **在模型的每一层互相 attend** |
| 能预计算吗 | ✅ 语料向量建索引时算好 | ❌ **正文的表示依赖于 query** |
| 复杂度 | 一次问答 = 1 次编码 | 每条候选都要跑一遍模型 |
| 用于 | 全库粗排 | 少数候选精排 |

★ **"不能预计算"是 cross-encoder 的全部代价，也是它必须配一个粗排的原因。**
1345 条全跑一遍不现实，只跑 50 条就很划算。这就是"先粗排、再精排"的分工。

### 5.2 召回（recall）和排序（ranking）是两件事

一个检索系统有**两个独立的失败模式**：

```
召回失败：正确答案压根不在候选池里      → 修法：扩池、改索引、改嵌入模型
排序失败：正确答案在池里，但排得靠后    → 修法：重排
```

★ **它们必须分开量，因为修法完全不同。**

本项目为此专门加了一列 `未进候选` —— 它**只数召回失败**。
把它和 `空`（一条都没返回）分开，也是同一个道理。

**一个系统同时有这两种病时，单一指标（比如 MRR）会把它们糊成一个数，
然后指向错误的修法。** 这是 S5-0/S5-2 那条教训的第三次发作。

### 5.3 「天花板」是可以在动手之前算出来的

```
天花板(pool) = 有多少题的正确答案本来就在前 pool 名里 = recall@pool
```

★ 这个量**不依赖重排器**，只依赖粗排。所以：

**在写重排代码之前，就能知道它最好能做到多少。**
如果 recall@5 只有 40%，那"把 pool 设成 5 然后上重排"的最好结果是 40% ——
**连试都不用试。**

> 推广：**动手前先算"完美情况下能做到多少"。**
> 如果天花板本身就很低，那你要修的**不是**你正准备修的那个东西。

### 5.4 `pool` 是系统的一部分，不是调参旋钮

同一个模型、同一批题，`pool=5` 和 `pool=50` 是**两个不同的系统**：

| | pool=5 | pool=50 |
|---|---|---|
| Top-1 | 57% | 68% |
| 延迟 | 5 对 | 50 对 |

★ 所以 **`config.RETRIEVE_POOL` 必须和 `TOP_K` 一样被生产路径读**。
如果它只活在评测脚本里，评测量的是"捞 50 排 5"，而生产跑的是"捞 5 排 5" ——
**这正是 S5-1（query 前缀）和 S5-2（查询扩展）犯过的同一个病，第三次就在眼前。**
（所以 `build_retriever()` 放在产品里，`pool` 从 config 读。）

### 5.5 对象生命周期：什么时候建、建几次

`ask()` 里那行 `DenseRetriever(...)` 以前是**每次调用新建**的 —— 那时无所谓，
因为它只是包了一下已有的向量，构造成本接近零。

**接上重排之后，同一个形状变成了一个 2.3GB 的坑。**

★ 这是重构里很典型的一类问题：**一段无害的代码，因为依赖的东西变了，变得有害。**
解药不是"小心一点"，是**把"什么时候建"变成调用方必须显式回答的问题**（依赖注入）。

### 5.6 一个指标的「定义域」决定它能不能用

`未进候选 > 0` 时，"平均排名"这个量的**定义域**是坏的 ——
它要拿一个真实的排名和一个哨兵值（`all_k+1`）做平均。

```
这就是为什么 4.3 里那两列会【方向相反】：
    一个是"包含了哨兵值的平均"
    一个是"只在有效值上的平均"
两者量的根本不是同一个东西。
```

★ **一条通用检查：把哨兵值（`-1` / `None` / `1346`）混进数值统计之前，先问
"这个平均值在说什么？"** 通常答案是"什么也没说"。

## 7. 遗留 / 下一步

### 7.1 ⚠️ 检索指标 ≠ 答案质量（本步最大的诚实缺口）

**本步量的全是检索指标。** Top-1 涨了 18 点，**不等于"答对的题多了 18 点"**。

生成那一层（Stage 3 的拒答、Stage 4 的引用校验）**一次都没重跑过**。

★ 下一步应该是**端到端评测**：同一批 28 题，跑 `ask()`，看
`status` 分布和引用校验通过率，对比开/关重排两组。
**这是唯一能回答"用户是不是真的更满意了"的量法。**

### 7.2 ⚠️ "四到六题两个模型一致地不同意" —— 该回头查题了

Q3、Q21、Q26、Q27（冻结），Q5、Q13（进池也顶不上来）。
**cross-encoder 和 bi-encoder 在这些题上意见一致，而且一致地错。**

两种可能，**必须先分清**：

1. **评测集的问题** —— `targets` 登记得太窄。答案可能分散在多个 chunk 里，
   或者正确的 chunk 换了，而 `targets` 没跟着更新。
2. **真的难** —— 两篇论文讲同一件事，正确答案确实不好认。

★ 如果是 (1)，那**当前所有基线数字都偏低而且偏低得不一样** ——
因为这六题在不同 pool 下被计分的方式不同。**这是当前最该查的一件事。**

### 7.3 ✅ 已办：`rerank.py` docstring 那句编造的耗时断言换掉了

原来是「20 对候选在 CPU 上大约 1~2 秒 —— 够用」。**实测是 10.8 秒，差一个量级。**
这句话的病不在于数字错，在于**它没有任何测量支撑却写成了断言**
—— 和 config 里那三条被删掉的绝对坐标阈值是同一类东西（见 config.py 的注）。

★ 换掉的时候**顺带改掉了另一个错**：原句把耗时归因于
「批大小和线程同步在打架」。线程实验（§4.6）**否掉了这个解释**
（14 → 8 线程反而慢 40%）。**一个没有实测支撑的机制解释，
和一个没有实测支撑的数字，是同一种毛病** —— 而且机制解释更危险，
因为它听起来像懂了。

### 7.4 pool 的取值是一个【可反对的决定】，不是定论

见 4.5。选 50 而不是 100 是基于"Top-1 已是主指标"这个判断。
**接入生成评测（7.1）之后应该重新量一遍。**

⚠️ 重量的时候**必须连着 `RERANK_BATCH_SIZE` 一起重量** ——
§4.6 的表显示批大小的最优值和 pool 是绑着的（n=20/50 时最优 4，
n=100 时最优 8）。两个常数各自都"量过"，但**合起来的最优不是各自的拼接**。

### 7.5 仍未验证：`--kind bm25` 粗排 + rerank

现在 `rerank` 分支固定用 dense 粗排。**"BM25 粗排 + rerank" 是另一个实验**
（BM25 单独只有 32%/54%，粗排质量更差，但错误可能更不相关 ——
而 S5-3 说过，融合类方法要的是**错误不相关**）。
`make_retriever()` 里留了注释，要试得单独加一个 kind。

### 7.6 ⚠️ `max_length=128` 那个"更好的数字"，修好 ground truth 之后要重测

见 §4.6「直接测量之一」。它在 28 题上把 Top-1 从 67.9% 抬到 75.0%，
而**本步决定不采纳**（就 2 题、集中在可疑题上、且不单调）。

★ 但**"不采纳"不等于"它是错的"**。有三种可能，本步**分不开**：

1. 它是噪声（我倾向这个，理由见 §4.6）。
2. **它是真的**：长 chunk 的尾部噪音确实会压低 cross-encoder 的打分，
   而 bge-reranker 的训练分布本来就偏短片段 —— 那截断就是**对的**。
3. 它是**对着一把坏尺子过拟合**：截断后模型更偏向那几道题的错误 target。

**分清这三条的唯一办法，是先把 §7.2 那几道题的 `targets` 核一遍。**
在那之前，`RERANK_MAX_LENGTH` 保持 512。
★ 这也是为什么它进了「遗留」而不是「结论」——
**一个没被采纳的测量结果，只要条件变了就可能翻案，得留个牌子。**

### 7.7 本步新暴露的两条

- **⚠️ `RETRIEVE_POOL` 的值差点没回写。** `build_retriever()` 确实防住了
  「pool 只活在评测脚本里」（§3 的规矩 #1 第三次发作被挡下），
  **但挡的是"路径"，不是"值"** —— 决策定在 50，而 `config.RETRIEVE_POOL`
  收尾时还写着 20。于是**记录和 ROADMAP 说生产是 `@pool50`，
  实际跑的是 `@pool20`**。同一类病换了个入口又进来一次。
  ★ 教训要升级一句：**"只有一个来源"不够，还要"这个来源被回写过"。**
- **⚠️ 生成那半边的延迟从来没量过。** `data/logs/paper_rag.log` 里
  **一行耗时都没记**。所以「每次问答要多久」这个用户唯一真正在意的问题，
  本步只能答一半（重排那半）。见 7.1 的端到端评测 —— 量的时候顺手把
  `ask()` 的分段耗时打进日志，否则下一次还是答不上来。
