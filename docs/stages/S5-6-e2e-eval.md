## 1. 改了什么

### 1.1 三个 arm，不是两个

| arm | 是什么 | 为什么必须有 |
|---|---|---|
| `dense` | 关掉重排 | **控制组**。只跑生产配置的话，「合规率 85%」没有参照系 |
| `rerank` | 生产配置 | 被检验的对象 |
| `oracle` | ★ 把**标准答案**直接当检索结果喂下去 | 把**检索层**和**生成层**切开 |

**为什么两个 arm 不够** —— 这是本步最重要的设计决定：

```
    只看 dense vs rerank：
        rerank 合规率 82%，dense 合规率 71%
        → 剩下 18% 是检索没捞到？还是捞到了模型没用好？
        → 说不清，而且【修法完全不同】

    加了 oracle：
        oracle 合规率 88%   ← 检索满分时，生成层也就到这儿
        → 88% 到 100% 的那 12 点是【生成层的天花板】
        → rerank 的 82% 对 oracle 的 88% 差 6 点，这才是【检索层的锅】
```

### 1.2 `OracleRetriever` —— 一个满足 `Retriever` 协议的假货

`scripts/eval_answer.py:118` 起。它只有两件事：`name` 和 `search`。

★ **它一个字都不用改 `ask()` 就能接进去** —— 这是 S5-1 那个 Protocol 判断的
**第三次兑现**：

| 换的是什么 | `ask()` 改了没有 |
|---|---|
| dense → bm25 | 没有 |
| + RerankedRetriever | 没有 |
| → 一个**作弊的假货** | **还是没有** |

★ 它是**评测专用**的作弊器，真上线不可能有这种东西 ——
所以它待在 `scripts/` 而不是 `paper_rag/`。

### 1.3 判卷表是**盲**的

`write_judge_sheet()`。同一道题的几个 arm **逐题重新打乱**，编成「甲/乙/丙」。

- **为什么不盲不行**：看到答案之前就知道哪个是"新方法"，然后不自觉地宽容它。
  这不是道德问题，是人脑的默认行为。
- **为什么逐题打乱**（而不是全局固定一个顺序）：
  全局固定的话，判到第 5 题你就会发现「甲总是同一个 arm」，盲就破了。
- **种子写死**（`--seed 20261013`）：判卷表要能重现。种子随机会让
  「同一份结果生成两次得到两张不同的表」，你就没法确认自己填的是哪一张。

### 1.4 `used` 的下标转换

`scripts/eval_answer.py:246` 附近：

```python
cited_target = any(
    0 < u <= len(material_ids) and material_ids[u - 1] in targets
    for u in used
)
```

★ `used` 装的是**材料编号（从 1 开始）**，不是 chunk_id（见 `generator.build_prompt`
的契约）。所以这里要 `-1` 转成下标。

⚠️ **写错了不会报错** —— 只会静默全判 `False`，然后你会得到「模型从不引对材料」
这个看起来很严重的结论。这是本项目第四次遇到「安静的错误」这一类。

## 2. 为什么这么写

### 2.1 为什么 `temperature=0`

`GEN_OPTIONS = {"temperature": 0}`。

检索是**确定性**的，生成不是。**这一条在生成这半边比在检索那半边重要得多** ——
忘了传，整张表都是噪声，而且你会把它当成「模型不稳定」而不是「我漏了个参数」。

### 2.2 为什么"合规回答率"这个列**故意起这个名字**

它**不叫**"正确率"，因为 `status=answered` + 引用校验通过
**只说明**「交付了一个有据可查的答案」。

模型完全可以引用一段**真材料**，然后从中推出一个**错的结论**。
引用校验只保证引文没伪造，**不保证结论正确**。

★ 名字起错，读表的人就会拿它当正确率用 —— 这就是 S5-5 §7 那条
「★ 名字即契约」的又一次应用。

### 2.3 为什么不用 qwen2:7b 自己判"答对了吗"

两个理由，第二个更根本：

1. **自评偏好**（self-preference）—— 同一个模型判自己的答案会系统性偏高；
2. **更根本**：那样你就有了**两把没校准过的尺子** —— 一把是它答的，
   一把是它判的，两个都不知道准不准。

本项目已经栽过三次「手搓第二把尺子」：

| 哪一步 | 手搓的是什么 |
|---|---|
| S5-1 | query 前缀只活在评测脚本里 |
| S5-2 | 查询扩展：评测没开、生产开着 |
| S5-5 | MRR 的定义（我的脚本 0.757 vs 仓库 0.763） |

这次**连模型都不信**。

### 2.4 为什么 oracle 要 pad 到 k 条

有些题只有 1 个 target。直接只喂 1 条材料的话，prompt 里的材料数就和别的 arm
不一样了（别的 arm 都是 k=5 条）—— **那 prompt 本身就变了，比的就不是同一件事**。

所以：target 排最前，剩下的空位用 dense 的结果补齐（去掉重复）。

## 3. 不应该怎么写

### 3.1 ❌ 只跑生产配置，看到 82% 就收工

**症状**：你得到一个没有参照系的数字。82% 是好还是坏？不知道。
**而且更危险的是**：你会拿它去和别的配置的 82% 比，而那两个 82%
可能一个来自检索好+生成差，一个来自检索差+生成好。**同一个数，两种病，两种药。**

### 3.2 ❌ 让生成模型兼任判卷人

**症状**：表格很好看，而且**看起来很有说服力**（因为它有条理、有理由）。
你甚至能从它的解释里学到东西 —— 但那不是校准过的测量，是**一次很有文采的猜测**。

### 3.3 ❌ 判卷表不给盲

**症状**：结果"符合预期"。你会觉得是方法有效，
其实是你**先知道了答案再打分**。这个偏差**不会以任何形式报警** ——
它只会让你的结论总是恰好支持你原本的想法。

### 3.4 ❌ 把「合规回答率」当成「正确率」写进结论

**症状**：报告里写「正确率 82%」，实际上那是「有引用且引文没伪造率」。
**数字是真的，标签是假的。** 而假标签会被下游的人当真 ——
ROADMAP 上那个「Top-1 68%」就是这么来的（它是个真的检索指标，
但**没人会知道它跟"答对"差多远**，因为一直没人量过）。

### 3.5 ❌ 在循环里调 `ask()` 不传 `retriever`

**症状**：评测"突然变得很慢"。不报错、不警告。
每题重建一次检索器 = 每题重排器构造一次 + 第一次前向的预热 ~9.5s。
S5-5 已经量过这条，本步是第一个会**真的踩到**它的地方（28 题 × 3 arm）。

## 4. 怎么验证它真的对了

### 4.1 冒烟（已做）

`--arms oracle --limit 2` → 桥通、`OracleRetriever` 对得上号、判卷表生成正常。

★ 顺带撞到第一个真数据点：**oracle 第 1 题（RotatE）材料里明明有答案，
引用校验却没过。** 这就是"桥通了但交付失败"—— 生成层的病，
修检索没用。留着看它在全量里是孤例还是常态。

### 4.2 复现检查（**不是**新结论）

`材料含答案率` 这一列，dense 应当 ≈ 71%、rerank 应当 ≈ 89% ——
**这跟 S5-5 的 recall@5 是同一个量**，只是换了条路算出来。

★ 它俩对不上，说明**有一条路算错了**，而不是"发现了新东西"。
这是本步的**自校验**：先确认新尺子和老尺子在同一段量上读数一致，
再去信它在**新**那段量（答案质量）上的读数。

### 4.3 ★★★ 汇总表 —— 这就是本步的答案

**28 题 × 3 arm，`temperature=0`，`k=5`，`+expand`：**

| arm | 材料含答案（检索层） | **合规回答（答案质量）** | answered | 拒答 | 可疑 | 解析失败 | 引用有问题 | 引对材料 | 秒/题 |
|---|---|---|---|---|---|---|---|---|---|
| `dense`（控制组） | 20/28 = **71%** | **22/28 = 79%** | 23 | 1 | 1 | 3 | 1 | 17/20 | 1.3 |
| `rerank`（= 生产） | 25/28 = **89%** | **22/28 = 79%** | 26 | 2 | 0 | 0 | 4 | 23/25 | 13.3 |
| `oracle`（检索满分） | 28/28 = **100%** | **23/28 = 82%** | 27 | 0 | 0 | 1 | 4 | 23/28 | 1.3 |

#### ★★★ 一句话结论

> **检索指标涨了 18 点（71% → 89%），答案质量一点没动（79% → 79%）。**

配对检验（McNemar，同一批 28 题）：

```
    合规回答   : dense → rerank    b=2  c=2   p=0.617   ← ★ 换了 2 题，净变化 0
    材料含答案 : dense → rerank    b=1  c=6   p=0.131
```

★ `b`/`c` 是**哪两题**（这个比百分比有用得多）：

```
    合规回答 rerank 变好: Q9（dense 拒答 → rerank 合规）
                         Q24（dense 解析失败 → rerank 合规）
    合规回答 rerank 变差: Q10（dense 合规 → rerank 拒答 ← ★ rerank 这题【桥通】，还是拒答了）
                         Q26（dense 合规 → rerank 引用有问题）
```

★★ **这四次翻转全部发生在【生成层】，跟检索没关系。**
Q10 尤其刺眼：rerank **把正确材料捞进来了**（桥通），模型却拒答了。

#### 误差分解（本步加 oracle 的全部意义）

```
    总损失（28 题里 6 题没交付干净）
        │
        ├── ① 检索层丢掉的 ────────── dense: 8 题   rerank: 3 题
        │      （材料含答案 = False，接不上 oracle 那条路）
        │
        └── ② 生成层丢掉的 ────────── 就算检索满分，也只有 82%
               （oracle 自己就丢了 5 题）
                    ├─ 引用有问题 4 题（见 4.6：其中 2 题是 prompt 的锅）
                    └─ 解析失败   1 题（见 4.6 下方：模型【答对了】，JSON 坏了）
```

★★ **② 比 ① 大。** 换掉整个检索器（dense → rerank）没能动的东西，
换成"检索满分"（oracle）也只动了 3 点（79% → 82%，p=1.000，**分不出来**）。

> **换句话说：在这个系统当前的状态下，瓶颈不在检索。**
> 而在此之前，这个项目所有的优化（S5-1 ~ S5-5）**全都在检索那一侧**。

#### ⚠️⚠️ 但是 —— 这张表**撑不起**比它更强的结论

必须同时说清楚，否则上面那段就成了过度解读：

1. **n=28，80% 附近的 95% 区间是 ±15 点**（见 4.5）。
   「79% = 79%」的准确读法是「**这两个数在噪声里无法区分**」，
   不是「它们精确相等」。
2. ★ **连检索那 +18 点，配对检验也只有 p=0.131**（b=1, c=6）。
   它是**这 28 题上的确切计数**（不带测量噪声），
   但"能不能推广到别的题"——28 题给出的证据是**弱的**。
3. **"合规回答"不是"答对"**（见 2.2）。这一列里混着
   「答对了但引文抄坏了」（如 Q1/Q6）和「真答错了」。
   **真正的答案质量在第 4.8 节的判卷表里，还没人填。**

> ★ 所以本步**能站住的**最强说法是：
> **没有证据表明答案质量跟着检索指标一起涨了 18 点。**
> 而不是「答案质量一定没涨」。

### 4.5 ★★ 噪声地板 —— n=28 量不出本步最想量的那个差异

在 reporting 之前，先算**这台仪器的分辨率**。

```
    某条线在 80% 附近时，n=28 的 95% 区间是 ±15 点
    →  79%、82%、85% 这三个数，在 28 题上【是同一个数】

    想分辨到 ±5 点，需要 n ≈ 246 题
    想分辨到 ±3 点，需要 n ≈ 683 题
```

`scripts/eval_answer.py` 里的 `print_noise_floor()` 就是干这个的，
用的是**配对 McNemar 检验**（不是两组独立比例的比较 —— 同一批 28 题各测两次，
是配对数据；把它当独立样本会算错显著性）。

#### 这个数字怎么读 —— 它**不**否定 S5-5

★ 别把它读成"前面都白干了"。分清楚：

| 量 | n=28 上能不能分辨 |
|---|---|
| `材料含答案率`（= recall@5） | ✅ 能。71% → 89% 是 18 点，而且它是**确定性**的检索计算，不带抽样噪声 |
| `合规回答率`（答案质量） | ❌ **不能**。差异全在 ±15 点里面 |

★★ **所以本步的诚实结论不是"检索指标和答案质量脱节"，而是：**

> **在 28 题上，答案质量的差异【小到量不出来】——
> 而这本身就是答案。**
>
> 它说明「检索涨 18 点 ⇒ 答案质量涨 18 点」这个直觉**不成立**：
> 如果答案质量真的跟着涨 18 点，28 题是**足够**看见的（±15 的区间挡不住 18）。
> 现在看不见，就说明它没涨那么多。

★ 这是一个**否定性证据**，而否定性证据在 n 小的时候是弱证据 ——
所以准确说法是「**没有证据表明它涨了 18 点**」，
不是「它一定没涨」。要收紧，得加题。

#### 这一条其实早就该算了

S5-3 把题从 12 道加到 28 道时，理由是「7 篇论文要全覆盖」。
**没人算过 28 题能分辨多大的差异。** 当时够用，
是因为当时量的是**检索指标**（18 点那种大差异）；
换成答案质量（本来就是几个点的差异）之后，28 题**立刻不够了**。

> **样本量不是一个"越多越好"的常数，它取决于你要分辨的效应有多大。**
> 换指标 = 换效应量 = 可能就得重新算样本量。
> 这条和 config 里那句「不要写绝对坐标」是同一族：
> **凡是写死的阈值，都要问一句"它是在什么前提下定的、那个前提还在吗"。**

### 4.6 ★★★ 「引用有问题」不是一种病，是**四种**

**这是本步挖出来的最值钱的东西**，而且它差点被我漏掉 ——
脚本第一版**没存 `quotes`**，只存了 `cite.verify` 报出来的那句
「引用 [N]：原文中找不到对应内容（疑似伪造）」。跑到第 7 题时我才发现，
于是停掉重写（代价约 2 分钟，值）。

把引文原文打出来，逐条回全语料里找，五种情况分开了：

| 题 | 引用 | 表面症状 | 真正发生了什么 | 该修哪 |
|---|---|---|---|---|
| Q1 | [1] | 疑似伪造 | 引文**完全正确**，只是前面多了个 `[1] ` 前缀 | **prompt** |
| Q6 | [1] | 疑似伪造 | 同上 | **prompt** |
| Q8 | [2] | 疑似伪造 | `65.31%` 那段**全语料里不存在** | 模型（真幻觉） |
| Q17 | [1] | 疑似伪造 | 内容真的存在，**编号数错了**（实际在 [2]） | 模型 |
| Q17 | [3] | 疑似伪造 | 引文全语料不存在 | 模型（真幻觉） |

**同一个字符串「疑似伪造」，背后是三种完全不同的东西。**

#### 那个 `[N] ` 前缀是哪来的 —— 我们自己埋的

`generator.build_prompt()` 给材料的排版是：

```
[1] 《论文标题》 / 章节 / 第 3 页
    正文正文正文……
```

而示例 JSON 写的是：

```json
"quotes": {"1": "材料1里的英文原句，逐字复制"}
```

★ **模型看到材料以 `[1]` 开头，就把 `[1] ` 一起抄进了 values。**
它做的是"逐字复制"—— 只是它理解的"材料 1 的原文"**包含了那个我们自己加的表头**。

**验证**（这一步是判定的关键，不能靠猜）：

```
去掉 "[N] " 前缀后 → cite._norm(引文) 是 cite._norm(材料) 的子串 → True
```

★ 修法有两条，**而且必须选一条，不能两条都做**：

1. **改校验**：`cite.verify` 容忍开头的 `[N]`（剥掉再比）；
2. **改 prompt**：明确告诉模型「quotes 里【不要】写 `[1]` 这个编号，只写句子本身」。

> ⚠️ 两条一起做会造出**第二条尺子** —— 校验放宽了、prompt 也改了，
> 下次再出问题你分不清是哪边在兜底。

★★ **本步【不修】。** 理由：
> 这张表量的是**现在这个生产系统**，而它**确实有**这个毛病。
> 现在改掉它，我就得重跑一遍才有一致的数字 ——
> 那这一"步"里就混进了两个改动，说不清是哪个带来的变化。
> 留到下一步，**改前改后各量一次**，那个对比本身就是记录。

#### 方法论教训（比这条 bug 重要）

> **评测记录必须留下「原始证据」，不能只留「判定结果」。**

`problems`（判定）是有损压缩：它把「前缀 / 数错编号 / 真幻觉」压成了一个布尔。
**有损压缩是不可逆的** —— 你没法从「疑似伪造」反推出是哪一种。

| 留什么 | 性质 | 能不能反查 |
|---|---|---|
| `n_problems > 0` | 判定 | ❌ 四种病糊成一个数 |
| `problems` 文本 | 判定 + 位置 | ❌ 知道是哪一条，不知道为什么 |
| **`quotes` 原文** | **证据** | ✅ 可以自己去比 |

★ 这和 S5-5 那条「**别写没量过的断言**」是同一族：
**凡是把信息压掉的地方，都要先问一句「以后还取得回来吗」。**

### 4.7 「桥断」也分两种 —— 而它们**只有一种**能靠加大 pool 治

`材料含答案 = False`（桥断）这个布尔，同样糊了两种病。
把 dense 的**全量排名**挖出来看：

| 题 | target 在 dense 全量里的排名 | 进了 pool=50 吗 | 桥断的原因 |
|---|---|---|---|
| Q5 | **287** / 139 | ❌ 没有 | **粗排**根本没捞到 |
| Q13 | **61** | ❌ 没有 | **粗排**没捞到（S5-5 记：pool=100 才进） |
| Q7 | **4** | ✅ 进了 | ★ **重排**把它从第 4 压出了前 5 |

★★ **这是两种病，而修法只有一个方向重叠：**

```
    粗排没捞到  →  只能加大 pool（或换更好的粗排）
    重排压下去  →  加大 pool 一点用都没有（它本来就在池子里）
```

★ 顺带对上了一笔账：S5-5 记的「rerank@pool50 **未进候选 = 2**」，
正好就是 Q5 和 Q13 —— **两个独立的量法给出同一对数**，
这又是一次 §4.2 那种自校验。

★ 这也解释了 Q7 的「重排后反而掉出去」为什么**不是矛盾**：
cross-encoder 是在**候选内部**比大小，它不知道全量里排第 4 ——
它只知道自己看到的那 50 条里谁更像答案。**换了个池子，就是换了个问题。**

## 5. 你要补的概念

### 5.1 ★★ 中间指标（proxy）与出口指标

这是**本步唯一的中心概念**，其余都是它的推论。

```
    出口指标：用户拿到的那句话对不对        ← 你真正想优化的
    中间指标：Top-1 / recall@5 / MRR        ← 你能自动算的
```

工程上你几乎**永远**在优化中间指标，因为出口指标要人判、贵、慢。
这没问题 —— **但你必须知道两者之间隔着多远**，否则你就是在
「朝着一个和目标不重合的方向使劲，而且越使劲越自信」。

| 中间指标 | 它离出口有多远 |
|---|---|
| 检索 Top-1 | 还要过生成层才能到出口 |
| 生成的「合规率」 | 还要过人判「对不对」才到出口 |
| **答案对错** | 就是出口 |

★ **本步的全部意义**：第一次量出「Top-1 → 出口」这一段的**传递率**。
在此之前，ROADMAP 上那个「Top-1 68%」是个**孤零零的数字** ——
它看起来像成绩，但你不知道离"有用"还有多远。

> 一句话记法：**中间指标决定你往哪走，出口指标决定你走到了没有。**
> 只有中间指标的项目，会在指标涨的时候**越来越确信**，而不是越来越对。

### 5.2 控制组 —— 为什么"一个数字"不是实验

`dense` arm 存在的唯一理由：**给那个数字一个参照系**。

- 只有 `rerank`：得到 82%。**82% 是什么？** 无从判断。
- 有 `dense`：得到 dense 71% / rerank 82%。**差 11 点**，这才是信息。

★ 这是科学方法里最基础的一条，但在工程里**天天被违反** ——
因为加个控制组要多跑一遍，而"多跑一遍"永远排在"赶紧出结果"后面。

### 5.3 ★ oracle 上界 —— 用「作弊」划出某一层的天花板

`oracle` arm 把标准答案直接喂给生成层。它**不是**一个候选方案，
它是一个**测量工具**：它回答「**把检索换成完美的，这个系统能到多少**」。

这是误差分解的标准手法，也是本步能切开"是谁的锅"的唯一原因：

```
    ┌─────────────────────────────────────────────────┐
    │  检索层             生成层                        │
    │  ────────►──────────►────────►                   │
    │  ①丢掉答案    ②材料里有答案但没用对   ③交付格式没执行 │
    └─────────────────────────────────────────────────┘
         ↑                    ↑                    ↑
      1−材料含答案率     oracle 的上限差      引用校验那一列
```

★ **同一个 S5-5 就用过这个手法**：`天花板(pool) = recall@pool` ——
「完美重排能到多少」只依赖粗排，不依赖你正要写的东西。
**先算上界，再决定要不要动手**，是这两步共同的方法论。

### 5.4 误差分解 —— 总误差不是各层误差的相加

直觉上「检索错 10% + 生成错 10% = 错 20%」，**这是错的**：

- 检索丢掉的那 10% 题里，生成层**本来就答不对**的那部分，丢掉也没差（重叠）；
- 检索错的题，生成层有时能**用别的材料蒙对**（补偿）；
- 反过来，检索多了几条干扰材料，还会**把本来对的题带错**（负作用）。

★ 所以分解必须**量**，不能推。`oracle` 和 `rerank` 的差是量出来的，
不是 1−89% 算出来的。

### 5.5 盲法与自评偏好

- **自评偏好（self-preference）**：模型判自己的输出会系统性偏高。
  原因和人不远 —— 它认得出自己的风格，而"熟悉"会被误当成"正确"。
- **盲法（blinding）**：判卷人不知道哪个是哪个 arm。
  不盲的偏差**不会以任何形式报警**，它只会让你的结论**总是恰好支持你原本的想法**。

★ 这两条合起来是一条工程纪律：**评判者不能和被评判者有利益关系**，
哪怕"利益"只是"这是我自己写的方法"。

### 5.6 「两把尺子」—— 复现检查为什么不是走过场

本步的 `材料含答案率` 和 S5-5 的 `recall@5` 是**同一个量**，
只是从两条完全不同的路算出来（一条在检索器内部、一条在流水线出口）。

> **两者对不上，第一反应必须是「有一把尺子错了」，而不是「发现了新东西」。**

★ 这是本项目第 4 次遇到同类问题（S5-1 query 前缀 / S5-2 扩展开关 / S5-5 MRR 定义）。
所以这次把它**主动做成了一道自校验**：先用新尺子量一个**已知答案**的量，
对上号了，才去信它在**未知**量上的读数。

> 一般化的说法：**新仪器上线前，先测一个已知量。**
> 你造了一把新秤，第一步是拿它称一个标着 1kg 的砝码，不是称未知的东西。

### 5.7 分母的选择（一个容易犯的统计错误）

`引对材料` 的分母是「**材料里真有答案的题数**」，不是总题数。

为什么：材料里压根没有答案的题，"没引对"是**检索的锅**，
不该算到模型的引用行为上。用总题数当分母，你会把检索的问题**记在生成头上** ——
然后去改 prompt，改不好，还找不到原因。

> **每一个比率，问三件事：分子是什么、分母是什么、分母里的人该不该在这儿。**
