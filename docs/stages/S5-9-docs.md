## §0 这批文档在项目里的位置

文档不在数据流上，但它有**依赖方向**，而且和代码是同一条：

```
  给【外来者】      README.md            5 分钟：这是什么 / 怎么跑起来
       │
       ▼
  给【接手者】      docs/ARCHITECTURE.md  数据怎么流 / 接口怎么定 / 失败怎么分
       │
       ▼
  给【决策者】      docs/ROADMAP.md       做到哪了 / 下一步 / 踩过哪些系统性坑
                    docs/PROJECT_REVIEW  这个项目做得怎么样（快照 - 复核）
       │
       ▼
  给【学习者】      docs/LEARNING_LOG.md  逐日过程
                    docs/stages/*.md      每小步的开发记录 ← 本文件
```

**越往上越短、越稳定；越往下越长、越容易过期。**
所以「哪份该更新」有一个机械判据：**改的东西会让哪一层的读者做出错误决定？**

- 换模型名 → README（他会拉错模型）+ ARCHITECTURE（决策表）
- 涨了数字 → README（数字表）+ ROADMAP（基线）
- 改接口 → ARCHITECTURE（接口节）
- 只改了某个常量 → `config.py` 的注释（它本身就是决策日志），文档不用动

## §2 为什么这么写

### 2.1 README 第一屏必须是「能跑的命令」，不是架构图

先说清楚**这是给谁的**：一个 clone 下来、5 分钟内想知道「这东西值不值得读」的人。

他的问题顺序是固定的：

```
  这是什么？ → 能跑吗？ → 要准备什么？ → 跑出来什么样？ → 有什么坑？
```

所以 README 的顺序是 **能力 → 架构（压缩版）→ 快速开始 → 数字 → 边界**。
架构图放在第 2 节，不在第 1 节 —— 因为**没跑起来之前，架构图是负担**。

⚠️ 这不是「信息越少越好」。**边界清单（第 8 节）必须在前半部分能找到**，
因为读者最容易被误导的地方是「以为它已经能用了」。

### 2.2 每个数字必须带限定，否则它比没有数字更危险

README 里三处数字，每一处都紧跟限定：

```
  68% / 79%   →  n=28，±15 点
  合规回答 79% →  ★ 不是「答对」，判卷表还空着
  0.09 ms     →  237 条时量的，现在语料是 1345 条
```

★ 最后一条是这次新发现的：`requirements.txt` 和 `LEARNING_LOG` 里的 FAISS
耗时数字是 **237 条**时量的，而现在的语料是 **1345 条**。
数字本身没错，**但它描述的那个语料已经不存在了。**

> **这条和 S5-7 的教训是同一个：量过的数字，也要问它量的是不是现在这个东西。**

### 2.3 `PROJECT_REVIEW` 为什么不直接改数字

选项有两个：

| 方案 | 代价 |
|---|---|
| 直接改正文的数字 | 那份文档的价值有一半在**「当时为什么这么判断」**。改完就变成一份没有时间坐标的报告，§五「Agent 化现在不是时候」的三条理由也跟着失去语境 |
| 保留快照 + 加复核节 | 读者可能只读前半部分 |

**选了后者**，代价用**顶部警告**来还：标题下面第一行就是「这是快照，先读 §九」。
★ 而且复核节不是「更新一下事实」，是**逐条判断哪些理由失效了**：

```
  ① 没有评测数字      → 部分失效（有 28 题了，但仍是 ±15 点的小尺子）
  ② 会放大今天的问题  → 仍然成立，而且更具体
  ③ 语料撑不起        → 失效（7 篇了）
```

**只改数字不改论证，等于伪造一份当时的判断。**

### 2.4 图为什么画成 ASCII，不用 Mermaid

三个理由，按重要性排：

1. **同一张图要活在三个地方**：README、ARCHITECTURE、代码注释。
   代码注释里只能是纯文本。三处放同一种格式，改的时候才知道改哪里。
2. **Mermaid 在 GitHub 上能渲染，但在 `git diff`、`grep`、终端 `cat` 里是代码块**。
   ASCII 图**本身就是可读文本** —— 搜索 `cite.verify` 能直接搜到图里的节点。
3. 本项目的读者是**在终端里读代码的人**。图的行宽控制在 78 字符内，任何窗口都不折行。

### 2.5 架构图只画「有决策的地方」

ARCHITECTURE 里 11 张图，没有一张是「模块调用关系大全」。每张图都在回答
**一个用文字说不清的问题**：

| 图 | 它回答的问题（文字版很难说清） |
|---|---|
| 总图 | 离线和在线的**唯一交点**是那两个文件 |
| ingest 五道工序 | 为什么 ②③ 必须在 ④ 之前（`section` 的状态推进） |
| 两阶段检索 | 为什么 `pool` 必须 > `k`（天花板） |
| 引用核对 | 为什么校验层要 import 生成层（同一个 `render_material`） |
| 四个 status | 哪条边最危险（`suspect`） |
| 三把尺子 | 为什么不能混着测 |
| 依赖方向 | 唯一一处**故意违反分层**的 import |

**画不出一条边的图，不该存在。** 「模块 A 调用模块 B」这种图不解决任何问题 ——
`import` 语句已经写着了。

## §3 不应该怎么写

### ❌ 反例一：把 `config.py` 的注释抄进 README

`config.py` 有 400 多行注释，是**决策日志**（为什么 40 字、为什么 CPU、
为什么 pool=50）。README 里如果要复述它，就有两份事实源 ——
改一处漏一处，**而且不会有任何东西报错**。

这正是这个仓库栽过三次的病（query 前缀 / 扩展开关 / pool 回写），
只不过这次的对象是文档。

✅ **正确写法**：README 只写「结论 + 指向」，理由留在
`config.py` 注释和 ARCHITECTURE 第 7 节，各只有一份。

### ❌ 反例二：只列文件名，不画数据流

骨架 README 里的「目录结构」就是这种：`（简短说明 paper_rag / scripts …）`。
读者知道**有哪些文件**，不知道**数据从哪来到哪去** ——
而后者才是他改代码时需要的信息。

✅ **正确写法**：目录树 + 一张两条链路的图 + 一张「模块 → 职责 → 产品/脚手架」表。

### ❌ 反例三：把「合规回答」写成「准确率」

这是最危险的一类错。看着只是措辞，实际上**改变了读者能做的判断**：

```
  「准确率 79%」   → 读者会以为 79% 的题答对了 → 基于这个去排优先级
  「合规回答 79%」 → 读者会问「那答对率呢？」  → 得到「还没量」→ 正确
```

✅ **正确写法**：用原词，加粗，紧跟一句「不是答对」。

### ❌ 反例四：Roadmap 打勾但不给证据

`[x] Stage 2` 本身什么也没说。**读者要问的是「哪一步做到什么程度」** ——
比如 Stage 2 的验收是「手写结果与向量库一致」，而生产其实**没用**向量库。

✅ **正确写法**：勾 + 一句话结论 + 记录链接。Stage 2 那一格因此补了
FAISS 对拍结果（`1.19e-07`）和「为什么进 requirements 但不接线」。

### ❌ 反例五：写「运行的命令」之外，不写「前置条件」

`eval_answer.py` 需要 Ollama 起着、索引存在。README 里没写，读者会撞上
`FileNotFoundError` 然后去翻源码。**报错应该在第一屏就能避免。**

## §4 怎么验证

文档没法跑单测，所以用三条机械检查代替：

### 4.1 数字 → 出处（每个数字都必须能点回去）

| README 里的数 | 出处 |
|---|---|
| 7 篇 / 1345 条 | `python -c "len(chunks)"`；`docs/stages/S5-0` |
| 1024 维 / `bge-m3:latest` | `data/processed/ids.json`；`paper_rag/config.py` |
| 50% / 0.605 / 71% | `docs/stages/S5-3`（dense 基线） |
| 68% / 0.763 / 89% | `docs/stages/S5-5`（rerank @pool50） |
| 32% / 0.429 / 54% | `docs/stages/S5-2`（BM25） |
| 71/89/100%、79/79/82% | `docs/stages/S5-6` |
| 22/28 → 24/28 | `docs/stages/S5-7` §1 |
| 19 / 8 / 2 | `docs/stages/S5-8` §0 |
| 0.09 ms（237 条） | `scripts/probe_scale.py` + `LEARNING_LOG` §10 |
| 10.6 s / 13.3 s | `docs/stages/S5-5` 4.6；`S5-6` |
| 4084 / 4228 行 | `wc -l paper_rag/*.py scripts/*.py` |
| 13 个探针 | `ls scripts/probe_*.py \| wc -l` |

★ **一条找不到出处的数字，就不该出现在 README 里。**
这一栏是这次的「判卷表」—— 人（我）写的每个数，机器（上表）能核。

### 4.2 链接检查

所有相对链接必须真的存在。跑一遍：

```python
# 检查 md 里的相对链接是否指向存在的文件
import re, pathlib
root = pathlib.Path(".")
bad = []
for md in root.rglob("*.md"):
    if ".venv" in md.parts:
        continue
    for link in re.findall(r"\]\(([^)#]+\.md)(?:#[^)]*)?\)", md.read_text(encoding="utf-8")):
        if link.startswith(("http://", "https://")):
            continue
        if not (md.parent / link).resolve().exists():
            bad.append(f"{md} -> {link}")
print("\n".join(bad) or "OK")
```

### 4.3 事实核对（命令真的能跑吗）

README 里的命令按**能不能解析参数**检查，不需要真跑完：

```powershell
python scripts/ask.py --help
python scripts/eval_retrieve.py --help
python scripts/eval_answer.py --help
python scripts/score_judge.py --help     # 这个没有 argparse，看源码
```

### 4.4 交叉核对：文档之间不能互相矛盾

这一条最容易漏，而且**最伤人** —— 读者不知道信哪个。

已核对的三处：

| 位置 A | 位置 B | 结论 |
|---|---|---|
| README「生产是 dense+rerank」 | ROADMAP 基线表 | 一致（68%） |
| README「没有向量库」 | ROADMAP Stage 2 | 一致（补上了 FAISS 不接线的说明） |
| README「判卷表空着」 | ROADMAP 待办 + PROJECT_REVIEW §九 | 一致 |

★ 这三处里，**ROADMAP 的 Stage 2 原本是矛盾的** ——
它写着「再换成向量库（FAISS）」，而生产用的是 numpy。这次一并修了。

## §5 要补的概念

| 概念 | 一句话 | 在这个项目里对应什么 |
|---|---|---|
| **单一事实来源** | 一份事实只写在一个地方，其它地方引用它 | 模型名只在 `config.py` 写一次；文档说「见 config」 |
| **快照文档 vs 活文档** | 快照记录「当时怎么判断」，不随现状改；活文档跟着代码走 | `PROJECT_REVIEW` = 快照；`README` / `ARCHITECTURE` = 活文档 |
| **分层读者** | 同一件事，对外来者、接手者、决策者、学习者要有四种写法 | 四份文档的目录那棵依赖树 |
| **可执行的例子** | 文档里的命令和输出必须是真的跑过的 | README 第 1 节那段 `ask.py` 输出 |
| **限定的传递** | 一个数字的适用范围必须跟着数字一起走 | `±15 点`、`237 条时`、`不是答对` |
| **信息密度 vs 渲染保真** | 图要能在终端、diff、GitHub 三处都成立 | 选 ASCII 不选 Mermaid |

## §6 自测题

1. **一个新人 clone 下来，第 3 步会撞什么错？**
   提示：`data/raw/` 里没有 PDF，而 `.gitignore` 把它们忽略了。
   README 第 10 节要能回答「怎么弄到它们、文件名为什么必须一模一样」。

2. **为什么不把 `config.py` 里「为什么 pool=50」的实测表格抄进 README？**
   （见 §3 反例一。关键词：两份事实源、不会报错。）

3. **`PROJECT_REVIEW` 的 §五「Agent 化现在不是时候」今天还成立吗？**
   三条理由里哪条失效、哪条更强了？（见 §九 9.4。
   注意：「语料撑不起」失效了，但 S5-6 给出了一个**更前置**的理由。）

4. **「合规回答 79%」和「准确率 79%」差在哪？**
   举一个反例：一份**引用全为真、结论讲反了**的回答，在哪一列是满分？
   （提示：`verify` 只查「这句话有没有出处」，不查「这个出处该不该用在这里」。）

5. **如果要给 ARCHITECTURE 再加一张图，你会加什么？判据是什么？**
   提示：判据是「这张图能不能回答一个文字说不清的问题」。
   如果你答的是「模块调用关系图」—— 那 `grep import` 已经干完了这件事。

6. **★ 这次最该记住的一条：**
   `requirements.txt` 里的 FAISS 耗时是在 237 条上量的，而语料已经是 1345 条。
   **数字没错，但它描述的那个东西已经不存在了。**
   问：怎么避免这种「正确的数字描述错误的现状」？
   （提示：数字旁边写清**它是针对什么量的**，而不只是「量出来是多少」。
   这和 S5-7 的「标定仪器」是同一件事的文档版。）
