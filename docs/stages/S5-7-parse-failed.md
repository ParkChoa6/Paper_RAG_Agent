## §2 为什么这么写

### §2.1 ★★ 先探针，再动手 —— 预写的修法为什么没用上

`parse_response` 的 docstring 里**早就预写好了修法**（2026-09-25 写的）：

```
已知漏洞：find("{") 默认【第一个左花括号就是 JSON 的开头】
真出现了怎么修 —— 逐个试每个 { 的位置：
    obj, _ = json.JSONDecoder().raw_decode(text, idx)
★ 恢复条件：探针里连续两次看到这个报错 → 立刻修。
```

**恢复条件早就触发了**（端到端 4 次 + 探针 4/4）。按规矩就该照着那段写。

**照做会白写一个解析器。** 因为探针第一次跑出来的东西是这样的：

```
dense Q6    done_reason='stop'  eval_count=78    {x2  }x0   ← 全文一个 } 都没有
dense Q13   done_reason='stop'  eval_count=286   {x2  }x1   ← 内层关了，外层没关
```

★ **`raw_decode` 解决的是「我们【切】错了位置」；实测的病是「文本里【缺】字符」。**
没有合法 JSON 可解，试遍每一个 `{` 也解不出来。

★★ **更要命的是第二个症状的误导性。** Q13 报的是
`Expecting ',' delimiter ... char 981`，看着就是"引号没转义"。点开原文那 60 个字符：

```
...Express intent to meet or\""}
                        ↑↑
                  这是【正确】的转义 \" ，后面那个 " 才是关字符串的
```

模型写的是**对的**。它只是少关了一个 `}`。
**按报错文本猜修法 → 去写一个处理未转义引号的解析器 → 完全打偏。**

> **恢复条件触发 ≠ 按预写的方案修。**
> 预写的方案是针对**当时想象的**失败模式的。真实失败模式变了，
> 那条恢复条件只是"该动手了"的信号，不是"动手做什么"的答案。
> **先探针，再动手。** 差这一步，就会写出一个让"壳缺括号"看起来已经被处理过的假防线。

同一件事还有第三个证据：**`done_reason`。** 如果只是缺个 `}`，
那"再叮嘱一句别忘了括号"就够了；真正的问题是**模型自己决定停了**。
`done_reason='stop'`（不是 `'length'`）说明它主动吐了 EOS ——
**它不是被砍断的，是它认为写完了。** 那就只能在采样器那一层拦。

### §2.2 三个备选修法，为什么选约束解码

| 修法 | 治的是什么 | 为什么否掉 / 采纳 |
|---|---|---|
| **① 容错解析器**（补括号 / raw_decode） | 症状 | ❌ 见 §2.1：缺的是字符不是切点。而且它**会掩盖**截断——见 §3.1 |
| **② 改 prompt**（"最后必须以 `}}` 结尾"） | 请求 | ❌ **是请求，不是保证**。S5-6 §2.3 记过：模型嘴上答应得很好，转头照旧。（更要命的是：这里它**以为**自己写完了，不是忘了） |
| **③ 约束解码**（`format=` JSON Schema） | 源头 | ✅ **采纳。** 采样器的合法下一步被语法限死，`{"answer":"…","used":[1]` 这个状态**不接受结束**。模型**物理上没法停在半路** |

★ 为什么 ③ 是"保证"而 ② 是"请求"，值得说透：

```
  prompt 里写"别忘了括号"  →  模型读完，仍然要【自己】决定下一个 token 是什么。
                              它是一个概率分布上的建议。

  format=<schema>          →  下一个 token 只允许是语法接受的那些。
                              分布被【裁剪】过了，不合法的 token 概率是 0。
```

**一个作用在"它怎么想"，一个作用在"它能说什么"。** 后者才是硬的。

---

### §2.3 为什么必须传【具体 schema】，不能传裸 `"json"`

Ollama 的 `format` 可以传 `"json"`（只要求"是 JSON"）。**实测会硬炸：**

```
ollama._types.ResponseError: prediction aborted, token repeat limit reached
                            (status code: 500)
```

★ 裸语法太松 —— 模型可以在它允许的空白/字段里打转，撞上 Ollama 的重复保护。
**必须传具体 schema**：字段名和类型钉死了，模型没有可打转的空间。

这条记在这里是因为它**反直觉**：一般人会以为"约束松一点更安全"。
实际相反 —— **约束不精确 = 给模型留了一块可以迷路的空地。**

★ 顺带：这个 500 是**在生成阶段**炸的，不是解析阶段。也就是说
`ask()` 的 `try/except` 会把它变成 `parse_failed` —— **同一个 status，
但病在更上游。** 如果当时没接住这个异常，探针会跑一半就死，
而且**已经拿到的证据也一起丢了**。

---

### §2.4 一份契约，现在有【三处】表达 —— 必须一起改

```
    build_prompt 第 5 节    给【模型】看的字面示例（人话）
    GEN_SCHEMA             给【采样器】看的语法（它不接受人话）
    parse_response 第 3 步  给【代码】做的形状校验（事后把关）
```

这三处说的是**同一件事**：输出的字段叫什么、什么类型。

⚠️⚠️ **加字段时漏改任何一处，症状都不一样，而且都不好查：**

| 漏了哪一处 | 症状 |
|---|---|
| 漏了 prompt | 模型不知道该填什么 → 语法又逼着它填 → **它编一个值** |
| 漏了 schema | 采样器不认 → 模型填了也输出不出来 → 表现为**解析失败** |
| 漏了 parse_response | 模型交了、采样器放了、**校验层把它扔了** |

这和 `render_material` 那条是**同一条规矩**：
> 「守卫的判据和它守的那个操作只要是两套，就会各自漂移 ——
>   而漂移出来的是一条'看起来在守卫'的假防线。」

★ 本步**没有**把三处合成一处（`GEN_SCHEMA` 无法自动从 prompt 文案里生成，
那需要把 prompt 改成数据驱动的）。所以这里留下的是**一条纪律**，不是一道防线 ——
**下次给契约加字段，记得改三处。**

## §3 不应该怎么写

### §3.1 按报错文本猜修法

**错法**：看到 `Expecting ',' delimiter` 就断定"引号没转义"，写一个转义修复器。

**症状**：修完之后 Q13 依然失败（因为缺的是 `}`，不是转义），
**而且更难查了** —— 多了一段"处理过引号"的代码，读代码的人会以为这一类已经处理完了。

**判据**：报错信息说的是**解析器走到哪儿卡住了**，不是**文本哪里错了**。
两者可以差得很远。**先看原文那 60 个字符，再决定修什么。**

---

### §3.2 ★★★ 报数之前不量【本底噪声】—— 而且要量够多次

**这是本步最重要的一条，而且我自己在这一条上先摔了一跤。**

**错法**：跑一遍 A（无约束）、跑一遍 B（约束解码），diff 一下，
发现 28 题里 **9 题答案文本变了** → 写进结论「约束解码改变了 9 题的回答」。

**实际发生的事**：那 9 题里 **7 题跟约束解码毫无关系**。

**正确的做法**：**先把"什么都不改时会变几题"量出来。**

```
  A  vs A2   同配置跑两遍     答案文本不同  7 / 28
  A  vs B    无约束 vs schema 答案文本不同  9 / 28
  ─────────────────────────────────────────────
  差集 = {6, 13}  ← 正好是被修好的那两题，一题不多
```

★ 也就是说：**约束解码除了修好那两题，一个字都没改。**

没有 A2 这一跑，本步会写下"改了 9 题"这个**错的**结论，
而且它会**看起来完全合理**（9 比 7 大一点，像是"约束解码让模型收敛了"）。

#### ★★★ 但"跑两遍"也不够 —— 这是本步最贵的一课

上面那张表里，我把 **7/28 标成了"这台仪器的本底噪声"。**
**它是错的。** 那是 **n=1 对配对**抽中的一次异常运行。

补到 **8 次运行**之后真相是：**21 个配对都在 0~2/28，只有 A 和谁都比 7 题。**

```
  ⇒ 本底噪声不是 7/28，是【1 题】。
  ⇒ 而 7/28 那一次，是 8 次里的 1 次异常。
```

**所以正确的做法要再进一步：不是"跑两遍"，是"跑到你能看出哪次不正常为止"。**

> ★★ **一个机制讲得通的解释 + 一对数据 = 看起来像结论。它不是。**
> **"什么是正常"要靠反复量，不靠更精致的解释。**

> **报数之前先算这台仪器的分辨率。**
> S5-6 §4.5 用这条量的是"n=28 时多少点算差异"；
> 本步用的是同一条规矩的**另一个方向**：**不是"多大的差算差"，
> 而是"什么都不改时本来会差多少"。**
> ★ 前者是**跨配置**的分辨率，后者是**跨运行**的分辨率。**后者更基本 ——
> 不知道它，前者算出来的也没有意义。**

### §3.3 在 `llm` 层"顺手清理一下输出"

**错法**：既然问题是 JSON 壳没闭合，就在 `llm.generate` 里
`raw = raw + "}" * (raw.count("{") - raw.count("}"))` 补上。

**症状**：
- 这个函数从此**不再返回模型说的原话**。而它的 docstring 第一条就是
  「模型说什么就原样返回什么，判断是上层的事」。
- 更要命：**截断（`done_reason='length'`）也会被它悄悄修好**。
  一个写到一半的答案，补两个括号之后**看起来是完整的** ——
  然后 `cite.verify` 大概会发现引文对不上，但 **`answer` 字段没人验**，
  用户会拿到半句话。**这是把"响亮的失败"换成了"安静的失败"。**

★ **补 `}` 不算"编内容"**（补的不是值，是结构），这条区分本身是对的。
但**判断"这次该不该补"需要的信息（`done_reason`）在 `llm` 层没有**，
在 `parse_response` 层也没有 —— 它在 `resp` 对象上，是**被 `generate` 丢掉的东西**。
**要拿到它，就得改 `generate` 的返回类型**，那是一次伤筋动骨的改动，
而约束解码**从源头就不产生这种输出**，根本不需要修。

> **能在上游拦住的，不要在下游补。** 下游补的每一处，
> 都要额外携带"这次该不该补"的判断信息 —— 而上游拦住时，这个信息不存在。

---

### §3.4 开关不记进评测结果

**错法**：`--gen-schema` 只在命令行里，结果 JSON 里没有。

**症状**：两周后你手里有两个 `results.json`，**看不出哪个是哪个**。
这和 S5-1（query 前缀只活在评测脚本里）、S5-2（扩展开关在 `eval_embed.py` 里不存在）、
S5-5（决策定在 pool=50、`config` 还写着 20）是**同一类病的第四次**。

**本步的挡法**：`--gen-schema` 的**默认值就是 `config.GEN_JSON_SCHEMA`** ——
**想量对照组，必须【明说】。** 并且每一行结果里都有 `gen_schema` 字段。

## §4 怎么验证它真的对了

### §4.1 冒烟

```bash
.venv/Scripts/python.exe -m py_compile paper_rag/*.py scripts/*.py
.venv/Scripts/python.exe -c "import ollama; ..."   # format=None 被接受吗
```

★ 那个 `format=None` 的小检查不是多余的：原来的 `client.generate` 调用
**一个 format 都没传**，现在无条件传一个 `None` 进去。
如果 Ollama 客户端对 `None` 的处理和"不传"不同，**生产路径当场变样**。
实测：接受，且行为确实是不约束（输出还带着 ` ```json ` 围栏）。

### §4.2 探针 A/B（4 个样本 × 4 遍）

```bash
.venv/Scripts/python.exe -u scripts/probe_parse_fail.py --repeat 4
.venv/Scripts/python.exe -u scripts/probe_parse_fail.py --repeat 4 --format schema
```

```
现状（不传 format）        ❌ 解析失败 8/16
                           —— Q6 4/4 必现、Q13 4/4 必现、Q24 0/4 偶发
--format schema（约束解码） ✅ 解析通过 16/16
```

★ 探针记下的**逐遍 `eval_count`** 是判断"必现还是偶发"的依据：
Q6 每次都是 78、Q13 每次都是 290 —— **一模一样**，说明这两个是**确定性的**，
不是运气。而 Q24 时好时坏。

### §4.3 28 题 A/B（dense 臂，同一 session）

```bash
.venv/Scripts/python.exe -u scripts/eval_answer.py --arms dense --no-gen-schema --out …A
.venv/Scripts/python.exe -u scripts/eval_answer.py --arms dense                    --out …B
```

**基线（无约束）跑了【4 遍】，约束解码跑了【3 遍】。**
★ 为什么要这么多遍：只有这样才能知道"22"和"24"之间那 2 题，
到底是修出来的还是抖出来的。**这是 §4.4 的铺垫。**

| 运行 | 约束解码 | `answered_clean`<br>（合规回答） | 拒答 | 可疑 | **解析失败** | 引用有问题 | 材料含答案 |
|---|---|---|---|---|---|---|---|
| A 无约束 | ❌ | 23 / 28（82%）⚠️ | 1 | 1 | **2** | 1 | 20 / 28 |

## §5 你要补的概念

1. **约束解码 / 语法约束（grammar-constrained decoding）**
   不是"让模型更守规矩"，是**在采样时把不合语法的 token 概率置零**。
   关键词：GBNF（llama.cpp 的语法格式）、JSON Schema。

2. **请求 vs 保证**
   prompt 里的话是**请求**（模型可以选择不听）；
   采样器上的约束是**保证**（不合法就输出不出来）。
   ★ 凡是"我说了它不听"的问题，先问：**能不能挪到保证那一侧？**

3. **`temperature=0` 到底是什么**
   它把采样器切成**贪心**（每步取概率最大的那个 token）。
   ★ 本步实测：**它确实在起作用，而且相当可复现**
   （11 题 × 3 遍，全部只出 1 种输出；默认温度下全部出 2~3 种）。
   ⚠️ 但**上一版我写的是反的**（"`temperature=0` ≠ 可复现"）——
   那是从一对运行读出来的，见 §4.4 / §7.1。
   **教训：一个参数的"实际行为"要用探针直接量，别从端到端指标反推。**

4. **本底噪声（跨运行）vs 分辨率（跨配置）**
   前者问"什么都不改时会差多少"，后者问"多大的差才算差"。
   **前者更基本**：不知道它，后者算出来的也没意义。
   ★ 本步把它量出来了：**合规回答 ±1 题 / `parse_failed` 0 题 / 材料含答案 0 题。**

5. **★ 一对配对不能标定仪器（本步最贵的一课）**
   我用 **n=1 对运行**（A vs A2）算出了"本底噪声 = 7/28"，
   还配上了讲得通的机制，写进记录和代码注释。
   **补到 8 次运行后，那个数变成了 1/28，而 7/28 只是其中一次异常。**
   > **要判断"什么是正常"，得先知道正常长什么样 ——
   > 那需要更多次运行，而不是更精致的解释。**
   > 一个机制讲得通的解释 + 一对数据 = 看起来像结论。**它不是。**

6. **"恢复条件触发" ≠ "按预写的方案修"**
   预写的是**针对当时想象的**失败模式的方案。
   触发只说明"该动手了"，不说明"动手做什么"。**先探针。**

7. **上游拦住 vs 下游补救**
   下游每补一处，都要额外携带"这次该不该补"的信息；
   而上游拦住时，这个信息**根本不需要存在**。

8. **一份契约的多个表达必须一起改**
   prompt 文案 / schema / 校验代码 —— 三处漏一处，三种不同症状。
