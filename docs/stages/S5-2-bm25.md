## 2. 为什么这么写

### 2.1 为什么要建倒排索引，而不是每次查询现扫

朴素做法：每来一个 query，把 1345 条文档全扫一遍数词频。

```
朴素：O(N × L)  ← N=1345 篇，每篇 L 个词
倒排：O(命中该词的文档数)
```

倒排索引把「**和 query 无关的那部分**」提前做完：

```
term → [(文档号, 出现次数), ...]
```

★ 这**和 `vectors.npy` 是同一个思路**：把和 query 无关的计算提前算完、存下来。
  区别只是向量那份要**存磁盘**（嵌入模型贵，22 秒），倒排这份**在内存里现建**（0.0 秒 —— 见下面实测）。

既然 0.0 秒就能建，就不该多一个文件、多一次同步。**能现建的东西不要存盘**，
存了就多一个「可能过期」的东西。

### 2.2 IDF 里那个 `1 +` 是**必须**的，不是修饰

```python
self.idf = {t: math.log(1 + (self.n - d + 0.5) / (d + 0.5)) for t, d in df.items()}
```

教科书上常见的写法是**不带**这个 `1 +`：

```
IDF(t) = ln( (N − df + 0.5) / (df + 0.5) )
```

当 `df > N/2`（这个词出现在**超过一半**的文档里）时，分子小于分母，
**IDF 是负数**。

后果：一个词越常见，得分越低，低到**把总分成负数**。
`the` 出现在几乎所有文档里 —— 它会给每个文档**倒扣分**。

★ 这是 BM25 里**最容易抄错**的一个字符。而且抄错了**不报错**，
只是分数整体偏、某些题莫名排得靠后。加 `1 +` 之后 IDF 恒 ≥ 0，
常见词只是「贡献接近 0」，不会倒扣。

### 2.3 为什么**不需要**停用词表

我已经预判到你会问这个：BM25 不做停用词过滤，`the` / `of` / `is` 照样进索引。

**不需要**，因为 IDF 自动干了这件事。`the` 出现在 1345 条里的 1200 条，
`df/N = 0.89`，代进公式 IDF ≈ `ln(1 + 0.12) ≈ 0.11` —— 几乎为零。
而 `transe` 可能只出现在 40 条里，IDF ≈ `ln(1 + 32) ≈ 3.5`。

**差 30 倍。** 常见词自动被压没了。

> **一条通用经验**：**能用统计解决的事，不要用手写清单。**
> 停用词表是手工的、语言相关的、换语料就得重写的东西。
> 而 IDF 是语料自己算出来的 —— 换语料自动适应。

★ 附带好处：**不用装 nltk**。少一个依赖。

### 2.4 为什么**不用** jieba 分词

语料是**英文论文**，题目是**中文问题**。这个不对称是本步最大的坑。

如果我装了 jieba：

```python
jieba.cut("静态知识图谱推理的模型按技术分成哪三类？")
# → ['静态', '知识', '图谱', '推理', '的', '模型', ...]
```

切得很漂亮。然后拿这些词去查**英文倒排索引** ——
`静态` 这个词在英文论文里出现 0 次。**一个都匹配不上。**

> **切出来能匹配上才有用，切出来匹配不上不如不切。**

所以 `tokenize` 只切 ASCII，中文 query 直接返回 `[]` —— 一个**诚实的空**，
而不是一个「看起来做了很多事但其实什么都匹配不到」的词列表。

### 2.5 接口只约束 `search`，构造函数各随各的

```python
DenseRetriever.from_chunks(client, model, chunks)    # 要 client、要模型名
BM25Retriever.from_chunks(chunks)                    # 什么都不要
```

★ 这两个签名**不一样**，而且**没关系**。`Retriever` 是 `Protocol` 不是 `ABC` ——
它只管 `search()` 长得对不对，不管你怎么造出来。

如果 S5-1 用的是 ABC（`class DenseRetriever(Retriever)`），
那就得给 `from_chunks` 定一个统一签名，`BM25Retriever` 只能收下一个
用不到的 `client` 参数装作需要。**这就是「接口漏了」的样子。**

> **一个抽象设计得对不对，不是看第一个实现写起来顺不顺，
> 是看【最不像的那个实现】能不能原样进来。**

`BM25Retriever` 这个类里**没有 `embed_one`、没有向量、没有 numpy**
（去数一下 import 就知道了）。它进来得干干净净。

### 2.6 ★ 为什么 rank 必须记 `all_k + 1`，不是 `len(scored) + 1`

这是本步唯一一个**必须**改的 bug，也是最有教学价值的一处。

```python
# 原来（eval_retrieve.py 早先的版本）
rank = len(scored) + 1

# 现在
rank = all_k + 1
```

原来的写法在 dense 上**永远是对的** —— 因为 dense 永远返回 min(k, N) 条，
你传 `all_k=1345` 它就返回 1345 条，`len(scored)+1 = 1346`，正好是「比最后一名还差」。

**但 BM25 不是。** 纯中文 query → `tokenize` 返回 `[]` → `search` 返回 `[]`。
这时：

```
len(scored) + 1  =  0 + 1  =  1      ← 被当成【第 1 名】
```

★ **一个什么都没返回的检索器，被记成了满分。**

而且它**不报错、不警告、退出码 0** —— 你会看到一张很漂亮的表。
实测代价见 4.5，那个数字值得单独记一笔。

正确写法应该是「**比全语料最后一名还差**」，也就是 `all_k + 1 = 1346`。
这个值**和检索器返回了什么无关** —— 这才是对的，
因为「找不到」这件事的严重程度不该取决于你试了多少条。

### 2.7 为什么「空结果」要**单列一列**，不并进平均排名

看 4.3 那两行 BM25：

```
BM25 不扩展   平均排名 897.9   空结果 7
BM25 开扩展   平均排名 242.8   空结果 1
```

「平均排名 897.9」是什么意思？它是这样来的：

```
9 题找到了（排名 1~94） + 7 题【压根没找到】（记成 1346）
897.9 × 12 = 10775
```

**这个平均数不描述任何一个真实情况。** 它把「排第 3」和「一个字都找不到」
糊成了同一个数。看到 897.9 你会想「要不要调调 k1？」

★ **但真正该修的是另外那 7 题**（加扩展词条），
而不是「让排名从 897 变成 800」。

> **一条通用经验**：**当一个指标把【完全不同性质的失败】糊成一个数时，
> 它会指向错误的修法。** 拆开它 —— 哪怕只是多一列。

所以有了 `空结果` 这一列。它问的不是「排得靠后吗」，
是「**有没有资格参与排名**」。

### 2.8 为什么 `k1` / `b` 要写进 `name`

```python
return f"bm25:k1={self.index.k1},b={self.index.b}"
```

和 `DenseRetriever` 的 `:raw` / `:prefix` 是同一个理由：
**将来调参做 A/B 时，两行在表格里必须能分开。**

名字写成 `"bm25"` 的话，`k1=1.5` 和 `k1=2.0` 两组长得**一模一样** ——
表格上两行同名，你会分不清哪行是哪个。

## 3. 不应该怎么写

### 3.1 ❌ `rank = len(scored) + 1`（静默偏袒「什么都不返回」）

**症状**：BM25 拿到一张 **Top-1 75% / MRR 0.828 / recall@5 92%** 的表，
**全面碾压 dense（50% / 0.563 / 58%）**。

而那个 BM25 **在 7 道题上一个字都找不到**。实测数字见 4.5。

★ 这个错最毒的地方在于：它**不会让你怀疑 BM25**，
它会让你**信心满满地往下做 RRF** —— 围绕一个假的前提做一整个 Stage。

> 注意这是 `eval_embed.py` / `eval_retrieve.py` 这类脚本特有的病。
> **生产路径不会犯这个错**（用户看得见答案不对），
> **只有「算分数的脚本」会**。所以评测脚本自己更需要被评测。

### 3.2 ❌ 把「平均排名 897.9」当成一个平均值

见 2.7。**症状**：你会去调 `k1`/`b`，而真正的问题是「7 题完全失明」。

### 3.3 ❌ 只在**一种** expand 设置下量

这是本步真正的教训，见 4.2。**症状**：你量了一个生产上根本不存在的配置，
然后拿它当基线，然后拿它去判断 RRF 有效没效。

### 3.4 ❌ 拿 BM25 的分数和 dense 的分数比大小

```
dense  Q4 = +0.7561        BM25  Q4 = +16.7830
```

`16.78 > 0.76` —— 所以 BM25 更好？**这个比较没有意义。**
余弦有上界 1，BM25 无上界（取决于文档长度、语料大小、词有多稀罕）。

★ 这就是**为什么 RRF 要按【排名】融，不能按【分数】加权平均**。
两个都「越大越好」，但 `0.8` 和 `0.8` 完全不是一回事。
（S5-3 的事，这里先把坑标出来。）

### 3.5 ❌ 用 `nltk` / `jieba` 分词

见 2.4。**症状**：中文 query 被切成很漂亮的词，
然后**一个都匹配不上**（因为语料是英文），BM25 依然返回空 ——
但你多了一个依赖、多了一层「我明明做了分词啊」的困惑。

## 4. 怎么验证它真的对了 / 量到了什么

### 4.1 先对拍：dense 的数字必须**一位都不动**

这是 S5-1 定下的规矩 —— **换实现时留一个独立参照物不动。**

参照物 = S5-0 记下的基线（`dense:bge-m3:raw`，语料 1345 条 / 12 题）：

| | S5-0 记的 | 本步实测 | |
|---|---|---|---|
| Top-1 | 50% | **50%** | ✅ |
| MRR | 0.563 | **0.563** | ✅ |
| 平均排名 | 21.4 | **21.4** | ✅ |
| recall@5 | 58% | **58%** | ✅ |
| 空结果 | （没这一列） | 0 | — |

**四位全同。** 说明 `eval_retrieve.py` 从「内联的 dense 循环」改成
「走 `Retriever` 接口」这一路，**没有偷偷动过数字**。
（顺带证明 `--kind bm25` 的加入没有污染 dense 那条路径。）

### 4.2 ★ 然后才发现：这个基线**量错了一个变量**

对拍通过之后我去量「开扩展」的那一格，才注意到一件事：

```
config.py:
    EXPAND_ENABLED = True          ← ★ 生产是【开着】的
```

而 `eval_retrieve.py` 和 `eval_embed.py` **从来就没有「扩展」这个概念**。
所以：

| | 之前所有历史数字 | 生产实际在跑的 |
|---|---|---|
| 查询扩展 | **关** | **开** |
| dense recall@5 | 58% | **67%** |

**我上一步（S5-0）写下的「要打败 58%」这个目标，是错的。**
真正要打败的是 **67%**。

★ 这不是「算错了」，是**评测和产品量的不是同一个东西** ——
正是 S5-1 里那个「query 前缀只活在评测脚本里」的**同一个病的第二个实例**。

> **一条通用经验（第二次撞到，该升级成规矩了）**：
> **评测里出现的每一个「只影响 query 的开关」，都要问一句
> 「生产是这个值吗？」** 这类变量最阴 —— 它们不改代码路径、
> 不报错、不影响单测，只让两边悄悄量不同的东西。

### 4.3 四格表（12 题 / 1345 条语料）

| 检索器 | Top-1 | MRR | 平均排名 | recall@5 | 空结果 |
|---|---|---|---|---|---|
| dense，不扩展 | 50% | 0.563 | 21.4 | 58% | 0 |
| **dense，扩展** | **58%** | **0.646** | **17.5** | **67%** | 0 |
| BM25，不扩展 | 17% | 0.237 | 897.9 | 33% | **7** |
| BM25，扩展 | 25% | 0.376 | 242.8 | 50% | 1 |

**三个读法：**

**① 扩展对 dense 也是加分项，而且不小。**
Top-1 `50% → 58%`，recall@5 `58% → 67%`，平均排名 `21.4 → 17.5`。
（这解释了 `config.py:146-157` 早就记下的那条观察：同一道题
「知识图谱嵌入模型是按什么标准分类的？」带扩展排 33、不带排 1…
—— 现在是同一张表上的系统测量。）

**② 扩展对 BM25 是生死线，但**没救活**。**
空结果 `7 → 1`（救回 6 题），Top-1 `17% → 25%`。
但仍然**远低于 dense**（58% / 67%）。

**③ 最重要的一条：BM25 单独用，打不过 dense。**
不要急着下结论说「BM25 没用」—— 见 4.6 和 4.7。

### 4.5 ★ 那个 bug 的实测代价

把两种 rank 写法都跑一遍（同一份 BM25、同一批题、**不扩展**）：

|---|---|---|---|
| `len(scored) + 1`（旧） | **75%** | **0.828** | **92%** |
| `all_k + 1`（现在） | **17%** | **0.237** | **33%** |

**旧写法下，BM25 看起来比 dense 强一整档**（dense 是 50% / 0.563 / 58%）。
真实的 BM25 在 **7 / 12 题上完全失明**。

> 如果这个 bug 留到 S5-3，我会基于「BM25 更强」去做 RRF、
> 去调 `k1`/`b`、去写一份「BM25 效果很好」的记录。
> **整个 Stage 5 会长在一个假前提上，而且中间不会有一次报错。**

### 4.6 为什么 Q9 是「找不到」而 dense 是「第 21 名」—— 本步最好的一个取证

Q9：`CompoundE3D 的剪切算子是复合了哪三个算子？`

扩展后只切出一个词：`["compounde3d"]`。BM25 给 **9 条**文档打了分。

**而那 9 条里没有正确答案。** 去看目标 chunk（`kg-embedding-overview#122`）的原文：

> The shear operator is the result of **compounding 3 operators**: Hyz, Hxz, and Hxy

**这个 chunk 里根本没出现过 "CompoundE3D" 这个词。**
模型名写在论文别处，这一块只讲算子本身。

- **BM25 的视角**：query 只有 `compounde3d` 一个词 →
  只有含这个词的 9 条能进候选 → 答案不在里面 → **它连机会都没有**
- **dense 的视角**：「剪切算子 / 复合 / 三个算子」在语义上
  对上了 "shear operator ... compounding 3 operators" ——
  **一个字都不重合，但它找到了，第 21 名**

★ 这一条把「**dense 比意思、BM25 比字面**」从一句口号
变成了一个能指着看的具体失败。也**同时**说明了：

- 不是 BM25 写得烂 —— 它严格、正确地执行了「字面匹配」
- 是**这题的字面信息压根不在正确段落里**

### 4.7 ⚠️ 但是：这张表**不支持**「加 BM25 会涨分」

必须把这条写下来，否则下一步会自欺。

12 题的逐题对照里，BM25 **没有一题**明显好过 dense（只有 Q5，而两边都在 80 名开外）。
而 dense 的 4 个弱点（Q3=6 / Q5=139 / Q9=21 / Q12=35），
BM25 分别是 25 / 83 / 找不到 / 94 —— **全都不如 dense**。

**所以在这 12 题上，BM25 的贡献约等于零。**

但**这不等于「RRF 没用」**，也不等于「BM25 该删」。两件事要分开：

| | 结论 | 证据强度 |
|---|---|---|
| 这 12 题上 BM25 单独打不过 dense | 成立 | 强（逐题可查） |
| 这 12 题上 RRF 会涨分 | **不知道** | **12 题量不出来** |
| BM25 该保留 | 应该 | 结构性理由（独立故障模式）|

★ **12 题，一道题值 8.3%，SE ±14%。**
BM25 和 dense 的差距只有 1~2 道题的量级 ——
**这个差距比测量的噪声还小。** 拿它下结论是不负责任的。

## 5. 你要补的概念

### 5.1 倒排索引（inverted index）

正排：`文档 → 它有哪些词`。倒排：`词 → 哪些文档有它`。

搜索引擎、ES、Lucene 全是倒排。核心动机和 `vectors.npy` 一样：
**把和 query 无关的计算提前做完。** 区别是向量表要存盘（贵），
倒排表可以现建（0.0 秒，见 4.3 的建索引时间）。

### 5.2 IDF · tf 饱和 · 长度归一化 —— 三个部件各管一件事

```
score = Σ  IDF(t) ·  ──────────────────────────────
                     tf + k1·(1 − b + b·|d|/avgdl)
```

| 部件 | 管什么 | 不管会怎样 |
|---|---|---|
| **IDF** | 这个词有多稀罕 | 常见词倒扣分（若忘了 `1 +`） |
| **tf 饱和** | 出现 10 次不比 1 次重要 10 倍 | 复读机文档垄断结果 |
| **长度归一化** | 长文档天然容易命中 | 长文档垄断所有结果 |

`k1=1.5` / `b=0.75` 是几十年的经验默认值 ——
**但它们不是普适常数**，是在别的语料上量的。
调它们之前先想清楚「我的语料哪里不一样」。

### 5.3 「候选池」不是一个常数

dense 的候选池**永远是全语料**（它给每条都算余弦）。
BM25 的候选池是「**含至少一个 query 词**」的那些 —— 本步实测 0~646 不等。

★ 所以两个检索器的「排名」**不在同一个尺度上**。
这件事对 RRF 有直接影响：RRF 按排名融，
但「BM25 的第 5 名」和「dense 的第 5 名」含金量不同 ——
**BM25 的第 5 名（池子 22 条）比 dense 的第 5 名（池子 1345 条）更稀松**。

这个坑记下来，S5-3 会撞上。

### 5.4 字面 vs 语义是**两种失败方式**，不是好坏

| | 强在 | 败在 |
|---|---|---|
| dense | 跨语言、跨同义词、换个说法也找得到 | 「意思近、事实不对」的段落会被排上来 |
| BM25 | 命中就是命中，**不瞎猜**；专有名词极准 | 换个说法就完全找不到（Q9 就是） |

★ **融合（RRF）有意义的前提是：两者的错误【不相关】。**
总是同时错的两个系统，融起来没用。这一点 S5-3 才验证得了。

### 5.5 手写查询扩展表的覆盖问题

现在的扩展表是 `config.EXPANSIONS` —— **8 条手写词条**。

```
命中的题：中文 → 加上英文关键词 → BM25 能查
没命中的题：中文原样 → tokenize → [] → 完全失明（Q8 就是）
```

★ **BM25 的分数在很大程度上不是「算法好不好」，
而是「手写表覆盖到没有」。** 这是个脆弱的依赖 ——
每加一道新题，都可能悄悄落进那个空档。

（真解法：改用嵌入模型做跨语言查询扩展，或者干脆让 dense 兜底。
这属于 S5-3 之后的事。）
