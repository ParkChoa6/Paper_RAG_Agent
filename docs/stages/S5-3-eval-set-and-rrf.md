## 2. 为什么这么写

### 2.1 为什么加题 —— 不是「想看 RRF 效果」，是**验收条件本身不成立**

上一步我用两个检索器的完整排名手算过 RRF 的理论上限：
12 题上 recall@5 **67% → 67%（不动）**，MRR 0.646 → 0.618（更差）。
**上限是 0。** 所以「加题来看 RRF 效果」这个说法本身是错的 —— 那个问题已经答了。

真正的问题是这一条：

> **ROADMAP 给 Stage 5 写的验收是「任何改动后都能定量说明是变好还是变坏」。
> 而当时这句话是假的。**

假的理由两条，都很具体：

1. **5 篇论文一道题都没覆盖。** 旧 12 题的 17 个 target **全部**落在原来 2 篇上。
   新增的 5 篇在评测里的角色**纯粹是干扰项** —— 你对它们做的任何改动，
   尺子**一根刻度都不动**。
2. **旧 12 题几乎全是「概念解释题」**（为什么 / 分成哪几类 / 优缺点各是什么），
   这类题天生偏袒 dense。这不是中立的题集，**是一个已经偏向某一方的题集**。
   拿它当裁判，等于问"你俩谁更像 dense"。

★ 第 2 条比第 1 条严重，也更容易被忽略：**出题人的偏好会伪装成"客观事实"。**
所以我刻意把 E 组做成**事实查找型**（答案是 `CompoundE3D` 的算子名、
`L*` 的两部分损失名、实验用的两个指标名）—— 这类题**词面命中即可**，给 BM25 一个公平的机会。

**结果证明这个设计是有效的**（见 4.4）：BM25 在新增 16 题里拿了 **6 个 top-1**，
而在旧 12 题里只有 **3 个**。

### 2.2 为什么 `guess` 必须**跑之前**写死

这是 `queries.json` 里早就立好的规矩，这次是它**第一次真的抓到我**：

> ★ 为什么要 guess：出题人是我，实现也是我。
>   我出的题会不自觉绕开我自己实现里的弱点。
>   抵消办法有两条：1. 故意塞进我【预期会失败】的题，并预先写死预测排名；
>   2. 跑完之后不许改 guess。预测错就是错，那才是信息。
>   没有 guess，跑完再回头说「我早就知道这题会挂」——那是事后编的，一分钱不值。

**这次我错了 9/16 题。** 而且错得有方向（见 4.4）：**多数是"悲观地错"** ——
我以为会挂的题，两个检索器都答对了。这条系统性偏差本身就是结论（见 5.6）。

### 2.3 为什么往 `EXPANSIONS` 里加词要按 **IDF** 挑，不按"意思对不对"

我在 `config.py` 里写下的判据：

```python
# ★ 只加【在这份语料里有区分度】的词。判断方法：在语料里数一下它出现多少条 ——
#   出现得越少越该加，出现得越多越不该加。
#
#   为什么：「状态」→ "state"、「损失」→ "loss" 这种看着对，其实是【有害】的。
#   它们本身就是高频英文词，IDF 很低，加进去等于往 query 里掺一个
#   「几乎每条文档都匹配」的词 —— 会把一堆不相关的文档捞进候选池，
#   而真正有区分度的那个词被稀释掉了。
#
#   所以：**加 quintuple，不加 state；加 hyperrectangle，不加 operator。**
```

**这个机制是真的，而且我量到了**（4.5：Q13 那题，两个"看着有用"的词把 rank 1 推到 rank 93）。

**但是**——我顺手做的套件级消融**推翻了这个规则的绝对形式**（4.6）：
按 IDF 裁表，整体**掉 15 个点**。所以这条判据最后被改写成**「倾向」而不是「铁律」**，
`config.py` 的注释也回填了这个实测（见第 7 节）。

★ 这个「机制为真、净效应相反」是我这一步学到的**最重要的东西**，单列在 3.3 和 5.4。

### 2.4 为什么 RRF 的结论是「**不建**」

先看 RRF 要什么（`K` 是平滑常数，一般 60）：

```
score(d) = Σ_over_retrievers  1 / (K + rank_i(d))
```

它是**按排名融**的，因为余弦 ∈ [−1,1] 而 BM25 无上界，**分数不可比**。
这个设计理由**仍然成立**。问题不在实现，在**前提**：

> RRF 是一个**民主**的融合器 —— 它把两个投票人当成**同等可信**。
> 于是「自信地错」和「犹豫地对」在它眼里权重一样。

实测这一条**要了命**（4.3）：dense 排第 1（对的）、BM25 排第 33（错的）
→ 融合之后**第 11**。**一个正确的 rank-1 判决，被一个自信的错判决投下去了。**

### 2.5 为什么这一步**不改**任何检索代码

因为改了就有两个变量在动：**尺子变了 + 检索变了**。
那时「数字从 67% 变成 X%」里，有多少是加题带来的、有多少是改代码带来的，**分不开**。

和 S5-0「加完语料先重量一遍基线」是同一条规矩：
**换尺子 → 先重新量基线 → 再动被测对象。**

## 3. 不应该怎么写

### 3.1 ❌ 出题前不查「目标的唯一性」

**症状：题目自己判错，而你会去怪模型。**

「答案唯一」是这份评测集的出题原则。但**它不是靠感觉成立的，是靠扫全语料查出来的。**
这次一查，纠了三处：

| 查到什么 | 后果 |
|---|---|
| `kg-opportunities-challenges#29` 也陈述了「补全的目标」 | 必须一起列进 `targets`，否则模型答对却被判错 |
| `tkg-time-layering#227` 把 `recency` 写成了 `novelty` | **内部自相矛盾 → 不能当 target**（这题只能换答案段落） |
| `tkg-box-embedding#127` 和 `#142` 各写了一遍评测协议 | 必须一起列进 `targets` |

⚠️ 注意第二行：**扫出来的不一定是"漏了一个 target"，也可能是"这题出错了"。**
只往 `targets` 里加东西是一个方向的修法；反方向（这道题的答案段落本身不合格）同样要查。

> 跟 S5-0 那条「我查的是哪个方向？反过来那一半谁来查？」是**同一个病**。

### 3.2 ❌ 用一个「平均排名」概括所有失败

**症状：指标指向错误的修法。**

`eval_retrieve.py` 的 detail 列其实有**三种**"没找到"，但只有一种被单独列出来：

| 显示 | 含义 | BM25 |
|---|---|---|
| `空` | 检索器**一条都没返回** | 池子为空 |
| `?` | **目标压根没进候选池**（和 query 零词面重叠） | Q9 |
| 数字（如 214） | 进了池，但排在很后面 | Q26 |

**后两种在算平均排名时都被记成 `all_k + 1 = 1346`。**
所以「平均排名 70.9」这一个数里，糊着「一条都没捞着」和「捞着了但排 214」两种**完全不同**的病 ——
而它们的修法一个是**加词表入口**，一个是**改排序**。

> ★ 本条和 S5-0 的「平均排名 897.9」是同一类病的**第三次发作**。
> 前两次：`guess` 与实测差几十名 / 空结果与深排名混在一起。
> **一个指标糊掉两种失败时，它一定会把你引向错误的修法。**

### 3.3 ❌ 把「我找到了机制」当成「改了这个会变好」

**症状：你在一个已经被量过的问题上，做出更差的版本，而且觉得很有道理。**

我这次差点就这么干了。完整的过程写在 4.5 / 4.6，一句话版本：

> 我在 Q13 上**量到了**「高频词稀释」的机制（rank 1 → rank 93，两词之间）。
> 于是我准备按 IDF 裁表。
> **裁完整体掉 15 个点。**

**局部为真的机制，整体可以是负的。**
机制解释的是**"为什么会这样"**，不解释**"改了会怎样"** —— 后者只能再量一次。

### 3.4 ❌ 出完题直接跑，不看扩展结果是不是**空的**

**症状：一道题对某个检索器完全失明，而你以为它只是"排得靠后"。**

这一步我立的体检：**把每道题的扩展结果拿去分词，看有没有仍然是 `[]` 的。**

```python
# 空 = BM25 一个字都进不去 = 这题对 BM25 完全失明
```

体检抓出 4 个缺口（`知识推理` / `指标` / `路径型` / `规则型`）。
注意 `知识图谱推理` 在表里、而 `知识推理` 不在 —— 这**纯粹是漏项**，不是设计取舍。

★ 体检和"看分数"是两件事：
- **看分数** → 你会去调那些"排得不好"的题
- **体检** → 你会去补那些"压根进不去"的题

后者更基础，而且要**在跑测之前**做掉，否则你不知道自己漏了什么。

## 4. 怎么验证它真的对了 / 量到了什么

### 4.1 新基线（28 题 / 7 篇 / 1345 条，全部 `+expand`）

| 检索器 | Top-1 | MRR | 平均排名 | recall@5 | 空结果 |

| **dense**（生产） | **50%** | **0.605** | **11.5** | **71%** | 0 |
| BM25 | 32% | 0.429 | 70.9 | 54% | 0 |

**要打败的数字：Top-1 50% / MRR 0.605 / recall@5 71%。**

**一个诚实的观察**：BM25 占 32%/54%，比 12 题时的 25%/50% 高 ——
**是 E 组（事实查找型）拉上来的**。这验证了 2.1 的判断：
**旧 12 题确实偏袒 dense。**

### 4.2 RRF 三个 K 值，**全部净负**

（用两边的**完整排名**做融合，比任何真实 top-k 实现都更宽松 —— 对 RRF 最有利的口径）

★ **最好的一档（K=1）也只追平 dense 的 recall，Top-1 少 7 点、MRR 少 0.051。**
**RRF 在任何 K、任何指标上都没有赢过 dense。**

### 4.3 权重扫描：**最优点是 `w_bm25 = 0`**

「等权是负的」还可能只是**权重没调对**。所以扫一遍（K=60）：

| 1.0 | 0.2 | 46% | 0.579 | 71% |
| 1.0 | 0.3 | 46% | 0.573 | 68% |

连 0.1 的权重都要付出 4 个点的 Top-1。**

**这就是「不建 RRF」的依据** —— 不是"等权没调好"，是**最优权重恰好是 0**，
也就是**别融合**。

### 4.5 Q13 解剖：**机制为真**

我以为 Q13 会排第 1 或第 2（答案是一个很特殊的词 `quintuple`）。
实测 **dense 61 / BM25 93**。查下去，收获比预期大得多：

**先看 BM25。把 query 拆开，逐层加词：**

| query | 候选池 | target 排名 |
|---|---|---|
| `quintuple` | **1** | **1** |
| `multi-hop completion quintuple` | 大量 | **82** |
| `ftmi multi-hop completion quintuple`（= 实际评测用的） | 大量 | **93** |

★ **两个"看着有用"的词，把一个 rank 1 的答案推到了 93。**
而 `ftmi` 单独搜，target **压根不在池子里**（28 条候选，它不在里面）——
**`ftmi` 对这个 chunk 的检索贡献是 0，稀释贡献是 11 名。**

原因（`idf` / `df` 实测，`df` 单位是 chunk）：

```
idf[quintuple] = 6.80   df = 1      ← 全库唯一，这就是"锚点"
idf[ftmi]      = 3.86   df = 28
idf[completion]= 2.72   df = 88
idf[hop]       = 2.33   df = 130
idf[multi]     = 1.98   df = 185    ← 全库 1/7 的段落都有它
```

`quintuple` 的 IDF 是 `multi` 的 **3.4 倍**，但**它只有 1 个词**，
而 `multi-hop` / `completion` 在那些 TKG 论文里被**反复重复**——
BM25 的 `k1` 饱和 + 长度归一化（`#45` 长 99，`avgdl` 58.2，被罚 1.53×）
让「一条稀有词」输给了「四条高频词的堆叠」。

**再看 dense —— 同一个词，行为完全不同：**

| query | dense 排名 |
|---|---|
| `quintuple` | **30** |
| 中文原问题 | 59 |
| 中文原问题 + 扩展（= 实际评测用的） | 61 |

★ **同一个全库唯一的稀有词：BM25 说 rank 1，dense 说 rank 30。**

为什么？因为 dense 把 **99 个 token 平均成一个 1024 维向量**，
一个稀有词只占很小的一份；而"定义 / 元素列表"这种**问法**，
语义上有大把段落比它更近。
**dense 不认为"这个词唯一"是一件多么重要的事 —— BM25 认为这是最重要的事。**

**★ 这两个数字放在一起，是两种检索器互补性最干净的一次展示。**
它同时解释了 RRF 为什么救不了这题：**两个 voter 都错（61 / 93），没有"一对一错"可融。**

### 4.6 ⚠️ 词表消融：**机制为真，净效应相反**

4.5 的机制指向一个显然的修法：**按 IDF 裁掉高频词条。** 我照做了：

| 表 | 空结果 | 目标未进池 | Top-1 | MRR | recall@5 |
|---|---|---|---|---|---|
| **FULL（28 条）** | **0** | 1 | **32%** | **0.429** | **54%** |
| 裁到锚点 df ≤ 150（去 2 条） | — | — | 32% | 0.428 | 54% |
| 裁到锚点 df ≤ 100（去 6 条） | **2** | 1 | 29% | 0.389 | 46% |
| 裁到锚点 df ≤ 80（去 10 条） | **3** | 1 | 32% | 0.416 | 50% |
| 裁到锚点 df ≤ 40（去 18 条） | **8** | 2 | 25% | 0.325 | **39%** |

★ **裁掉 18 条高频词条 → 8 道题直接失明**（空结果 0 → 8），recall@5 掉 15 点。

机制说清楚了：**高频词条是"入口"，不只是"噪音"。**
`multi-hop` 这种词对 Q13 是稀释，但对另外十几道题是**唯一能把候选池撑开的词**。
裁掉它，那些题在 BM25 里**连一条候选都没有** —— 从"排得靠后"直接变成"完全失明"。

> **这是这一步最重要的一课：**
> **局部为真的机制，整体可以是负的。「我找到了机制」不等于「改了这个会变好」。**

所以 `config.py` 里那条判据**保留了，但降级成"倾向"**，并把这次实测回填进去。

### 4.7 我预注册的 `guess` 错在哪（错的**方向**也是信息）

16 道新题里：**方向正确 7 题、明显错 2 题、一半对一半 7 题。**

把错的按方向分类，出现了一个**系统性偏差**：

## 5. 你要补的概念

### 5.1 RRF 为什么按**排名**融，而不是按分数

因为**分数不可比**：

| | 取值范围 | 含义 |
|---|---|---|
| 余弦相似度 | [−1, 1] | 0.65 是"挺像" |
| BM25 | [0, +∞) | 16.78 是"挺强"，但**和 0.65 没法比** |

直接加权求和，等于**拿摄氏度加华氏度**。RRF 用 `1/(K + rank)` 把两者都映射成
「你在你自己那份榜单里排第几」，**尺度问题就消失了**。

★ 这个设计理由**至今成立**，不是错的。RRF 失败的原因在**前提**，不在实现（见 5.2）。

### 5.2 RRF 的前提：两个投票人要**同强**，而且**错得不相关**

RRF 是一个**民主**融合器：

```
score(d) = 1/(K + rank_dense(d)) + 1/(K + rank_bm25(d))
```

**两个投票人的票，权重完全一样。**

于是：

| 情形 | RRF 怎么看 | 对不对 |
|---|---|---|
| dense 第 1（对）+ BM25 第 1（对） | 稳居第 1 | ✅ |
| dense 第 1（对）+ BM25 第 33（错） | **掉到第 11** | ❌ **一个对的判决被投下去了** |
| dense 第 139（错）+ BM25 第 83（错） | 第 104 —— **两个都错，谁也救不了** | ➖ 无变化 |

**实测（4.4）：第二行那种情形发生了 3 次，第三行发生了很多次，
而「BM25 对 / dense 错」的情形一次都没能转换成前五。**

★ 一句话：**融合器的收益上限，取决于"两个检索器的错误有多不相关"。
在这个语料上，dense 和 BM25 的错误不是不相关 —— 是 BM25 单方面错得更凶。**

### 5.3 候选池不是常数 → 「没找到」有**三种**

dense 永远给全部 N 条打分；BM25 只给**含有至少一个 query 词**的段落打分（实测 0~646 / 1345）。

所以三种"没找到"要分开看：

| 状态 | 含义 | 该怎么修 |
|---|---|---|
| `空`（池子为空） | query 一个词都没匹配上 | **补词表 / 补扩展** |
| `?`（未进池） | 目标段落和 query 零词面重叠 | **补词表 / 换问法** |
| 数字（如 214） | 进了池，但排在很后面 | **改排序 / 改相似度** |

**它们的修法完全不同**，所以不能糊成一个"平均排名"。

★ 而且这也说明：**BM25 的「第 94 名」和 dense 的「第 35 名」不在同一个尺度上** ——
分母就不一样（94/266 vs 35/1345）。

### 5.4 「机制」与「净效应」是两件事

| | 问的是 | 怎么得到 |
|---|---|---|
| **机制** | 「为什么会这样？」 | 拆开看、做消融、读中间量 |
| **净效应** | 「改了这个会怎样？」 | **再量一次整体** |

这两件事**经常给出相反的答案**（4.5 vs 4.6 就是活例）。

★ 危险在于：**机制的解释力很强，会让你产生"我已经懂了，所以我知道怎么修"的错觉。**
抵御办法只有一个 —— **改完再量一次，用同一把尺子。**

> 这一步同一类的事发生了**两次**：RRF（理论上是标准做法 → 实测净负）
> 和词表裁剪（机制清楚 → 实测净负 15 点）。

### 5.5 稀有词在两种检索器里的**地位不同**

| | BM25 | dense |
|---|---|---|
| 稀有词 `quintuple`（df=1） | **最重要的信号** —— 它就是判别式 | **只占向量的很小一份** |
| 实测 | rank **1** | rank **30** |

- **BM25 是"词的账本"**：一个词越稀有，权重越高。稀有词 = 精确的路标。
- **dense 是"意思的平均"**：整段话压成一个向量，**单个词的分量被段落长度摊薄**。
  段落的"问法像不像"（是不是在列举、是不是定义）**比**某一个词是否稀有**更重要**。

★ 这不是谁好谁坏，是**两种检索器的分工**：
BM25 抓**罕见的专名 / 符号**，dense 抓**换了说法的同一个意思**。
真正的问题是：**它们的错误相关度太高，融不到一起。**

### 5.6 为什么最优点是 `w=0`，但 BM25 **仍然要保留**

这两件事不矛盾：

| 问题 | 答案 |
|---|---|
| 「加进去会不会涨分？」 | **不会**（4.2 / 4.3 实测） |
| 「该不该保留？」 | **该** —— 结构性理由：它有**独立的故障模式** |

BM25 在 Q9 上给出 `?`（dense 给 21），在 Q13 上给出 rank 1 的原始信号（dense 给 30）——
**它能看到 dense 看不到的东西。**

★ 但**"能看到"不等于"现在用得上"**：

- 要做**融合**，前提是两个检索器**同强**——现在不是（32% vs 50%）
- 要让 BM25 有用，得先**把它单独做强**（改切分？改词表？），或者
- **换一种用它的方式**：不是平权融合，而是**当 dense 的置信度低时才启用**（路由 / 门控），
  或者**用它的信号做 rerank 特征**（而不是投票）。

**RRF 被否掉的，是「平权投票」这一种用法，不是 BM25。**

### 7.1 ✅ 本步的结论：**S5-4（RRF）不做了**

原判据写成了一条**铁律**（「只加稀有词」）。实测（4.6）不支持铁律的形式，
所以降级为**倾向**，并把「裁表掉 15 点 / 空结果 0→8」写进注释 ——
**下一个人（可能是三个月后的我）看到这条规则时，会同时看到它的反例。**

### 7.3 ⚠️ `eval_retrieve.py` 仍然只有一种"没找到"被单独列出

`空结果` 有独立一列，`?`（未进池）没有，它被混进平均排名（3.2）。
**修法很小**：在 `evaluate()` 里加一个 `not_in_pool` 计数，和 `empty` 并列即可。
**没做，因为本步的结论不依赖它。记下来。**

### 7.4 ⚠️ RRF 的融合代码**没有进仓库**

4.2 / 4.3 的数字来自一次性的探针脚本（用完即弃）。
公式是 5 行的东西，记录里写全了，**但严格说这不可复现**。
如果以后要重做 RRF（比如 BM25 变强之后），**得重写一遍探针**。
**这是本步的一个真实的可复现性缺口，不掩饰。**

### 7.5 ⚠️ 下一步（Rerank）有一个**我没验证的前提**

证据支持的最高价值一步是 **Rerank（cross-encoder 重排）**：

- dense 的 recall@5 是 71%、Top-1 只有 50% —— **前五里有对的，只是没排到第 1**，
  这正是 rerank 擅长的事（rerank 只重排、不召回，代价可控）
- 而且它**不受 5.2 那个前提的约束**：rerank 不是"两个 voter 投票"，
  是一个**更强的裁判**看完整 query-passage 对

**但是**——

> ⚠️ **本地 Ollama 上有没有能用的 cross-encoder reranker，我还没验证。**
> `bge-reranker` 系列在 HuggingFace 上是标准选择，但**它是不是能通过 Ollama 跑，
> 或者需不需要另装 sentence-transformers / 单开一个进程**，我没查。
> **没有的话这一步要换做法** —— 这个我**不确定，所以先不写进计划。**

★ 按本仓库自己的规矩：**先验证前提，再承诺步骤。**
这不是"待办"，是"待查"。
